# 多 Agent 协作计划（分工 Agent + 主管调度）

> 本文档规划多 Agent 协作：文档分析 Agent + 数据查询 Agent + 报表生成 Agent + 主管调度。**方案待定，本轮不实现代码。**
> 定位：展示价值高、工作量大。**须先想清楚"是否真需要多 Agent"——避免为了用而用。**

---

## 一、现状分析

| 维度 | 现状 | 证据 |
|------|------|------|
| Agent 数量 | **单 Agent 多工具** | 全程一个 `UnifiedAgent` + 一个 LLM 决策角色 |
| 职责分离 | 有，但**非自主 Agent** | `DecisionEngine`/`Scheduler`/`SkillExecutor` 是被主循环调用的无状态服务，无各自推理循环 |
| 多后端预留 | 有 | `tool_registry.ToolMeta.source_server` 注释"预留多服务器扩展" |
| 编排 | 静态 Skill steps + ReAct turns | 无状态机/DAG，无 Agent 间消息传递 |

**核心事实**：当前是"一个大脑用多个工具"，不是"多个专家协作"。

---

## 二、先回答：为什么需要多 Agent？（诚实评估）

**单 Agent 的瓶颈**（多 Agent 的立足点）：
- 单一 LLM 上下文里塞进所有工具 + 所有职责，prompt 臃肿、角色混杂、易分心。
- 复杂任务（"分析这批文档 → 查出关键数据 → 生成报表"）是**有阶段依赖的流水线**，单 Agent 的伪多轮 ReAct（成功即退出）难以稳定编排。

**但要警惕过度设计**：
- 若任务只是"查天气/查知识库"这类单步，多 Agent 是**纯负担**（多几次 LLM 调用、更慢、更贵）。
- 多 Agent 的价值只在**真正的多阶段、跨领域任务**上体现。

**结论**：多 Agent 应作为**复杂任务专用通道**，与现有单 Agent 并存，由主管按任务复杂度路由（见 `LangGraph编排.md`）。

---

## 三、目标：三分工 Agent + 主管

```
                  ┌─────────────────┐
   用户复杂任务 → │  主管 Agent      │ 拆解任务 → 派活 → 汇总
                  │  (Supervisor)   │
                  └────┬───┬───┬────┘
          ┌────────────┘   │   └────────────┐
          ▼                ▼                ▼
   ┌────────────┐  ┌────────────┐  ┌────────────┐
   │ 文档分析    │  │ 数据查询    │  │ 报表生成    │
   │ Agent      │  │ Agent      │  │ Agent      │
   │ 用RAG检索   │  │ 查结构化数据 │  │ 汇总成报告   │
   └────────────┘  └────────────┘  └────────────┘
```

| Agent | 职责 | 复用现有能力 |
|-------|------|-------------|
| **主管** | 拆解任务、决定调用哪些子 Agent、按依赖编排、汇总结果 | 类似现有 `DecisionEngine` 的决策逻辑 |
| **文档分析** | 从知识库检索并分析文档 | 复用 `retriever` 全套（改写+混合检索+重排） |
| **数据查询** | 查询结构化数据（如表格/DB） | 复用 `ask_knowledge_base` 或新增 SQL 工具 |
| **报表生成** | 把前两者结果汇总成结构化报告 | 复用 LLM 生成 + `build_prompt` 思路 |

## 四、落地设计

### 4.1 实现基座：LangGraph（详见 `LangGraph编排.md`）

- 用 LangGraph 的 **Supervisor 模式**（主管节点 + 子 Agent 节点 + 条件边）实现，天然支持状态传递、条件路由、子图。
- 每个子 Agent = 一个 LangGraph 节点，内部可复用现有工具/检索能力。
- **不替换自研 ReAct**：单步任务仍走现有 `UnifiedAgent`，多阶段任务才进 LangGraph 多 Agent 图。

### 4.2 Agent 能力复用（关键：不重复造轮子）

- **文档分析 Agent** 直接调 `retriever.retrieve_and_answer()`（已有改写/混合/重排全链路）。
- 现有 **Skill 体系**（`skills/builtin/` 深度检索等）可包装成子 Agent 的内部能力——评估现有 3 个 Skill 能否直接复用为 Agent 工具。
- **数据查询 Agent** 若知识库无结构化数据源，需先明确数据从哪来（现有只有文档向量库，可能需要新增数据源，否则此 Agent 无用武之地）。

### 4.3 Agent 间通信

- 走 LangGraph 的共享 State（TypedDict），主管把子任务写入 state，子 Agent 读取并回写结果，主管汇总。
- 复用 `MCP工程化.md` 的 trace_id，让多 Agent 调用链在 LangFuse 里可视化。

## 六、与现有体系联动

- **检索**：文档分析 Agent 复用现有 RAG 全链路，零重写。
- **编排**：依赖 `LangGraph编排.md` 的基座；两文档需一起落地。
- **可观测**：多 Agent 调用树用 LangFuse 可视化（否则多 Agent 排障极难）。
- **成本**：多 Agent = 多次 LLM 调用，`token_tracker` 需按 Agent 维度记账。

---

## 七、优先级与代价

- **优先级**：★★★ 展示价值高（"多 Agent 协作"是热门简历词），但**依赖 LangGraph 先落地**、工作量最大、且需要真实的多阶段任务场景才有意义。
- **代价**：LangGraph 学习 + 三个 Agent + 主管编排；成本翻数倍；调试复杂。
- **前置条件**：先落地 `LangGraph编排.md`；确认有真实的多阶段任务需求（否则是过度设计）。

---

## 八、风险与注意

- **过度设计风险（最大）**：本项目当前任务多为单步检索，多 Agent 可能是"杀鸡用牛刀"。**建议先造一个真实的多阶段 demo 场景**（如"分析6G文档→提取关键指标→生成调研摘要"）证明价值，再投入。
- **数据查询 Agent 悬空**：现有只有文档向量库，无结构化数据源；此 Agent 需先明确数据来源，否则名不副实。
- **成本与延迟**：多 Agent 显著增加 LLM 调用，需成本护栏 + 复杂度路由（简单任务不进多 Agent）。
- **保留单 Agent 亮点**：不替换自研 ReAct，多 Agent 是"复杂任务专用通道"，讲"按复杂度选引擎"的故事。

## 九、优化建议（贴合面试定位，降低落地成本）

### 9.1 先做最小 Demo：主管 + 2 Agent（砍掉悬空的数据查询）

不必一上来做三个 Agent。**先做「主管 + 文档分析 + 报表生成」两子 Agent 最小版**，跑通一个完整多阶段任务：

> **Demo 场景**："帮我分析知识库中 6G 物理层安全的相关文档，生成一份 300 字调研摘要"
> 主管拆解 → 文档分析 Agent 检索提炼（复用 `retriever`）→ 报表生成 Agent 整理成结构化报告

**收益**：完整展示多 Agent 流程，同时**避开"数据查询 Agent 无数据源"的悬空问题**，工作量减少约 1/3，面试演示完全够用。后续有结构化数据源了再补第三个 Agent。

### 9.2 强化"复杂度路由"设计（这本身就是架构亮点）

把"任务要不要走多 Agent"的判定做扎实，三层递进：

1. **关键词粗筛**：含"生成报告/分析汇总/整理文档/先…再…"等 → 候选多 Agent。
2. **LLM 判断复杂度**：确认是"多阶段、有依赖"的任务再路由到多 Agent 通道（注意 max_tokens≥512，推理模型陷阱）。
3. **兜底**：判断不清默认走单 Agent，避免简单任务被过度处理。

> 面试话术升级为"**按需调度的双引擎架构**"，比"我做了多 Agent"更有深度。详见 `LangGraph编排.md` 的 `engine_router`。

### 9.3 明确与自研 ReAct 的定位差异（突出架构层次）

| 引擎 | 定位 | 适用任务 |
|------|------|---------|
| **自研 ReAct 单 Agent** | 通用灵活兜底 | 单步、不确定、开放式长尾任务 |
| **LangGraph 多 Agent** | 专用高效处理 | 多阶段、有明确依赖的结构化流水线 |

形成 **"通用灵活兜底 + 专用高效处理"** 的双引擎模式——层次感强于单纯堆多 Agent，且**保住自研 ReAct 核心亮点**。

### 9.4 与 Skill 体系打通：工具→Skill→Agent 三层复用梯队

把现有 Skill 作为子 Agent 的内部能力，形成清晰的能力复用层级：

```
Agent 层    完整领域能力，多阶段任务协作      ← 新增
   ↑ 复用
Skill 层    固定工具组合，高频场景快速执行     ← 现有 skills/builtin/
   ↑ 复用
工具层      MCP 原子工具                     ← 现有 mcp_server.py
```

> **价值**：这是本方案最漂亮的架构叙事——不是"又加一层多 Agent"，而是**把现有工具/Skill 沉淀为 Agent 的能力基座**，三层各司其职、逐层复用。子 Agent 内部直接调 Skill（如文档分析 Agent 用现有"深度检索"Skill），零重复建设。
