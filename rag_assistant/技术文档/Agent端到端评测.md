# Agent 端到端轻量评测 —— 工具调用成功率 + 端到端延迟

> 目标：补上现有评测体系缺失的「Agent 端到端指标」，让 Agent 能力有量化支撑，而非只有 RAG 检索指标。

## 一、S —— Situation（背景）

现有评测体系 `rag_eval/` 基于 RAGAS，只覆盖 **RAG 检索质量** 四个指标：

| 指标 | 含义 |
|------|------|
| context_precision | 上下文精准率 |
| context_recall | 上下文召回率 |
| faithfulness | 忠实度（幻觉率 = 1 - faithfulness） |
| answer_relevancy | 答案相关性 |

**缺口**：这 4 个全是 RAG 检索/生成维度，**没有任何 Agent 端到端指标**——即岗位 JD 最看重的「任务准确率、工具调用成功率、端到端响应延迟」。

而项目其实已经在产出 Agent 运行数据：`tool_audit.py` 全程记录每次工具调用的 `latency_ms / success / retry_count / trace_id / timestamp`（`tool_audit.jsonl`），只是**没有聚合利用**。

## 二、T —— Task（任务）

基于已有的 `tool_audit.jsonl`，聚合出一份「Agent 工具调用成功率 + 端到端延迟」的**轻量评测**，要求：

1. **轻量**：零额外成本（不调 LLM），单脚本秒级出结果；
2. **真实**：数据来自生产审计，不额外跑任务；
3. **可复用**：随审计数据积累，随时重跑刷新指标。

## 三、A —— Action（方案对比）

三个候选方案：

### 方案 A：离线聚合统计脚本（零成本）

独立脚本读 `tool_audit.jsonl`，按 `trace_id` 分组聚合，输出报告。

**优点**
- **零成本**：纯本地统计，不调 LLM、不跑任务；
- **轻量**：单文件脚本，秒级出结果，随数据积累可反复重跑；
- **真实**：数据来自 `tool_audit.py`（全程 try/except 记录，不干扰主链路）。

**缺点**
- **是「指标统计」不是「任务评测」**：只能算「工具调用是否成功」，无法判断「任务是否完成」（例：工具调用成功但答案答非所问，此方案看不出）；
- **端到端延迟是近似值**：`tool_audit` 记录的是「事件时间点」而非「区间」，不含 LLM 首尾推理时间（详见下文口径）；
- **依赖数据积累**：当前 `tool_audit.jsonl` 仅 3 条，统计意义弱。

### 方案 B：任务评测集 + LLM-as-a-Judge（补任务准确率）

定义 N 个 Agent 任务（含预期结果），跑完用 LLM 判断「任务是否成功完成」，算任务准确率；结合审计数据算工具调用成功率 + 端到端延迟。

**优点**
- **真「端到端评测」**：能算出 JD 最想要的「任务准确率」；
- **能发现隐蔽问题**：「工具调用成功但任务失败」这类仅靠审计算不出来的 case。

**缺点**
- **成本高**：每次评测要调 LLM 打分；
- **周期长**：需设计任务集、跑任务、写 judge prompt；
- **复杂度高**：比方案 A 多「任务执行 + LLM 判定」两个环节。

### 方案 C：扩展 RAGAS 框架（统一评测体系）

在 `rag_eval/run_eval.py` 上扩展 Agent 端到端指标，纳入统一评测。

**优点**
- 与现有 RAGAS 体系统一，长期演进。

**缺点**
- **水土不服**：RAGAS 本身只测 RAG 质量，不测 Agent 任务，硬扩展是「把两套维度塞进一个框架」；
- **改动大、周期长**：短期收益低，属于过度工程。

### 方案对比总表

| 维度 | A 离线聚合 | B 任务评测集 | C 扩展 RAGAS |
|------|-----------|-------------|-------------|
| 成本（调 LLM） | 无 | 高 | 高 |
| 实现复杂度 | 低（单脚本） | 中 | 高（改框架） |
| 能否算「任务准确率」 | ❌ 只能算工具成功率 | ✅ 能 | ⚠️ 勉强 |
| 能否算「端到端延迟」 | ⚠️ 近似 | ✅ 较准 | ✅ 较准 |
| 落地周期 | 半天 | 1-2 周 | 1 周+ |
| 复用现有数据 | ✅ 直接用 | ⚠️ 需跑任务 | ⚠️ 需改造 |

## 四、R —— Result（推荐方案）

**推荐：方案 A 先行，方案 B 作为 P5 演进。**

- **现在用方案 A**：零成本快速产出「工具调用成功率 + 端到端延迟」报告，补上 JD 缺的指标，让 Agent 能力有量化支撑；
- **数据积累后走方案 B**：补「任务准确率」，形成完整 Agent 端到端评测；
- **方案 C 不推荐**：RAG 评测与 Agent 评测是两套维度，强扭在一起不如分开维护。

### 指标口径（必须诚实定义）

| 指标 | 定义 | 备注 |
|------|------|------|
| 工具调用成功率 | 成功调用数 ÷ 总调用数（聚合 `success` 字段） | 精确 |
| 工具调用耗时分布 | `latency_ms` 的均值 / 中位 / P95 | 精确 |
| 重试率 | `retry_count > 0` 的调用占比 | 精确 |
| **端到端延迟** | 同一 `trace_id` 内 `max(timestamp) - min(timestamp)` | **近似值**：不含 LLM 首尾推理时间 |

> ⚠️ **端到端延迟的诚实说明**：`tool_audit` 记录的是「事件点」而非「区间」，故只能以「同 trace 首事件 → 末事件」的跨度近似。真正的端到端应从 `unified_agent._run()` 的开始/结束时间戳计算，属于后续增强项（可在审计里补一条 `type="trace"` 带 `elapsed_ms`）。

### 当前数据量限制

`tool_audit.jsonl` 当前仅 3 条（2 工具调用 + 1 决策），聚合结果**无统计意义**。脚本会内置「数据量不足」告警（阈值建议 `>= 30` 条工具调用），并在报告中如实标注样本数。
