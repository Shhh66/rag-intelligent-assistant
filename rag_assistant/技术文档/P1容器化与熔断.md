# P1 容器化与熔断（STAR 法则 + 两轮审查闭环）

> 部署运维改造的第二阶段。针对「痛点 3：无容器化」「痛点 4：LLM 无熔断」的审查发现，逐条核对 + 用 STAR 法则讲清来龙去脉，附技术栈、架构、核心代码，以及 2-3 个方案的优缺点对比与推荐。
>
> **熔断部分经过两轮审查**：第一轮发现「接入点错位」，第一次整改又踩了「下沉到无状态子进程」的坑，第二轮才收敛到「主进程常驻 + 关键路径熔断 + 子进程 fallback 兜底」的正确分层。这是本文档最有价值的部分。

## 〇、两轮审查核对结论

### 痛点 3：无容器化 → Dockerfile + compose（已修复，有坑）

| # | 审查点 | 核对 | 证据 |
|---|--------|------|------|
| 1 | api_server 未容器化 | ✅ **属实** | [app.py:143](app.py#L143) 硬编码 `http://localhost:8000/api/auth/login`；[docker-compose.yml](docker-compose.yml) 无 `api-server` 服务，登录必失败 |
| 2 | slim 镜像缺系统库 | ✅ **属实（风险）** | [Dockerfile](Dockerfile) `FROM python:3.12-slim`；torch/onnxruntime 缺 `libgomp1` |
| 3 | PID 1 / 子进程信号 | ✅ **属实** | 无 `tini`/`dumb-init`，SIGTERM 时 mcp_server stdio 子进程可能变孤儿 |
| 4 | Windows 挂载 D 盘需授权 | ✅ **属实** | compose 绝对路径挂载，Docker Desktop 需授权 D 盘共享 |
| 5 | main 无 healthcheck | ✅ **属实** | compose `main` 段无 `healthcheck`，embed/rerank 有 |

### 痛点 4：LLM 无熔断 → 熔断器（两轮审查）

**第一轮审查：接入点错位（保护的是 MCP 通道而非 DeepSeek）**

| # | 审查点 | 核对 |
|---|--------|------|
| 1 | 接入点错位 | ✅ **属实（核心）**：熔断器接在 [mcp_client_manager.py:100](mcp_unified_agent/mcp_client_manager.py#L100) `call_tool`，DeepSeek 调用在子进程 [retriever.py](retriever.py)，异常被 [mcp_server.py](mcp_server.py) `except Exception → return "问答处理出错…"` 吞成字符串，`isError=False` |
| 2 | 粒度太粗 | ⚠️ **方向对，例子需修正**：全局单例属实，但「天气 ConnectionError 误伤知识库」不成立——`isError=True` 不记 failure；真正的全局熔断触发源是通道级故障 |
| 3 | HALF_OPEN 并发放大 | ✅ **属实**：[circuit_breaker.py](mcp_unified_agent/circuit_breaker.py) 原 `return True` 无条件放行 |

**第一次整改（错误，被第二轮审查推翻）**：把熔断器「下沉到子进程」，在 `retriever.py` 的 DeepSeek 调用处包裹熔断器。

**第二轮审查：下沉到无状态子进程 = 熔断器形同虚设**

| 问题 | 结论 |
|------|------|
| 熔断器状态必须**跨请求累积** | [unified_agent.py:185](mcp_unified_agent/unified_agent.py#L185) 每次 `chat()` 都 `async with stdio_client(...)` **新建子进程、用完即断**；子进程里 `get_breaker("deepseek")` 每次全新实例，`failure_count` 归零 |
| 单次请求内最多 2 次 LLM 调用 | 阈值 5 **永远到不了**，熔断器从不 OPEN |
| 真正高频的 LLM 调用在主进程 | [decision_engine.py](mcp_unified_agent/decision_engine.py) 的 `decide_with_skills`（每轮 ReAct 都调）+ `final_answer` + `match_skill`，[skill_executor.py](mcp_unified_agent/skill_executor.py) 的 2 处——这些**全被漏掉了** |

**根本教训**：熔断器三条原则有优先级——「**状态能跨请求累积**」是地基，「离故障源近」「per-destination 分区」都排在它后面。第一次整改用「离故障源近」覆盖了更前置的「状态累积」，本末倒置。

**最终方案（本轮落地）**：熔断器撤回主进程常驻进程，接 decision_engine + skill_executor；子进程撤熔断，靠 fallback 兜底。

## 一、STAR 法则

### S — 情境（Situation）

P0 完成后，系统已把嵌入/重排拆成独立服务、权限改成无状态参数透传。P1 有两个「生产化」目标：容器化 + 给 DeepSeek 加熔断。

### T — 任务（Task）

1. Dockerfile + docker-compose 编排「api + main + embed + rerank」四服务，模型缓存挂 D 盘。
2. 熔断器保护 DeepSeek：连续失败快速失败、冷却后自动恢复。

### A — 行动（Action）

容器化一次到位；熔断器经过两轮审查才收敛：

1. **第一轮**：熔断器接在 `call_tool` 层，发现「保护的是 MCP 通道而非 DeepSeek」。
2. **第一次整改（错）**：下沉到子进程的 DeepSeek 调用处。
3. **第二轮审查**：发现下沉到 per-request 子进程，状态无法跨请求累积，熔断器形同虚设——且漏掉了主进程 decision_engine 这个真正高频调用点。
4. **最终整改（对）**：撤回主进程，在 decision_engine + skill_executor 的 LLM 调用点接入 `call_llm_with_cb`，`CircuitBreakerError` 冒泡到 `unified_agent.chat()` 快速失败；子进程撤熔断，靠现有 fallback 兜底。

### R — 结果（Result）

1. **容器化**：`docker compose up` 一条命令起完整 4 服务，登录可用。
2. **熔断**：主进程常驻的 `get_breaker("deepseek")` 状态跨请求累积，DeepSeek 持续故障 → 连续 5 次失败 OPEN → 冷却 30s 放 1 次试探 → 恢复 CLOSED；熔断期间快速失败返回「下游模型暂时不可用」，不再进入 ReAct 循环反复重试。子进程 RAG 失败靠 fallback 兜底，不误伤后台记忆抽取。

## 二、技术栈

| 模块 | 技术 | 说明 |
|------|------|------|
| 容器化 | Docker + Docker Compose | 多服务编排、`depends_on: service_healthy` |
| 系统库 | `python:3.12-slim` + `apt` 补 `libgomp1`/`libglib2.0-0` | 小镜像 + 声明式依赖 |
| PID 1 | `tini` | 回收孤儿子进程、转发信号 |
| 熔断器 | 自研三态状态机（thread-safe） | CLOSED/OPEN/HALF_OPEN |
| 下游分区 | per-destination breaker | 不同下游独立熔断 |
| 熔断宿主 | **主进程常驻**（`unified_agent._llm_client`） | 状态跨请求累积的前提 |

**核心原则**：「状态能跨请求累积」>「离故障源近」——熔断器必须放在常驻进程的高频调用点。

## 三、架构设计

### 3.1 熔断器最终架构（两轮审查收敛后）

```
主进程（Streamlit 常驻，st.session_state.agent 持久）
  unified_agent.chat()
    ├─ DecisionEngine.decide_with_skills ──┐
    ├─ DecisionEngine.final_answer ────────┤
    ├─ DecisionEngine.match_skill ─────────┼─▶ call_llm_with_cb ──[breaker: deepseek]──▶ DeepSeek
    └─ SkillExecutor._post_process/_summarize
                                            │ 熔断 OPEN → 抛 CircuitBreakerError
                                            ▼
                              unified_agent.chat() 捕获 → 返回「下游模型暂时不可用」

MCP stdio 子进程（每次请求新建，per-request）
  mcp_server.py → retriever.answer_with_fallback
    ├─ _call_llm（无熔断，统一超时 + token 埋点）
    └─ 失败靠 fallback 兜底（检索失败→直答、翻译失败→跳过）
```

**关键设计**：
1. **熔断器放常驻进程**：主进程 `_llm_client` 在 `__init__` 创建、跨请求复用，`get_breaker("deepseek")` 的 `failure_count` 天然累积——这是熔断能走到 OPEN 的前提。
2. **子进程不接熔断**：per-request 生命周期，状态每次归零，熔断器在这里没有「跨请求」价值；单次请求内失败靠 fallback 兜底。
3. **熔断快速失败**：`CircuitBreakerError` 从 decision_engine 冒泡到 `chat()`，返回可读提示，而不是被 ReAct 循环反复重试。
4. **fallback ≠ 熔断**：fallback 管「单次请求内降级」，熔断管「跨请求快速失败」，职责边界清晰。

### 3.2 容器化整改前后对比

```
【整改前】                         【整改后】
embed  ──┐                        api-server (:8000)  ← 补上
rerank ──┼─▶ main (streamlit)      embed-server (:8001)
          (登录调 localhost:8000    rerank-server (:8002)

                                   │ 登录走 API_SERVER_URL ──┘
                                   └ 所有容器 ENTRYPOINT ["tini","--"]
```

## 四、核心代码（已实施）

### 4.1 熔断器：per-destination + HALF_OPEN 单探测 + 统一调用入口（circuit_breaker.py）

```python
class CircuitBreaker:
    def __init__(self, failure_threshold=5, cooldown_seconds=30.0, half_open_max_probes=1):
        self.failure_threshold = failure_threshold
        self.cooldown_seconds = cooldown_seconds
        self.half_open_max_probes = half_open_max_probes  # HALF_OPEN 只放 N 次试探
        self.half_open_probes = 0                          # 当前已放行的试探数
        ...

    def allow_request(self) -> bool:
        with self._lock:
            if self.state == "CLOSED":
                return True
            if self.state == "OPEN":
                if time.time() - self.last_failure_time >= self.cooldown_seconds:
                    self.state = "HALF_OPEN"
                    self.half_open_probes = 0
                else:
                    return False
            # HALF_OPEN：只放行 half_open_max_probes 次试探，其余拒绝（防并发放大）
            if self.half_open_probes < self.half_open_max_probes:
                self.half_open_probes += 1
                return True
            return False

    def record_failure(self):
        with self._lock:
            self.failure_count += 1
            self.last_failure_time = time.time()
            if self.state == "HALF_OPEN" or self.failure_count >= self.failure_threshold:
                self.state = "OPEN"  # 试探失败立即回 OPEN

# per-destination：每个下游一个独立熔断器
_breakers = {}
def get_breaker(destination: str = DESTINATION_MCP_CHANNEL) -> CircuitBreaker:
    global _breakers
    if destination not in _breakers:
        from config import CB_FAILURE_THRESHOLD, CB_COOLDOWN_SECONDS
        _breakers[destination] = CircuitBreaker(CB_FAILURE_THRESHOLD, CB_COOLDOWN_SECONDS)
    return _breakers[destination]

# 统一 LLM 调用入口（只在「常驻进程」里调用）
def call_llm_with_cb(client, model, messages, temperature, max_tokens, call_site):
    """熔断 + 成功/失败记录。熔断 OPEN → 抛 CircuitBreakerError 快速失败。"""
    breaker = get_breaker(DESTINATION_LLM)
    if not breaker.allow_request():
        raise CircuitBreakerError("DeepSeek 熔断打开，请求快速失败")
    try:
        resp = client.chat.completions.create(model=model, messages=messages,
                                              temperature=temperature, max_tokens=max_tokens)
    except Exception:
        breaker.record_failure()
        raise
    breaker.record_success()
    from token_tracker import get_tracker
    get_tracker().record(model, resp.usage, call_site=call_site)
    return resp
```

### 4.3 熔断快速失败入口（unified_agent.py chat 捕获）

```python
def chat(self, user_input, kb_groups=None, user_id=None) -> str:
    try:
        return asyncio.run(self._run(user_input, kb_groups))
    except CircuitBreakerError as e:
        # 熔断打开：下游模型持续故障，快速失败，不再进入 ReAct 循环反复重试
        logger.warning(f"下游模型熔断: {e}")
        return "下游模型服务暂时不可用（熔断保护中），请稍后重试。"
    except Exception as e:
        return f"处理请求时出现错误: {type(e).__name__}: {e}"
```

### 4.4 子进程撤回熔断（retriever.py + mcp_server.py）

```python
# retriever.py：_call_llm_with_cb 退化成 _call_llm（保留统一超时 + token 埋点，去熔断）
def _call_llm(messages, temperature, max_tokens, call_site, timeout=30.0):
    """统一 DeepSeek 调用入口（子进程）：统一超时 + token 埋点。

    不做熔断——子进程是 per-request 的，熔断状态无法跨请求累积，形同虚设。
    单次请求内的失败由 answer_with_fallback 的 fallback 兜底。
    熔断器放在主进程的决策引擎（decision_engine）。
    """
    client = OpenAI(api_key=GROQ_API_KEY, base_url=GROQ_BASE_URL, timeout=timeout)
    resp = client.chat.completions.create(model=LLM_MODEL, messages=messages,
                                          temperature=temperature, max_tokens=max_tokens)
    get_tracker().record(LLM_MODEL, resp.usage, call_site=call_site)
    return resp

# mcp_server.py：撤掉 CircuitBreakerError 分支，仅保留 stderr 记录
try:
    return await asyncio.to_thread(answer_with_fallback, query, TOP_K, None, kb_groups)
except Exception as e:
    print(f"[MCP] 问答异常: {type(e).__name__}: {e}", file=sys.stderr, flush=True)
    return f"问答处理出错: {type(e).__name__}: {e}"
```

## 五、方案对比与推荐

### 5.1 熔断器位置：3 个方案（两轮审查后重选）

| 维度 | 方案 A：主进程常驻 + 关键路径熔断（**最终推荐**） | 方案 B：下沉到子进程 | 方案 C：子进程常驻复用后下沉 |
|------|-----------------------------------------------|---------------------|---------------------------|
| 状态能否跨请求累积 | ✅ 主进程常驻，天然累积 | ❌ 子进程 per-request，每次归零 | ⚠️ 需重构生命周期 |
| 保护对象 | ✅ 主进程决策（真正高频、致命） | ⚠️ 子进程 RAG（低频、有 fallback） | ⚠️ 子进程 RAG |
| 改动量 | 小（封装 + 6 处调用点） | 中 | 大（重构 stdio 生命周期） |
| Windows 风险 | ✅ 无 | ✅ 无 | ❌ 跨 asyncio.run 事件循环是坑 |
| 目标漂移 | ✅ 无 | ❌ 保护错重心 | ❌ 为救熔断器改连接生命周期 |

**推荐：方案 A（主进程常驻 + 关键路径熔断）**

**理由**：
1. **「状态能跨请求累积」是熔断器的地基**。主进程 `_llm_client` 常驻，`failure_count` 天然累积；子进程 per-request，状态每次归零，熔断器永远到不了阈值（单次请求内最多 2 次调用 < 阈值 5）。
2. **主进程决策才是真正的高频 + 致命点**。`decide_with_skills` 每轮 ReAct 都调、失败无 fallback（决策失败整个请求就失败）；子进程 RAG 失败有 fallback 兜底，不致命。
3. **方案 C 本末倒置**。子进程常驻复用是性能优化方向（避免冷启动重载 420MB 模型），不该用来「救一个放错位置的熔断器」；且 Windows 下跨 `asyncio.run` 复用连接是大坑。

### 5.2 HALF_OPEN 并发放大：2 个方案

| 维度 | 方案 A：单探测计数（**推荐**） | 方案 B：逐步放量 |
|------|------------------------|----------------|
| 语义 | HALF_OPEN 只放 1 次试探 | 按比例放行（如 10%） |
| 实现 | 计数器 + 锁，~10 行 | 需速率控制，复杂 |
| 适用 | 通用，标准做法 | 高并发防冷启动洪峰 |

**推荐：方案 A**。当前并发量不需要逐步放量，单探测是熔断器教科书标准实现。

### 5.3 容器化系统库：2 个方案

| 维度 | 方案 A：slim + apt 显式补库（**推荐**） | 方案 B：换完整 Debian 镜像 |
|------|----------------------------------|-------------------------|
| 镜像体积 | 小 | 大（多 ~200MB） |
| 依赖可追溯 | ✅ 明确列出 libgomp1/tini | ⚠️ 靠「完整镜像什么都带」 |

**推荐：方案 A**。slim + 显式补库是「小镜像 + 依赖可追溯」的平衡，符合 Docker 最小镜像最佳实践。

## 六、面试话术（浓缩版）

> **S**：P1 要给 DeepSeek 加熔断。第一版接在 MCP 的 `call_tool` 层，审查发现它保护的是「MCP 通道」而不是 DeepSeek——真正的 LLM 调用在子进程，异常被吞成字符串，熔断器感知不到。
> **T**：让熔断器真正保护到 DeepSeek，同时补齐容器化。
> **A**：第一次整改我把熔断器下沉到子进程的 DeepSeek 调用处——结果又踩了更深的坑：MCP 子进程是每次请求新建的，熔断器的 `failure_count` 每次归零，而单次请求内最多 2 次 LLM 调用，永远到不了阈值 5，熔断器形同虚设。这让我明白一个原则：**熔断器「状态能跨请求累积」是比「离故障源近」更前置的前提**。最终我把熔断器撤回主进程——主进程 `_llm_client` 常驻，状态天然累积，而且主进程的 ReAct 决策（每轮都调、失败无 fallback）才是真正的高频致命点。用统一封装 `call_llm_with_cb` 接入 decision_engine 的 4 处 + skill_executor 的 2 处，熔断 OPEN 时 `CircuitBreakerError` 冒泡到 `chat()` 快速失败、返回可读提示。子进程撤掉熔断，靠 fallback 兜底——fallback 管「单次请求内降级」，熔断管「跨请求快速失败」，职责边界划清。
> **R**：DeepSeek 持续故障时，连续 5 次失败打开熔断、快速失败，不再让每个请求都跑满 ReAct 循环反复超时；恢复后冷却 30s 放 1 次试探自动关闭。核心收获：熔断器的宿主必须是常驻进程，性能优化（子进程常驻）和容错（熔断）要解耦，别为了救一个放错位置的熔断器去改连接生命周期。

**边界说明（熔断范围 = 关键路径）**：

- **熔断范围**：仅主进程 decision_engine（4 处）+ skill_executor（2 处）——这些是「失败无 fallback」的关键路径。
