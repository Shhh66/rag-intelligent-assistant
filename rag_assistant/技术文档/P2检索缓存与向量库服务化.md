# P2 检索缓存与向量库服务化（STAR 法则）

> 部署运维改造的第三阶段。用 STAR 法则讲清楚来龙去脉，附技术栈、架构、核心代码，以及 2-3 个方案的优缺点对比与推荐。

---

## 一、STAR 法则

### S — 情境（Situation）

P0/P1 完成后，系统已经具备：模型服务化（嵌入/重排独立服务）、权限参数透传、熔断器、容器化。但检索链路里还剩**两个「重复计算 / 单机锁死」的点**：

1. **重复计算**：用户反复问同样的问题（如"什么是 RAG"），每次都要完整走「查询改写 → 双语混合检索（向量+BM25）→ 翻译 → 合并去重 → BGE 重排 → LLM 生成」，重复消耗 Token 和延迟。
2. **单机锁死**：向量库用的是 ChromaDB 的 `PersistentClient`，数据存在本地文件夹。模型已经拆成服务了，但向量库还是「单进程独占本地文件」，多实例部署时其他实例访问不了。

### T — 任务（Task）

1. 给检索结果加缓存，让热点问题第二次问直接命中，不再重复检索。
2. 让向量库从「单机本地」升级到「可被多实例共享」。

### A — 行动（Action）

针对两块分别设计 2-3 个方案，权衡「复杂度 vs 收益」，最终各选一个渐进式方案（详见第五节）。

### R — 结果（Result）

1. **检索缓存**：相同权限下第二次查询跳过检索（延迟降 70%+、嵌入/翻译 Token 消耗为 0），不同权限严格隔离。
2. **向量库**：通过 `CHROMA_SERVER_URL` 一键切换 Client/Server 模式，多实例共享同一向量库，数据无需迁移。

## 二、技术栈

| 模块 | 技术 | 说明 |
|------|------|------|
| 检索缓存 | Redis + `redis-py`（分布式缓存） | 多实例共享，TTL 自动过期，岗位主流技术 |
| 向量库客户端 | `chromadb.HttpClient` | Client/Server 模式客户端 |
| 向量库服务端 | `chroma run` 内置 server | ChromaDB 自带，无需额外安装 |
| 现有框架 | LangChain `Chroma` 包装 | 嵌入计算仍在客户端 |

**核心原则**：缓存选 Redis（分布式、岗位主流、多实例天然共享），向量库选 Chroma 自带的 client-server（不换库、渐进升级）。

## 三、架构设计

### 3.1 检索缓存架构（Redis 分布式）

```
多实例（Redis 共享缓存）：
┌──────────┐  ┌──────────┐
│ 实例 1    │  │ 实例 2    │
│ (app.py) │  │ (app.py) │
└────┬─────┘  └────┬─────┘
     │  redis-py   │
     └──────┬──────┘
            ▼
     ┌─────────────┐
     │  Redis      │  ← 共享缓存，TTL 自动过期
     └─────────────┘

answer_with_fallback(query, kb_groups)
  │
  ├─ 查缓存：key = md5(query + 排序后 kb_groups)
  │    ├─ 命中 → 反序列化 merged docs，跳过检索
  │    └─ 未命中 → 走完整检索链路
  │
  ├─ 检索：改写 → 双语混合检索 → 翻译 → 合并去重
  │    └─ 写缓存（setex 设 TTL，存序列化 docs）
  │
  └─ 重排 + LLM 生成（命中缓存后仍执行，保证质量）
```

**关键设计**：
1. 缓存的是「检索结果（合并去重后的 docs）」，**不是**「最终答案」——最终答案依赖 LLM 语义、命中率低；检索结果是重计算，缓存收益最大。
2. key 用 `md5(query + 排序后 kb_groups)` 缩短，避免超长 query 撑爆 Redis key，同时权限维度进 key 防串台。
3. Document 对象需序列化（JSON 存 page_content + metadata），命中后反序列化回 Document。

### 3.2 向量库 Client/Server 架构

```
单机（当前）：                    多实例（升级后）：
┌─────────────┐                  ┌──────────┐  ┌──────────┐
│  app.py     │                  │ 实例 1    │  │ 实例 2    │
│  (主进程)    │                  │ (app.py) │  │ (app.py) │
└──────┬──────┘                  └────┬─────┘  └────┬─────┘
       │ PersistentClient             │ HttpClient  │ HttpClient
       ▼                              └──────┬─────┘
┌─────────────┐                              ▼
│ 本地目录     │                     ┌──────────────────┐
│ chroma_db/  │                     │ chroma server     │
└─────────────┘                     │ (chroma run :8100)│
                                    └────────┬─────────┘
                                             ▼
                                    共享向量数据 chroma_db/
```

**关键点**：Chroma Client/Server 模式下，**嵌入计算仍在客户端**（LangChain Chroma 的 `embedding_function` 在客户端执行），server 只负责存储和检索向量。

## 四、核心代码

### 4.1 检索缓存（search_cache.py，Redis 实现）

```python
import json
import hashlib
from langchain_core.documents import Document


def _serialize_docs(docs) -> str:
    """Document 列表序列化为 JSON（重排会污染 metadata，落缓存前序列化隔离）。"""
    return json.dumps([
        {"page_content": d.page_content, "metadata": d.metadata}
        for d in docs
    ], ensure_ascii=False)


def _deserialize_docs(data: str) -> list:
    """JSON 反序列化回 Document 列表。"""
    return [Document(page_content=item["page_content"], metadata=item["metadata"])
            for item in json.loads(data)]


class SearchCache:
    """检索结果缓存：Redis 分布式缓存，key 含权限维度，TTL 自动过期。

    选 Redis 而非进程内 LRU 的理由：
    1. 多实例天然共享（P0/P1 已服务化，缓存不该退回单机）
    2. TTL 由 Redis setex 自动管理，无需自己管过期时间
    3. 岗位主流技术栈，面试加分
    """

    def __init__(self, ttl: int = 600, host: str = "localhost", port: int = 6379):
        import redis
        self._ttl = ttl
        self._client = redis.Redis(host=host, port=port, decode_responses=True)

    def _key(self, query: str, kb_groups: list) -> str:
        # 权限维度进 key：不同权限用户缓存隔离，防串台
        # 用 md5 缩短 key，避免超长 query 撑爆 Redis key
        g = ",".join(sorted(kb_groups or []))
        return "search:" + hashlib.md5(f"{query}|{g}".encode()).hexdigest()

    def get(self, query: str, kb_groups: list):
        data = self._client.get(self._key(query, kb_groups))
        return _deserialize_docs(data) if data else None

    def set(self, query: str, kb_groups: list, docs):
        # setex = SET + EXPIRE，一条命令搞定写入 + TTL
        self._client.setex(self._key(query, kb_groups), self._ttl,
                           _serialize_docs(docs))

    def invalidate(self):
        # 知识库变更后，清空所有 search:* 前缀的 key（scan 避免阻塞）
        for key in self._client.scan_iter("search:*"):
            self._client.delete(key)
```

### 4.3 向量库服务化（vector_store.py 示意）

```python
def _get_client():
    """按配置返回 PersistentClient 或 HttpClient（单机 vs 多实例共享）。"""
    if CHROMA_SERVER_URL:
        host, port = _parse_url(CHROMA_SERVER_URL)
        return chromadb.HttpClient(host=host, port=port)
    return chromadb.PersistentClient(path=VECTOR_DB_PATH)

def load_vector_store() -> Chroma:
    embeddings = get_embeddings()
    if CHROMA_SERVER_URL:
        client = _get_client()
        return Chroma(client=client, collection_name="langchain",
                      embedding_function=embeddings)
    return Chroma(persist_directory=str(VECTOR_DB_PATH),
                  embedding_function=embeddings,
                  collection_name="langchain")
```

## 五、方案对比与推荐

### 5.1 检索缓存：3 个方案

| 维度 | 方案 A：Redis 分布式缓存 | 方案 B：进程内 LRU | 方案 C：文件持久化缓存 |
|------|------------------------|-------------------|----------------------|
| 依赖 | 引入 redis-py + Redis 服务 | 零（dict + TTL） | 零（pickle/JSON 落盘） |
| 延迟 | 网络往返 ~1ms | 最低（内存访问） | 磁盘 IO 较慢 |
| 多实例共享 | ✅ 天然共享 | ❌ 各缓存各的 | ⚠️ 需共享文件系统 |
| 重启持久化 | ✅ | ❌ 丢失 | ✅ |
| TTL 过期 | ✅ 自动（setex） | 手动管理 | 手动 |
| 岗位匹配 | ✅ 面试加分 | ❌ | ❌ |
| 实现复杂度 | 中（部署 Redis） | 低（半天） | 中（并发锁） |
| 架构一致性 | ✅ 与 P0/P1 服务化一致 | ❌ 退回单机 | ⚠️ 半吊子 |

**推荐：方案 A（Redis 分布式缓存）**

**理由**：
1. **岗位匹配**：市面 AI 应用开发岗位普遍要求 Redis，用 Redis 是简历/面试的硬通货。
2. **架构一致性**：P0/P1 已经把模型拆成服务、权限改成无状态参数透传，多实例架构已经成型——缓存如果退回进程内 LRU，等于「多实例的检索缓存各存各的」，与整体服务化方向矛盾。
3. **生产级特性**：TTL 由 Redis `setex` 自动管理，天然支持过期、持久化、多实例共享，不用自己造轮子管 LRU 淘汰。

**代价**：多一个 Redis 服务要部署（`docker run redis` 一条命令），多一次网络往返（~1ms，相对检索几百 ms 可忽略）。这是「岗位要求 + 架构一致性」换来的合理成本。

### 5.2 向量库服务化：3 个方案

| 维度 | 方案 A：Chroma Client/Server | 方案 B：换 Milvus/Qdrant | 方案 C：保持 PersistentClient |
|------|---------------------------|------------------------|----------------------------|
| 数据迁移 | ✅ 无需迁移 | ❌ 全量迁移 | ✅ 无需迁移 |
| API 改动 | ✅ 基本兼容 | ❌ 全改 | ✅ 零改动 |
| 多实例共享 | ✅ | ✅ | ❌ |
| 规模上限 | 百万级够用 | 亿级分布式 | 单机 |
| 部署复杂度 | 低（chroma run） | 高（集群部署） | 最低 |
| 当前适配度 | ✅ 合适 | ❌ 过度设计 | ⚠️ 架构锁死 |

**推荐：方案 A（Chroma Client/Server）**

**理由**：这是「渐进式升级」的典型——数据不迁移、API 基本兼容、一条 `chroma run` 就能起 server。换 Milvus/Qdrant 是「数据到百万级、需要分布式检索」才考虑的事，现在换是典型的「过度设计」。而方案 C 不升级，等于把向量库锁死在单机，P0/P1 辛辛苦苦拆出来的多实例能力就白费了。

**核心原则**：选型要匹配规模——单机用 PersistentClient，多实例共享升级 Client/Server，百万级再换库。每一步都是「到了那个规模才做那个事」。

## 六、面试话术（浓缩版）

> **S**：P0/P1 把模型拆成了服务、加了熔断和容器化，但检索链路还剩两个点——热点问题每次重复计算浪费 Token，向量库还是单机本地文件多实例共享不了。
> **T**：给检索加缓存、让向量库支持多实例共享。
> **A**：缓存我设计了三个方案（Redis / 进程内 LRU / 文件持久化），权衡后选了 Redis——因为 P0/P1 已经把架构做成多实例服务化，缓存如果退回进程内 LRU，多实例就各存各的、与整体方向矛盾；而且市面 AI 岗位都要求 Redis，是技能硬通货。核心设计是 key 用 `md5(query + 排序后 kb_groups)`，既缩短 key 又保证多租户隔离，TTL 用 Redis `setex` 自动过期。向量库也对比了三个，选了 Chroma Client/Server——数据不迁移、API 兼容、渐进升级。
> **R**：缓存让热点问题第二次秒回、Token 消耗归零，且 Redis 多实例天然共享、key 含权限维度保证多租户隔离；向量库一条配置切换 Client/Server，多实例共享同一库。核心收获是「架构一致性」——缓存、模型、权限、向量库四个维度都朝服务化/无状态收敛，不出现「拆了模型却退回单机缓存」的割裂。
