# P3 限流（STAR 法则）

> 部署运维改造的第四阶段。用 STAR 法则讲清楚来龙去脉，附技术栈、架构、核心代码，以及 2-3 个方案的优缺点对比与推荐。
>
> 两层限流：**用户请求级**（防滥用/控成本）+ **LLM 调用级**（配合供应商 RPM），复用同一个 Redis 令牌桶组件。

---

## 一、STAR 法则

### S — 情境（Situation）

P1 做完熔断后，系统的容错还缺一块：熔断管的是「下游 DeepSeek **挂了**」快速失败，但没管「DeepSeek **好好的、请求却太多**」的频率问题。企业级 RAG 有两个现实约束：

1. **供应商限流**：DeepSeek 有 RPM（每分钟请求数）限制，超了返回 429，客户端无节制调用会撞上限。
2. **成本控制**：DeepSeek 按 token 计费，单用户高频刷（或恶意脚本）就是实打实的钱。

验收审查的 6 项差距里，「限流」是唯一**完全缺失**的一项——熔断器有了、缓存有了、模型服务化有了，但限流一个都没有。

### T — 任务（Task）

加两层限流：
1. **用户请求级**：每个登录用户有请求频率配额，防滥用 + 控成本。
2. **LLM 调用级**：对 DeepSeek 的调用频率限流，配合供应商 RPM 限制。

### A — 行动（Action）

用一个 Redis 令牌桶组件（Lua 原子操作）复用两层。分别设计算法方案和存储方案并权衡（详见第五节）。

### R — 结果（Result）

1. **用户级**：同一用户 1 分钟内超限 → 429，不同用户互不影响。
2. **LLM 级**：DeepSeek 调用超限 → 快速失败（不调下游），返回可读提示，不进入 ReAct 循环反复重试。
3. **fail-open**：Redis 挂了限流降级放行，主链路不断。
4. **容错三件套**：重试（瞬时抖动）+ 熔断（下游故障）+ 限流（上游频率），维度完整。

## 二、技术栈

| 模块 | 技术 | 说明 |
|------|------|------|
| 限流算法 | 令牌桶（Token Bucket） | 容量允许突发 + 速率平滑补充 |
| 原子操作 | Redis Lua 脚本 | 令牌补充 + 扣减 + 时间戳更新，一条命令防竞态 |
| 存储 | Redis + `redis-py` | 多实例共享，与 P2 检索缓存同一 Redis |
| 用户级接入 | FastAPI 依赖注入（`Depends`） | JWT 鉴权后按 username 限流，超限 429 |
| LLM 级接入 | `call_llm_with_cb` 内嵌 | 熔断检查之后、实际调用之前 |
| 降级 | fail-open | Redis 不可用放行（限流是软保护） |

**核心原则**：限流是「软保护」，降级策略是 fail-open（Redis 挂了放行）；熔断是「硬保护」，降级策略是 fail-closed（下游挂了快速失败）——两者降级方向相反。

## 三、架构设计

```
┌─ 第一层：用户请求级（api_server FastAPI 依赖）─────────────────┐
│  登录用户 → JWT 鉴权 → 令牌桶(rate:user:{username}) → 超限 429  │
│  目的：防滥用 + 控成本（每个用户有请求频率配额）                  │
└───────────────────────────────────────────────────────────────┘
                          │ 通过
                          ▼
┌─ 第二层：LLM 调用级（call_llm_with_cb 内部）──────────────────┐
│  call_llm_with_cb → 限流(rate:llm:deepseek) → 熔断 → DeepSeek  │
│  超限 → RateLimitError → unified_agent.chat() 捕获 → 可读提示   │
│  目的：配合 DeepSeek 的 RPM 限制                                │
└───────────────────────────────────────────────────────────────┘
```

**关键设计**：
1. **两层复用同一组件**：`RedisTokenBucket` 只做令牌桶，两层通过不同 `key_prefix`（`rate:user` vs `rate:llm`）+ 不同标识（username vs deepseek）区分。
2. **调用顺序**：LLM 级限流在**熔断检查之后、实际调用之前**——先判断「下游是否故障」（熔断），再判断「频率是否超限」（限流），两个维度各管各的。
3. **key 维度隔离**：用户级 key 含 username，LLM 级 key 含下游名，天然互不干扰。
4. **fail-open 语义**：Redis 不可用时 `allow()` 恒返回 True（放行）——限流是软保护，Redis 挂了不应阻断正常用户和主链路。

## 四、核心代码

### 4.1 Redis 令牌桶组件（rate_limiter.py，两层共用）

```python
"""Redis 令牌桶限流器 —— 两层限流共用（用户请求级 + LLM 调用级）。"""
import sys
import time

_RATE_LIMIT_LUA = """
local key = KEYS[1]
local ts_key = KEYS[2]
local capacity = tonumber(ARGV[1])
local refill = tonumber(ARGV[2])      -- 每秒补充令牌数
local now = tonumber(ARGV[3])
local tokens = tonumber(redis.call('get', key))
if tokens == nil then tokens = capacity end
local last = tonumber(redis.call('get', ts_key))
if last == nil then last = now end
tokens = math.min(capacity, tokens + (now - last) * refill)  -- 按经过时间补令牌，封顶
redis.call('set', ts_key, now)
if tokens >= 1 then
    redis.call('set', key, tokens - 1)
    return 1
end
redis.call('set', key, tokens)
return 0
"""


class RedisTokenBucket:
    """令牌桶：容量允许突发、速率平滑补充；Lua 原子操作防竞态。

    fail-open：Redis 不可用时 allow() 恒返回 True（放行），
    因为限流是软保护（防滥用/控成本），Redis 挂了不应阻断主链路。
    """

    def __init__(self, key_prefix, capacity, refill_per_sec, host="localhost", port=6379):
        self._key_prefix = key_prefix
        self._capacity = capacity
        self._refill = refill_per_sec
        self._client = None
        self._available = False
        try:
            import redis
            self._client = redis.Redis(host=host, port=port, decode_responses=True)
            self._client.ping()
            self._available = True
            print(f"   🚦 限流器就绪: Redis {host}:{port}", file=sys.stderr, flush=True)
        except Exception as e:
            print(f"   ⚠️ Redis 不可用，限流降级关闭（fail-open 放行）: {e}",
                  file=sys.stderr, flush=True)

    def allow(self, identifier: str) -> bool:
        """取 1 个令牌，返回是否放行。Redis 不可用 → True（fail-open）。"""
        if not self._available:
            return True
        key = f"{self._key_prefix}:{identifier}"
        ts_key = key + ":ts"
        try:
            result = self._client.eval(
                _RATE_LIMIT_LUA, 2, key, ts_key,
                self._capacity, self._refill, time.time(),
            )
            return result == 1
        except Exception as e:
            print(f"   ⚠️ 限流检查失败(fail-open 放行): {e}", file=sys.stderr, flush=True)
            return True


class RateLimitError(Exception):
    """限流超限时抛出（LLM 级由上层捕获快速失败）。"""
    pass


# 全局单例（懒加载，读取 config）
_user_limiter = None
_llm_limiter = None


def get_user_limiter() -> RedisTokenBucket:
    global _user_limiter
    if _user_limiter is None:
        from config import (USER_RATE_LIMIT_CAPACITY, USER_RATE_LIMIT_REFILL,
                            REDIS_HOST, REDIS_PORT)
        _user_limiter = RedisTokenBucket(
            "rate:user", USER_RATE_LIMIT_CAPACITY, USER_RATE_LIMIT_REFILL,
            host=REDIS_HOST, port=REDIS_PORT)
    return _user_limiter


def get_llm_limiter() -> RedisTokenBucket:
    global _llm_limiter
    if _llm_limiter is None:
        from config import (LLM_RATE_LIMIT_CAPACITY, LLM_RATE_LIMIT_REFILL,
                            REDIS_HOST, REDIS_PORT)
        _llm_limiter = RedisTokenBucket(
            "rate:llm", LLM_RATE_LIMIT_CAPACITY, LLM_RATE_LIMIT_REFILL,
            host=REDIS_HOST, port=REDIS_PORT)
    return _llm_limiter
```

### 4.2 第一层：用户请求级限流（api_server.py）

```python
from fastapi import Depends, HTTPException
from rate_limiter import get_user_limiter

async def rate_limit_user(user=Depends(get_current_user)):
    """用户级限流：每个登录用户有请求频率配额，超限 429。"""
```

### 4.3 第二层：LLM 调用级限流（circuit_breaker.py 的 call_llm_with_cb）

```python
def call_llm_with_cb(client, model, messages, temperature, max_tokens, call_site):
    """统一 LLM 调用入口：限流 + 熔断 + 成功/失败记录。"""
    breaker = get_breaker(DESTINATION_LLM)
    if not breaker.allow_request():
        raise CircuitBreakerError("DeepSeek 熔断打开，请求快速失败")
    # LLM 级限流：熔断检查之后、实际调用之前（管「频率」，不管「故障」）
    from rate_limiter import get_llm_limiter, RateLimitError
    if not get_llm_limiter().allow("deepseek"):
        raise RateLimitError("LLM 调用频率超限，请稍后重试")
    try:
        resp = client.chat.completions.create(model=model, messages=messages,
                                              temperature=temperature, max_tokens=max_tokens)
    except Exception:
        breaker.record_failure()
        raise
    breaker.record_success()
    from token_tracker import get_tracker
    get_tracker().record(model, resp.usage, call_site=call_site)
    return resp
```

### 4.4 限流超限快速失败入口（unified_agent.py chat 捕获）

```python
def chat(self, user_input, kb_groups=None, user_id=None) -> str:
    try:
        return asyncio.run(self._run(user_input, kb_groups))
    except CircuitBreakerError as e:
```

## 五、方案对比与推荐

### 5.1 限流算法：3 个方案

| 维度 | 方案 A：令牌桶（**推荐**） | 方案 B：固定窗口 | 方案 C：滑动窗口 |
|------|------------------------|----------------|----------------|
| 突发处理 | ✅ 允许（桶内积攒的令牌） | ❌ 无 | ⚠️ 有限 |
| 边界毛刺 | ✅ 无 | ❌ 窗口切换瞬间可双倍放行 | ✅ 无 |
| 实现复杂度 | 中（Lua ~10 行） | 低（INCR+EXPIRE 2 行） | 高（需记录每次时间戳） |
| 内存占用 | 低（2 个 key） | 低（1 个 key） | 高（每请求一个时间戳） |
| 生产主流度 | ✅ 高 | ⚠️ 入门级 | ⚠️ 精确但重 |

**推荐：方案 A（令牌桶）**

**理由**：
1. **固定窗口有真实缺陷**：计数器在窗口边界重置，如果限制是「每分钟 60 次」，用户在 59.99s 和 60.01s 各发 60 次，1 秒内就发了 120 次——面试被追问「窗口边界怎么办」就露馅。
2. **滑动窗口过度设计**：要记录每次请求的时间戳（或用 Redis ZSET），内存和复杂度都高。当前项目并发量用不上。
3. **令牌桶是平衡点**：允许突发（用户瞬间连点不会误伤）+ 平滑（长期速率受控）+ 实现可控（一条 Lua 原子操作），是生产限流的主流选择。

### 5.2 限流存储：2 个方案

| 维度 | 方案 A：Redis（**推荐**） | 方案 B：进程内 |
|------|------------------------|--------------|
| 多实例共享 | ✅ 天然共享 | ❌ 各限各的 |
| 一致性 | ✅ 全局统一 | ❌ N 个实例 = N 份配额 |
| 重启持久化 | ✅ | ❌ 丢失 |
| 依赖 | 引入 Redis（已有） | 零 |
| 与架构一致 | ✅ 与 P2 缓存同一 Redis | ❌ 退回单机 |

**推荐：方案 A（Redis）**

**理由**：P0/P1/P2 已经把模型、缓存、向量库都服务化了，多实例架构已成型。进程内限流在多实例下「各限各的」——N 个实例就是 N 倍配额，等于没限。而且 P2 已经引入 Redis（检索缓存），限流复用同一 Redis，零新增基础设施。Redis 的 Lua 脚本保证令牌操作原子性，天然支持分布式限流。

## 六、面试话术（浓缩版）

> **S**：做完熔断后我发现还差一块——熔断管的是「DeepSeek 挂了」快速失败，但没管「DeepSeek 好好的、请求却太多」的频率问题。企业 RAG 有两个现实约束：DeepSeek 有 RPM 限制（超了 429），成本按 token 计费、单用户刷爆就是钱。验收审查里「限流」也是唯一完全缺失的项。
> **T**：加两层限流——用户请求级（防滥用/控成本）+ LLM 调用级（配合供应商 RPM）。
> **A**：用一个 Redis 令牌桶组件（Lua 原子操作）复用两层：① 用户级在 api_server 的 JWT 鉴权后做依赖注入，key 按用户名，超限 429；② LLM 级在 `call_llm_with_cb` 里、熔断检查之后，key 按 deepseek，超限抛 `RateLimitError` 冒泡到 `chat()` 快速失败。两个关键决策：算法选令牌桶（固定窗口切换瞬间会双倍放行，滑动窗口过度设计）；降级选 fail-open（Redis 挂了限流放行，因为限流是软保护，不该像熔断那样 fail-closed 阻断主链路）。
> **R**：两层限流 + 已有的熔断器，形成容错三件套——**重试**（瞬时抖动）、**熔断**（下游故障）、**限流**（上游频率）。核心收获是讲清三者维度边界：重试管单次、熔断管下游、限流管上游，互不替代；以及限流和熔断的降级方向相反（软保护 fail-open vs 硬保护 fail-closed）。

## 七、风险备注与 P4 迭代（工程真实漏洞，面试主动讲）

> P3 方案是「快速落地」版本，有 6 个**已知取舍**。把「用户隔离 / Token 管控 / 可观测性」留给 P4。面试里**主动讲出这些取舍**，比声称方案完美更显成熟——面试官最怕的不是有缺点，而是看不出自己的缺点。

### 7.1 现存风险（6 项，按严重度）

| # | 风险 | 现状 | 后果 | 归属 |
|---|------|------|------|------|
| 1 | LLM 级全局桶，缺用户维度隔离 | `allow("deepseek")` 全系统共用 | A 用户刷爆 LLM 桶，卡住正常用户（Agent 循环放大多次调用） | P4 |
| 2 | 只做 RPM，无 TPM（token 维度） | 全按请求次数限流 | 长文档 1 次请求上万 token，RPM 没超但成本爆炸 | P4 |
| 3 | 缺监控/埋点/告警 | 限流无 metrics/日志字段/告警 | 无法区分恶意攻击 vs 业务上涨 | P4 |
| 4 | Lua 两个 key 分存 | `key` + `ts_key` 两次 set | 多一次 Redis 写（不影响正确性） | P4 优化 |
| 5 | 限流无退避重试 | `RateLimitError` 直接失败 | 瞬时限流也硬拒绝 | P4 可选 |
| 6 | 未区分前端用户 vs 内部 API | 依赖绑定 `get_current_user` | 内部无 JWT 调用时用户限流失效 | P4 预留 |

### 7.2 两个核心缺口的本质

**① 资源隔离缺口（风险 1）**：用户级限流按 username 隔离了「请求频率」，但 LLM 级是**全局单桶**。Agent 系统里一次用户请求会触发多轮 ReAct = 多次 LLM 调用，一个用户就能占满全局 LLM 配额，把其他用户全部卡住。本质是「**请求级隔离了，资源级没隔离**」——请求级隔了（username），资源级没隔（全局桶）。正确做法是 LLM 桶也带用户维度：`allow(f"deepseek:{username}")`，或「全局桶保下游 + 用户维桶保公平」双层叠加。

**② 成本管控缺口（风险 2）**：限流按「请求次数」（RPM）计，但 LLM 成本核心是「token」。一个用户发 1 次请求传入上万 token 长文档，RPM 不超限但 token 消耗爆炸。完备方案是 RPM + TPM 双维度限流。

### 7.3 P3 落地时的 3 个小改进（不扩大工作量）

1. **文档明示**：LLM 级为全局桶，存在用户抢占风险，适合 P3 快速落地，P4 升级按用户维度。
2. **补充说明**：当前仅 RPM，未实现 TPM token 成本管控，长文本场景仍有成本风险。
3. **日志带 username**：LLM 级限流触发时打印当前用户，便于排查「是谁触发的限流」。

### 7.4 P4 迭代方向

| 迭代 | 内容 |
|------|------|
| LLM 用户维度 | `allow(f"deepseek:{username}")` 每用户独立配额，租户完全隔离（或全局桶 + 用户维桶双层叠加） |
| TPM 管控 | RPM + TPM 双维度，token 成本可控 |
| 可观测 | prometheus 埋点（`user_rate_limit_triggered` / `llm_rate_limit_triggered`）+ 告警（区分恶意攻击 vs 业务上涨） |
| 退避重试 | 限流错误可控指数退避（Agent 循环内设最大重试次数，防死循环） |

**验证覆盖**：fail-open（Redis 不可用放行，主链路不断）、`RateLimitError` 继承链、`call_llm_with_cb` 限流超限抛异常、限流放行后正常调用、两层 limiter 独立（`rate:user` vs `rate:llm`）。

**「日志带 username」实现位置**（7.3 第 3 点）：
- 用户级：[api_server.py](api_server.py) 的 `get_current_user` 限流触发时打印 `user={username}`；
- LLM 级：[unified_agent.py](mcp_unified_agent/unified_agent.py) 的 `chat()` 捕获 `RateLimitError` 时打印 `user={self._user_id}`（`call_llm_with_cb` 在深层拿不到用户，故由入口 `chat()` 打印）。

**实现取舍说明**：用户级限流挂在 `get_current_user`（而非文档 4.2 示意的「逐个端点挂依赖」）——因为 api_server 有 30+ 个鉴权端点，逐个挂不现实；`get_current_user` 是所有鉴权端点的公共入口（login 除外），一次覆盖全部。
