## 一、STAR 法则

### S — 情境（Situation）

P0–P3 完成了部署运维改造（模型服务化、权限参数透传、熔断、限流、缓存、容器化）。但对照「企业 Agent 智能体」清单审查时，发现两个 Agent 核心能力有缺口：

1. **工具调用鉴权（🔴 最明显缺口）**：JWT 里已经签发了 `permissions`（如 `search_all/upload/manage_users`），但这套身份**从未传导到工具层**——[scheduler.py](mcp_unified_agent/scheduler.py) 的 `_execute_one` 只有 `kb_groups` 数据权限注入（「能看哪些文档」），没有工具级鉴权（「能调哪些工具」）。Agent 理论上可以调用任何工具，包括 `clear_memory` 这类本应受控的操作。这正是企业级清单里「Agent 不能随便删数据」的硬要求。

2. **思考过程留痕（🟠 合规缺口）**：工具调用有审计（`tool_audit.jsonl`），但 ReAct 的「思考（Thought）→ 行动（Action）」过程没有结构化留痕，只有 `logger.debug`。达不到企业合规「每一步思考可回溯」的要求——出问题时无法还原「Agent 当时为什么这么决策」。

### T — 任务（Task）

1. **工具调用鉴权**：让 `permissions` 从登录态传导到工具调度层，在工具调用唯一收口处做权限校验，未授权工具被拒绝。
2. **思考留痕**：把 ReAct 每一步决策（轮次、行动类型、思考、拟调工具）结构化落盘，与工具调用审计归并同一 trace。

### A — 行动（Action）

分别设计 2-3 个方案并权衡（详见第五节），核心是两件事：
1. 工具鉴权选「统一元数据体系」（`required_perms` 收敛到 `ToolMeta`）+ **参数透传**（继承 P0 的无状态原则，而非 MCP工程化.md 里旧规划的「写文件」）。
2. 思考留痕选「扩展 `tool_audit`」（加 `decision` 类型），复用现有审计基础设施。

### R — 结果（Result，目标态）

1. **工具鉴权**：访客/普通用户调 `clear_memory` 这类受控工具被结构化拒绝（走 `is_error` 通道，不抛异常）；未配置权限的「写/敏感工具」默认拒绝（fail-closed），查询工具默认公开。新增工具忘配权限不会变成安全漏洞。
2. **思考留痕**：一次 chat 的每一步 ReAct 决策 + 每一次工具调用，都在同一 `trace_id` 下结构化落盘，可还原完整决策链。
3. **零破坏**：`TOOL_PERMISSION_ENABLED=False`（默认）时行为与改造前一致。

## 三、架构设计

### 3.1 工具鉴权（权限传导 + 收口校验）

```
登录态 permissions（JWT 已签发）
  → app.py session_state 存 permissions
  → chat(user_input, ..., permissions=...)          # 参数透传（非文件）
  → UnifiedAgent._run → Scheduler(permissions=...)   # 请求级注入
  → _execute_one 收口：
       _check_tool_permission(tool_name, permissions)
         ├─ ToolMeta.required_perms 查该工具所需权限
         ├─ 有权限 → 继续调用
         └─ 无权限 → 结构化拒绝（is_error=True，不抛异常）
```

**关键设计**：
1. **权限来源复用**：JWT 里 `permissions` 已经在，不用新鉴权体系，只需传导。
2. **参数透传而非文件**：MCP工程化.md 旧规划是「写跨进程文件」，已被 P0 否定（文件共享有串台风险）；P4 走 `chat(permissions=...)` 参数透传，和 `kb_groups` 完全一致。
3. **收口校验**：`_execute_one` 是工具调用唯一入口（串行/并行都走它），一处插钩子全覆盖。

### 3.2 思考留痕（决策审计）

```
ReAct 循环（unified_agent._pipeline）
  → decision_engine.decide_with_skills → 解析出 AgentDecision(action, thought, tools)
  → 记录一条 decision 审计（trace_id + turn + action + thought + tool_names）
  → scheduler.execute → 工具调用审计（现有 tool_audit）

同一 trace_id 下：
  [decision] turn=1 action=call_tools thought="..." tools=[query_weather]
  [tool]     query_weather 成功
  [decision] turn=2 action=call_tools thought="..." tools=[ask_knowledge_base]
  [tool]     ask_knowledge_base 成功
  → 完整还原「Agent 为什么这么决策、调了什么工具」
```

### 4.2 权限校验（scheduler.py 收口）

```python
class Scheduler:
    def __init__(self, ..., permissions: list = None):
        self.permissions = permissions  # 请求级权限（None=不限，向后兼容）

    async def _execute_one(self, decision: ToolDecision) -> dict:
        # 0. 工具级权限校验（收口，fail-closed 防漏配）
        if self.permissions is not None:
            denied = self._check_tool_permission(decision.tool_name)
            if denied:
                return {  # 结构化拒绝，走 is_error 通道，不抛异常
                    "tool_name": decision.tool_name,
                    "arguments": decision.arguments,
                    "result": f"权限拒绝: 缺少 {denied} 权限",
                    "is_error": True,
                    "latency_ms": 0,
                }
        # ... 原有 kb_groups 注入 + validate + call_tool ...

    def _check_tool_permission(self, tool_name: str):
        """查 ToolMeta.required_perms，返回缺失的权限名（None=有权限）。"""
        meta = self.registry.get_meta(tool_name)
        required = meta.required_perms if meta else ["*"]
        if required == ["*"]:
            return None  # 公开工具
        missing = [p for p in required if p not in (self.permissions or [])]
        return missing[0] if missing else None
```

### 4.6 工具注册 + 启动期校验（mcp_server.py，风险补救核心）

```python
# 工具注册：required_perms 必填（开发时忘配 → TypeError）
_TOOL_PERMISSIONS = {}  # 工具名 → required_perms

def register_tool(required_perms, name=None):
    """注册工具并声明权限。required_perms 必填，开发时忘配直接报错。"""
    def decorator(func):
        tool_name = name or func.__name__
        _TOOL_PERMISSIONS[tool_name] = required_perms
        return mcp.tool(name=tool_name)(func)
    return decorator

@register_tool(required_perms=["*"])            # 公开工具
async def query_weather(city: str) -> str: ...

@register_tool(required_perms=["manage_users"]) # 受控工具
async def clear_memory() -> str: ...

# 启动期校验：扫描所有注册工具，未声明 required_perms 直接启动报错
def _validate_tool_permissions():
    """把「运行时故障」提前到「启动阶段」：新增工具忘配权限，程序直接跑不起来。"""
    registered = [info.name for info in mcp._tool_manager.list_tools()]
    missing = [name for name in registered if name not in _TOOL_PERMISSIONS]
    if missing:
        raise RuntimeError(
            f"[启动检查] 以下工具缺少权限配置，请补充 required_perms: {missing}"
        )
    # 风险② 轻量提示：公开工具打 warning，提醒确认是否需精细化
    for name, perms in _TOOL_PERMISSIONS.items():
        if perms == ["*"]:
            print(f"   ⚠️ 工具 {name} 声明为公开(['*'])，确认是否需要精细化权限",
                  file=sys.stderr, flush=True)

# mcp_server.py 启动时（__main__ 前）调用
_validate_tool_permissions()
```

## 五、方案对比与推荐

### 5.1 工具鉴权：3 个方案

| 维度 | 方案 A：统一元数据 + 参数透传（**推荐**） | 方案 B：独立配置表 | 方案 C：MCP 层校验 |
|------|----------------------------------------|-------------------|-------------------|
| 权限映射位置 | `ToolMeta.required_perms`（工具属性） | `config.TOOL_PERMISSION_MAP` 字典 | 每个 `@mcp.tool()` 内部 |
| 新增工具漏配 | ✅ 默认拒绝（fail-closed） | ❌ 忘配 = 安全漏洞 | ❌ 忘写 = 无鉴权 |
| 收口位置 | `_execute_one` 一处 | `_execute_one` 一处 | 散落各工具 |
| 与现有体系 | ✅ 与 skill retryable 一脉相承 | ⚠️ 散落配置各自为政 | ❌ 侵入业务逻辑 |
| 改动量 | 中（ToolMeta + scheduler） | 低（config + scheduler） | 大（每个工具都改） |

**推荐：方案 A（统一元数据 + 参数透传）**

**理由**：
1. **从「三套散落配置」收敛为「一个工具属性来源」**——`required_perms` 是工具自身的属性（和 `retryable`/`idempotent` 一样），权限跟着工具定义走，而不是散落在 config 字典里。
2. **权限最小化默认（fail-closed）**：查询类默认 `["*"]` 公开，写/敏感工具未显式配置则拒绝——新增工具忘配权限不会变成安全漏洞（方案 B 会）。
3. **参数透传而非文件**：MCP工程化.md 旧规划「写跨进程文件」已被 P0 否定（文件共享串台），P4 走 `chat(permissions=...)`，和 `kb_groups` 一致，符合项目「无状态优先」原则。

**代价**：方案 A 改动比方案 B 略大（要动 ToolMeta），但换来「漏配不危险」的安全兜底，值得。

### 5.2 思考留痕：3 个方案

| 维度 | 方案 A：扩展 tool_audit（**推荐**） | 方案 B：独立 decision_audit.jsonl | 方案 C：LangFuse span |
|------|----------------------------------|--------------------------------|---------------------|
| 复用现有基建 | ✅ 零新增文件 | ⚠️ 多一个文件 | ⚠️ 依赖 LangFuse |
| trace 归并 | ✅ 思考+工具同一 jsonl 可归并 | ⚠️ 两个文件要手动 join | ✅ 可视化 |
| 默认可用 | ✅（jsonl 落盘） | ✅ | ❌（LangFuse 默认关） |
| 改动量 | 低（加 log_decision） | 中（新建模块） | 低（obs_span） |

**推荐：方案 A（扩展 tool_audit）**

**理由**：复用现有审计基础设施（零新增文件、零新增依赖），思考留痕和工具调用审计在同一 `tool_audit.jsonl`、同一 `trace_id` 下，可直接还原「决策 → 调用」完整链路。方案 C（LangFuse）可视化好，但默认关闭，不能作为唯一留痕（合规要求「落盘」而非「可视化」）。

## 六、默认开启的风险与补救（面试要主动讲）

默认 `TOOL_PERMISSION_ENABLED=True` 有两个**原生风险**，工程上做两点补救：

| # | 风险 | 后果 |
|---|------|------|
| ① | 新增工具忘配 required_perms | fail-closed 拒绝调用，但**运行时才发现**（Agent 调用失败） |
| ② | 习惯写 `["*"]` 通配 | 弱化精细化权限 |

**补救 1（开发时辅助校验，代码层面）**：`register_tool(required_perms)` 把 required_perms 做成**必填参数**——忘配在写代码时就 `TypeError`（IDE 也提示缺参），不用等到启动/运行时。

**补救 2（启动期检查，fail-fast）**：`_validate_tool_permissions()` 在启动时扫描 `mcp._tool_manager.list_tools()`，未声明权限的工具**直接启动报错**。把「运行时 Agent 调用失败」提前到「程序跑不起来」——新增工具忘配权限，程序直接启动失败，而不是运行时才发现。

**两补救互补**：
- 补救 1 是「正常路径」：通过 API 设计强制，开发时暴露
- 补救 2 是「兜底」：防绕过 `register_tool` 直接 `@mcp.tool()`，运行时扫描拦截

**风险②轻量处理**：启动检查时对 `["*"]` 工具打 warning，提醒确认是否需精细化（不强制，避免过度设计）。

**核心叙事**：默认开启是有风险的，但我知道风险——用「启动期 fail-fast」把「忘配权限」这个隐患从「运行时 Agent 调用失败」提前到「启动阶段报错」，规避心智负担。面试里主动讲出这个风险 + 补救，比「默认关、形同虚设」或「默认开、不管风险」都更成熟。

## 七、面试话术（浓缩版）

> **S**：做完 P0–P3 的部署运维改造后，我对照「企业 Agent」清单做了次能力审查，发现两个缺口：一是 JWT 里已经签发了 `permissions`，但从来没传导到工具层——Agent 理论上可以调任何工具，包括 `clear_memory` 这种本应受控的操作；二是工具调用有审计，但 ReAct 的「思考过程」没留痕，达不到合规「每一步思考可回溯」。
> **T**：补工具调用鉴权 + 思考过程留痕。
> **A**：工具鉴权我对比了三个方案（统一元数据 / 独立配置表 / MCP 层校验），选了「统一元数据」——把 `required_perms` 收敛到 `ToolMeta`（和 `retryable`/`idempotent` 一起），在 `scheduler._execute_one` 这个工具调用唯一收口插校验钩子。两个关键设计：一是**权限参数透传**（继承 P0 的无状态原则，不用旧规划里的「写文件」）；二是**默认开启 + 启动期 fail-fast**——默认 `TOOL_PERMISSION_ENABLED=True`，但我知道默认开有风险（新增工具忘配权限会 fail-closed），所以用启动期检查兜底：扫描注册工具，忘配权限直接启动报错，把「运行时故障」提前到「启动阶段」。思考留痕扩展 `tool_audit`，加 `decision` 类型，让「思考」和「工具调用」在同一 trace 下可还原完整决策链。
> **R**：Agent 不能随便调受控工具了，每一步决策可回溯。核心收获是「身份有了、授权没做全」——JWT 的 `permissions` 一直都在，缺的是把它传导到工具层的「最后一公里」，以及「默认拒绝」的安全兜底。

1. `required_perms` 通过 FastMCP 的 `meta` 参数（`@mcp.tool(meta={"required_perms": [...]})`）传递，主进程 `ToolMeta.from_mcp_tool` 提取——比文档 4.6 里「register_tool 单独维护 _TOOL_PERMISSIONS 映射」更简洁，权限声明就跟着工具定义走。
2. `clear_memory` 声明 `["manage_users"]`（唯一受控工具），其余 6 个公开 `["*"]`。
3. 鉴权收口在**两条路径**：`scheduler._execute_one`（ReAct 路径）+ `skill_executor._execute_step`（Skill 路径），复用同一 `_check_tool_permission` 逻辑。

### 边界与解决之法（skill_executor 鉴权补齐）

**边界（首轮实施的已知缺口）**：首轮 P4 只做了 `scheduler._execute_one` 收口，`skill_executor` 的 Skill 路径工具调用未接鉴权——若用户通过内置 Skill（如「综合查询」）间接触发 `clear_memory`，会绕过鉴权。这是「鉴权收口不完整」的边界。

**解决之法**：给 `skill_executor` 加 `registry` + `permissions` 参数，在 `_execute_step` 里、`call_tool` 之前加同一套 `_check_tool_permission` 校验（未授权返回 `_error_result` 结构化拒绝）；`unified_agent` 构造 `SkillExecutor` 时传入 `tool_registry` + `scheduler.permissions`。两条路径共享同一逻辑，杜绝「换条路径就绕过鉴权」。

**核心叙事**：鉴权收口要找全所有「工具调用入口」——Agent 调工具有 ReAct 决策和 Skill 声明两条路径，只收一条就会漏。这是「对称性」问题（同 P0 的 BM25 双通道权限一致），教训一致：**凡是「多路径」的功能，权限/鉴权必须每一条都收口**。
