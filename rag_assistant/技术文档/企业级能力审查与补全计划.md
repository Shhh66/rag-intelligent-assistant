# 企业级能力审查与补全计划

> 对照「企业 RAG 知识库」和「企业 Agent 智能体」两份企业级清单，盘点当前项目已具备的能力，把 7 项差距按投入产出比拆成 P4–P7 阶段。
>
> 这是 P0–P3（部署运维改造）之后的新一轮规划：P0–P3 解决的是「怎么部署、怎么容错」，P4–P7 解决的是「怎么补齐企业级横切能力」。

---

## 一、审查结论（现状盘点）

**一句话总评**：项目在「Agent 引擎层」已接近企业级（ReAct / 记忆 / 容错三件套都做透了），短板集中在「横切关注点」——**鉴权链条不完整**（身份有了、授权没做全）和**合规审计不完整**（工具调用有审计、思考过程没留痕）。

### 1.1 企业 RAG 知识库（6 项）

| 能力 | 状态 | 现状 vs 差距 |
|------|------|------------|
| 多数据源接入 | ⚠️ 3/7 | PDF/Word/TXT ✅；数据库/飞书/网页/工单 ❌ |
| 文档处理 | ✅ 4.5/5 | 解析/分块/清洗/RRF ✅；版本管理只有快照回退 |
| 权限隔离 | ⚠️ | 组级（kb_group + visibility）✅；文档级 ACL ❌ |
| 检索增强 | ✅ 3/3 | 混合检索 + 重排 + RAGAS，全项目最强项 |
| 可观测 | ⚠️ 3.5/4 | 检索日志/溯源/用量 ✅；生产级幻觉检测 ❌ |
| 部署 | ✅ 3.5/4 | 多实例/限流/缓存 ✅；向量库 client-server 非分布式集群 |

### 1.2 企业 Agent 智能体（6 项）

| 能力 | 状态 | 现状 vs 差距 |
|------|------|------------|
| 标准化工具调用 | ⚠️ | MCP 协议 ✅；对接系统只接天气+教务，OA/数据库/工单/CRM ❌ |
| ReAct/多轮/并行/重试/超时 | ✅ 全达标 | 自研 ReAct + 并行调度 + tenacity 重试 + 超时，最强项 |
| 记忆管理 | ✅ 全达标 | 短期 `_history` + 长期 `long_term_memory` + user_id 过滤 |
| 权限管控 | ❌ 最明显缺口 | 只有数据权限（kb_groups）；工具调用鉴权没落地 |
| 全链路日志审计 | ⚠️ | 工具调用审计 ✅；思考留痕 ❌（Thought 无结构化记录） |
| 限流/熔断/降级 | ✅ 全达标 | 两层限流 + per-destination 熔断 + fallback，容错三件套 |

## 二、差距清单（7 项，按性价比排序）

| # | 缺口 | 归属 | 严重度 | 关键点 |
|---|------|------|--------|--------|
| 1 | **工具调用鉴权** | Agent | 🔴 高 | JWT 已签发 `permissions` 但没传导到工具层，Agent 可调任何工具。`MCP工程化.md` 有规划未落地 |
| 2 | **文档级权限** | RAG | 🔴 高 | 只有组级+visibility，无 per-document ACL |
| 3 | **思考过程留痕** | Agent | 🟠 中 | 合规要求「每一步思考可回溯」，当前只记工具调用不记 Thought |
| 4 | **生产级幻觉检测** | RAG | 🟠 中 | 只有 RAGAS 离线评测，生产无「回答是否被上下文支撑」的实时判定 |
| 5 | **多数据源** | RAG | 🟡 中 | 缺数据库/飞书/网页/工单连接器，工作量最大但门槛最低 |
| 6 | **向量库分布式集群** | RAG | 🟡 低 | client-server 单机，非分片/副本；百万级才需要 |
| 7 | **文档版本管理** | RAG | 🟡 低 | 只有快照回退，无多版本追踪/diff |

**核心判断**：前 4 项（鉴权 + 文档权限 + 思考留痕 + 幻觉检测）是「横切能力」，是 demo 到企业级的本质差距；后 3 项（多数据源 + 集群 + 版本管理）是「规模能力」，规模到了才需要。

## 三、分阶段规划（P4–P7）

### P4：Agent 合规闭环（工具鉴权 + 思考留痕）—— 性价比最高，先做

**为什么先做**：这是 Agent 清单唯一的 🔴 缺口（工具鉴权），且 JWT 里 `permissions` 字段**已经签发了**，只是没传导到工具层——改动小、面试硬伤、直接补上「Agent 不能随便调工具」这个企业级硬要求。思考留痕和它同属「Agent 合规」主题，一起做形成闭环。

| 改动 | 文件 | 说明 |
|------|------|------|
| 工具鉴权钩子 | `scheduler.py` | `_execute_one`（工具调用唯一收口）前插 `_check_tool_permission(tool_name, caller_perms)`，无权限结构化拒绝 |
| 权限传导 | `unified_agent.py` / `mcp_client_manager.py` | 登录态 `permissions` 传导到调度层（仿 kb_groups 参数透传模式，无文件） |
| 思考留痕 | `decision_engine.py` | ReAct 的 Thought/Action 结构化落盘（仿 tool_audit.jsonl 追加模式） |
| 权限字段 | `mcp_server.py` | 各工具声明 `required_perms`（如删除类工具需 `manage_kb`） |

**投入产出比**：**高**。改动集中（scheduler + decision_engine），面试价值大（补上「工具级鉴权」这个企业级硬要求）。

### P5：文档级权限（RAG 门面）

**为什么第二做**：部门隔离（组级）能做，但「文档 → 角色/用户」的细粒度授权是「企业级」的量级差异，是 RAG 权限链从「能用」到「合规」的门槛。

| 改动 | 文件 | 说明 |
|------|------|------|
| 文档 ACL 表 | `api_server.py` | permission.db 加 `doc_acl(doc_id, user/role, permission)` 授权表 |
| 权限过滤 | `vector_store.py` | `search` 的 where 从「组级」扩展「文档级」过滤（按用户能看的具体文档列表） |
| 双通道一致 | `bm25_index.py` | BM25 签名纳入文档级权限（防两通道泄露，同 P0 的教训） |

**投入产出比**：**中**。改动中等（授权表 + 过滤逻辑 + 双通道一致），企业级门面价值大。

### P6：RAG 横向扩展（多数据源 + 幻觉检测）

**为什么第三做**：多数据源是「横向扩展」（逐个加连接器，门槛低但工作量大），幻觉检测是「质量兜底」。两者都服务于「覆盖更多业务场景」，放在权限闭环之后。

| 改动 | 文件 | 说明 |
|------|------|------|
| 多数据源连接器 | `document_loader.py` | 数据库（SQL 拉取）/ 飞书 / 网页 / 工单，逐个加 loader 函数 |
| 幻觉检测 | `retriever.py` / 新模块 | 生产级 faithfulness 判定（回答是否被检索上下文支撑），未支撑则标注/降级 |

**投入产出比**：**中**。多数据源工作量大但门槛最低（每格式一个 loader）；幻觉检测改动中等。

### P7：规模演进（向量库集群 + 文档版本管理）—— 最后做

**为什么最后做**：这两项是「百万级规模才需要」的能力，现在做是过度设计（P2 已确立「按规模演进」原则）。

| 改动 | 文件 | 说明 |
|------|------|------|
| 向量库集群 | `vector_store.py` | 换 Milvus/Qdrant（分片/副本），数据迁移 |
| 文档版本管理 | `vector_store.py` / `kb_manager.py` | 多版本追踪 + diff + 按版本回滚 |

**投入产出比**：**低**。需换库/大改，当前数据量用不上。

## 四、优先级与投入产出比总表

| 阶段 | 主题 | 缺口 | 投入产出比 | 触发条件 |
|------|------|------|-----------|---------|
| **P4** | Agent 合规 | 工具鉴权 + 思考留痕 | 🔴 高 | 现在就该做（面试硬伤） |
| **P5** | 文档级权限 | 文档 ACL | 🟠 中高 | 需要细粒度授权时 |
| **P6** | 横向扩展 | 多数据源 + 幻觉检测 | 🟡 中 | 要接更多业务系统时 |
| **P7** | 规模演进 | 集群 + 版本管理 | ⚪ 低 | 百万级数据 / 多版本需求时 |

**贯穿原则**（继承 P0–P3）：
1. **零破坏**：不配置新参数/不传新参数时，行为与改造前一致
2. **按规模演进**：到了那个规模才做那个事，不超前设计
3. **双通道权限一致**：任何权限改动，向量 + BM25 两通道必须同步（P0 踩过的坑）
4. **无状态优先**：身份/权限靠参数透传，不靠文件共享
