## 二、7 坑修补详解

这是 LangChain 默认实现直接套用会踩的 7 个工程坑，每个都在本模块中做了修补：

### 坑 1：标题不入正文，向量检索丢标题语义

**问题**：`MarkdownHeaderTextSplitter` 默认只把标题存入 metadata，不放入 `page_content`。向量化时模型看不到标题内容。用户搜"第一章 引言"反而匹配不到对应 chunk。

**修复**：每个 chunk 正文开头拼接标题路径：
```
【章节：6G移动通信 > 1 引言】
当前，全球无线通信基础设施正经历着一场深刻的范式转变...
```

用 `【章节：...】` 格式而非 `## ...` 格式——避免被二级切分器再次识别为标题边界。

### 坑 2：文档开头无标题，孤儿块元数据为空

**问题**：摘要、前言、封面说明等内容出现在第一个 `#` 标题之前，被拆成元数据全空的块。

**修复**：兜底赋值 `{"h1": "文档前言", "h2": "", "h3": ""}`，避免空元数据导致后续过滤异常。

### 坑 3：标题层级断层，元数据传递错乱

**问题**：文档出现 H1→H3 跳级（没有 H2），默认拆分器保留空值。后续逻辑依赖完整层级时会出错。

**修复**：拆分后元数据向上继承——H3 的块如果没有 H2，自动取最近一个非空 H2 值。

```python
def _fill_header_gaps(sections):
    last_h1, last_h2 = '', ''
    for sec in sections:
        md = sec.metadata
        if md.get('h1'): last_h1 = md['h1']
        if md.get('h2'): last_h2 = md['h2']
        if not md.get('h1'): md['h1'] = last_h1
        if not md.get('h2') and md.get('h3'): md['h2'] = last_h2
```

### 坑 4：表格/代码块/公式的边界保护

**问题**：两级切分解决了标题边界，但章节内部的表格、公式、代码块依然可能被二级切分从中间切断。`MarkdownHeaderTextSplitter` 本身不解决这个问题。

**修复**：二级切分的 `separators` 优先级中，`\n\n`（双换行）排在句子标点之前。上游 document_loader 在表格/公式/代码块前后都插入了空行，靠这个保证这些语义单元不被拆散。

### 坑 5：小章节碎片化，影响检索效率

**问题**：很多短章节（只有一两行的标题+说明）被拆成十几字的超短块，浪费向量库存储空间，也干扰召回排序。

**修复**：章节长度 < `CHUNK_SIZE / 3` → 合并到相邻同级+同父级章节（优先向前合并），再参与二级切分。

```python
merge_threshold = int(CHUNK_SIZE * CHUNK_MERGE_RATIO)  # 500 * 1/3 ≈ 167
```

### 坑 6：原始元数据丢失

**问题**：拆分器默认只保留自己的元数据，原有 metadata（source、page_label、struct 等）会被覆盖。

**修复**：原始基础元数据全程透传，标题元数据（h1/h2/h3）增量追加，不覆盖：

```python
def _make_chunk(text, chunk_meta, header_meta, filename, page_label, struct_ctx):
    meta = {}
    if filename:    meta['source'] = filename       # 透传
    if page_label:  meta['page_label'] = page_label  # 透传
    for k in ('h1','h2','h3'):                      # 增量追加
        if header_meta.get(k): meta[k] = header_meta[k]
    if struct_ctx:  meta['struct'] = struct_ctx      # 专项结构
```

### 坑 7：空标题/异常标题容错

**问题**：不规范文档的 `#` 后面没有文字，拆分器生成空元数据的异常块。

**修复**：拆分后最终过滤——正文长度 < 10 字符的无效块直接丢弃。

## 三、关键设计决策

### 为什么是两级拆分而非一级？

| 方案 | 效果 |
|------|------|
| 仅 `MarkdownHeaderTextSplitter` | 长章节（>500字）成为一整块，召回粒度太粗 |
| 仅 `RecursiveCharacterTextSplitter` | 按字符硬切，标题/表格/公式全被切碎 |
| **两级拆分（当前）** | 一级保语义边界，二级控块大小 |

### 为什么 separators 中不用 `\n# ` 等标题分隔符？

一级拆分（`MarkdownHeaderTextSplitter`）已经按标题边界切过了。二级拆分处理的是单个章节内部的文本，不再需要标题分隔符。如果保留 `\n# ` 会导致章节内部的 `#` 引用被误切。

### 为什么标题路径用 `【章节：...】` 而非 `## ...`？

如果正文开头是 `## 第一章 > 1.1 背景`，`MarkdownHeaderTextSplitter` 会再次把它识别为二级标题，拆分逻辑会混乱。

### 为什么 `\n| ` 不加入 separators？

这是早期计划中的一个错误——把 `\n| `（表格行开头）加入 separators 会导致完整表格被切成一行一个块。正确的做法是**边界保护**（坑 4），而非把表格行当作分隔符。

## 四、与上下游的协作

```
上游（document_loader）                    本模块（text_splitter）              下游（vector_store）
══════════════════════                     ════════════════════════            ═══════════════════
输出统一 Markdown                          两级语义切分                         向量化存入 ChromaDB
  │                                          │                                    │
  ├─ #/##/### 标题                           ├─ 一级按标题切                       ├─ 每个 chunk 独立向量
  │   → MarkdownHeaderTextSplitter 识别       │   章节变 chunk                     │
  │                                          │                                    │
  ├─ \n\n 段落边界                            ├─ 二级按双换行优先切                ├─ 表格/公式不被拆散
  │   → 表格/公式/代码块被空行隔离             │   保护语义单元                     │   检索时返回完整结构
  │                                          │                                    │
  ├─ $$...$$ / |...| 结构标记                 ├─ 标题路径拼入正文开头               ├─ 向量包含层级上下文
  │                                          │   【章节：H1 > H2】               │   搜索"引言"可命中
  │                                          │                                    │
  └─ metadata: source/page_label             └─ metadata 透传+增量追加             └─ 检索结果带来源标注
```

**核心约束**：上游只需输出标准 Markdown，下游只需一套分块逻辑。无论来源是 PDF 快速通道、PDF 慢速通道还是 DOCX，分块器行为完全一致。

## 七、未来进阶计划：父子分块（Parent-Child）+ 语义切片

> **现状定位**：当前是"Markdown 标题 + 递归字符"的两级**规则切分**，产出**单层扁平 chunk**。它解决了"句子切断/标题丢失/碎片化"，但仍有两个天花板：
> 1. **切块粒度两难**：块太小 → 检索精准但上下文不足，LLM 答不全；块太大 → 上下文足但向量语义被稀释，检索命中率下降。
> 2. **断点靠标点/字数**：`RecursiveCharacterTextSplitter` 在 `CHUNK_SIZE=500` 处按分隔符硬断，可能把"语义连贯的一段话"拦腰截断。
>
> 下面两项进阶专门解决这两个天花板，**均可在现有 `text_splitter.py` 上增量实现，不破坏现有规则切分**。

### 7.1 父子分块（Parent-Child Chunking）

**要解决的问题**：粒度两难。让"**检索用小块**（精准命中）"与"**喂给 LLM 用大块**（上下文完整）"解耦。

**核心思路**：
- **父块（Parent）**：较大粒度（如整个 `##` 章节，或 1500~2000 字），保存完整上下文。
- **子块（Child）**：在父块内继续细切成小块（如 200~300 字），**只有子块进向量库参与检索**。
- **检索时**：向量命中子块 → 通过 `parent_id` 回溯其父块 → **把父块（而非子块）喂给 LLM**。既保留小块的检索精度，又补齐大块的上下文。

**落地设计（增量，不推翻现状）**：
1. `text_splitter.py` 新增 `split_documents_parent_child()`：
   - 复用现有两级切分产出**父块**（当前的 chunk 即可直接作父块）。
   - 对每个父块再跑一次小粒度 `RecursiveCharacterTextSplitter` 得**子块**。
   - 每个子块 metadata 写入 `parent_id`（= 父块的稳定 ID `{file_hash}_{index:04d}`）与 `chunk_level="child"`。
2. **父块存储**两条路线，二选一：
   - **路线 A（LangChain 原生）**：用 `ParentDocumentRetriever` + `InMemoryStore`/本地 docstore 存父块，子块进 Chroma。改动集中、但要引入新检索器。
   - **路线 B（贴合现状，推荐）**：父块和子块**都进 Chroma**（父块标 `chunk_level="parent"` 且 `is_parent_only=True` 不参与检索过滤），检索只查子块，命中后在 [retriever.py](rag_assistant/retriever.py) 用 `parent_id` 批量 `get()` 回捞父块去重。复用现有 ChromaDB + `vector_store` 元数据体系，无需新组件。
3. [retriever.py](rag_assistant/retriever.py) 的 `retrieve_and_answer` / `answer_with_fallback`：检索 → 收集命中子块的 `parent_id` → 回捞父块 → 去重 → （可选重排）→ `build_prompt`。

**预期收益**：多跳/长文档问题的上下文完整度显著提升；可用第五功能的 **RAGAS `context_recall`** 量化验证（父子分块前后对比）。

### 7.2 语义切片（Semantic Chunking）

**要解决的问题**：断点不智能。用 **embedding 相似度**决定切分点，而非字数/标点。

**核心思路**：
- 先把文本按句子拆分，逐句计算 embedding。
- 计算**相邻句子的向量相似度**，在**相似度骤降处**（语义发生转折）设切分点 → 每个 chunk 内部语义高度内聚。

**落地设计**：
- 优先复用 LangChain 实验组件 `langchain_experimental.text_splitter.SemanticChunker`，**直接复用项目现有嵌入** `paraphrase-multilingual-MiniLM-L12-v2`（`vector_store.get_embeddings()`），无需新模型。
- `breakpoint_threshold_type`（`percentile` / `standard_deviation` / `gradient`）作为可调参数写入 `config.py`。
- **定位**：作为**二级切分的可选替代**——一级仍走 `MarkdownHeaderTextSplitter`（保留标题结构），超长章节的二次切分从"递归字符"切换为"语义切片"。用开关 `SPLIT_STRATEGY = "recursive" | "semantic"` 控制，默认保持 `recursive` 兼容现状。

**代价与权衡**：语义切片要为每句算 embedding，**切块阶段耗时上升**（一次性建库成本，非查询期成本）；小/结构化文档收益有限，**长的连续叙述型文档收益最大**。

### 7.3 组合与验证

- 两者**可叠加**：语义切片决定"子块"的自然边界，父块仍按章节聚合 → "语义子块 + 章节父块"。
- **验证闭环**：借助已落地的 RAGAS 评测体系（见 `RAG评测体系.md`），把"父子分块""语义切片"作为新的 A/B 配置项，量化 `context_recall`（召回全面性）与 `faithfulness`（上下文是否够 LLM 作答）的前后变化，用数据驱动是否采纳。

**优先级建议**：先做 **7.1 父子分块**（对"长文档上下文丢失"最对症、收益最直接、贴合现有 Chroma 架构），再视效果做 **7.2 语义切片**。
