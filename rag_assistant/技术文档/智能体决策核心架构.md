# 智能体决策核心架构

## 1. 概述

智能体决策核心是 RAG 智能助手的"大脑"，负责理解用户意图、选择合适的工具、编排执行顺序，并生成最终回答。本文档描述其架构设计、决策流程和输出约束机制。

## 2. 架构总览

```
用户输入
    ↓
┌─────────────────────────────────────────────────────────────┐
│  决策引擎 (DecisionEngine)                                    │
│                                                               │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐                │
│  │ Prompt   │ →  │   LLM    │ →  │ 输出解析  │                │
│  │ 构建器    │    │ (DeepSeek)│    │ (Parser) │                │
│  └──────────┘    └──────────┘    └──────────┘                │
│       ↑                            ↓                          │
│  工具注册表                    AgentDecision                   │
│  Skill注册表                   (结构化决策)                     │
│  对话历史                                                      │
│  长期记忆                                                      │
└─────────────────────────────────────────────────────────────┘
    ↓
┌─────────────────────────────────────────────────────────────┐
│  执行调度器 (Scheduler)                                       │
│                                                               │
│  ① 权限校验 → ② 参数注入 → ③ Schema校验 → ④ MCP工具调用      │
└─────────────────────────────────────────────────────────────┘
    ↓
  工具结果 → 最终回答
```

## 3. 决策流程：基于 ReAct 范式的自研五阶段

本项目基于 ReAct（Reasoning + Acting）范式进行自研扩展，从原生四阶段演进为五阶段循环：

```
原生 ReAct:  Thought → Action → Observation → (循环)
自研五阶段:  Plan → Thought → Action → Observation → Evaluation → Decision → (循环)
```

### 3.1 五阶段定义

| 阶段 | 职责 | 首轮 | 后续轮次 |
|------|------|------|----------|
| **Plan** | 任务分解，规划执行步骤 | ✅ 必填 | — |
| **Thought** | 推理过程，说明为什么选择这个行动 | ✅ 必填 | ✅ 必填 |
| **Action** | 执行工具或直接回答 | ✅ 必填 | ✅ 必填 |
| **Observation** | 工具返回结果（框架层记录） | ✅ 自动 | ✅ 自动 |
| **Evaluation** | 评估当前进展，信息是否足够 | — | ✅ 必填 |
| **Decision** | 决定下一步：continue/answer/abort | — | ✅ 必填 |

### 3.2 完整循环示例

```
第1轮（首轮）:
  Plan:        1. 查询北京天气  2. 搜索故宫攻略  3. 汇总出行建议
  Thought:     用户需要天气+故宫建议，先查天气，可并行查知识库
  Action:      call_tools → [query_weather, search_knowledge_base]
  Observation: 天气：晴 28°C；知识库：故宫攻略片段

第2轮（后续轮次）:
  Evaluation:  天气和攻略都已获取，信息足够回答
  Decision:    answer
  Thought:     基于天气和攻略，汇总完整的出行建议
  Action:      direct_answer → "北京今天晴天28°C，去故宫建议..."
```

### 3.3 为什么扩展为五阶段

原生 ReAct 的 Thought 隐含了 Evaluation + Decision，但存在以下问题：

| 问题 | 说明 |
|------|------|
| **审计不清晰** | Thought 混合了推理和决策，难以分离分析 |
| **控制粒度粗** | 无法在 Observation 后显式决定"继续/终止/回答" |
| **abort 无入口** | 遇到无法解决的问题时，缺少显式终止机制 |

自研五阶段的改进：

| 改进 | 说明 |
|------|------|
| **Evaluation 显式化** | 每轮独立评估进展，审计可追溯"为什么继续/终止" |
| **Decision 显式化** | 三种决策（continue/answer/abort）明确下一步行动 |
| **Plan 首轮规划** | 首轮输出任务分解，后续轮次可对照执行进度 |

## 4. 决策输出结构

LLM 输出 JSON，经 Structured Outputs 硬约束后，解析为 `AgentDecision` 对象：

```python
@dataclass
class AgentDecision:
    action: Literal["direct_answer", "call_tools"]
    tools: list[ToolDecision]      # call_tools 时的工具列表
    execution_mode: str            # serial / parallel
    direct_response: str | None    # direct_answer 时的回答内容
    plan: str                      # 首轮规划
    thought: str                   # 推理过程
    evaluation: str                # 评估内容（后续轮次）
    decision: str                  # continue / answer / abort
```

### 4.1 输出模式示例

#### 模式一：首轮调用工具
```json
{
  "plan": "1. 查询北京天气 2. 搜索故宫攻略 3. 汇总出行建议",
  "thought": "用户需要天气+故宫建议，先查天气",
  "evaluation": "",
  "decision": "continue",
  "action": "call_tools",
  "tools": [{"tool_name": "query_weather", "arguments": {"city": "北京"}}],
  "execution_mode": "serial"
}
```

#### 模式二：后续轮次评估后回答
```json
{
  "plan": "",
  "thought": "天气已查到，信息足够",
  "evaluation": "天气：晴 28°C，攻略：已获取故宫游览建议",
  "decision": "answer",
  "action": "direct_answer",
  "direct_response": "北京今天晴天28°C，去故宫建议..."
}
```

#### 模式三：后续轮次继续调用
```json
{
  "plan": "",
  "thought": "天气已知，还需查故宫攻略",
  "evaluation": "天气已获取，攻略未搜索",
  "decision": "continue",
  "action": "call_tools",
  "tools": [{"tool_name": "search_knowledge_base", "arguments": {"query": "故宫攻略"}}],
  "execution_mode": "serial"
}
```

#### 模式四：abort 终止
```json
{
  "plan": "",
  "thought": "API 持续超时，无法获取数据",
  "evaluation": "query_weather 连续 3 次超时",
  "decision": "abort",
  "action": "direct_answer",
  "direct_response": "抱歉，天气服务暂时不可用，请稍后再试"
}
```

## 5. 输出约束机制：Structured Outputs

### 5.1 为什么需要硬约束

| 约束方式 | 可靠性 | 说明 |
|---------|--------|------|
| Prompt 文本约束 | ⚠️ 弱 | LLM 可能不遵循格式 |
| 正则解析兜底 | ⚠️ 弱 | 需要处理各种格式变体 |
| Structured Outputs | ✅ 强 | LLM **必须**输出合法 JSON |

### 5.2 API 兼容性与降级策略

不同 LLM API 对 Structured Outputs 的支持程度不同：

| API | `json_schema` | `json_object` | 降级策略 |
|-----|--------------|---------------|---------|
| OpenAI (GPT-4o) | ✅ 支持 | ✅ 支持 | 无需降级 |
| DeepSeek | ❌ 不支持 | ✅ 支持 | 自动降级到 `json_object` |
| Groq | ❌ 不支持 | ✅ 支持 | 自动降级到 `json_object` |

**降级逻辑**（`decision_engine.py`）：
```python
# 模块级探测缓存：None=未探测 / True=支持 / False=不支持
_JSON_SCHEMA_SUPPORTED = None

response_format = _pick_response_format(         # 已知不支持 → 直接用 fallback
    REACT_RESPONSE_FORMAT_STRICT, REACT_RESPONSE_FORMAT_FALLBACK
)
try:
    response = call_llm_with_cb(..., response_format=response_format)
except Exception as e:
    if _is_json_schema_unavailable(str(e)):
        _mark_json_schema_unsupported()          # 记住探测结果
        response_format = REACT_RESPONSE_FORMAT_FALLBACK  # 降级到 json_object
```

> **为什么要探测缓存**：降级结果原先只在单次调用内生效，导致**每次决策都白发一个注定 400 的请求**
> （一轮 ReAct 一次、每次 Skill 匹配一次）。加模块级标记后，**每个进程只探测一次**，
> 之后直接走 `json_object`，日志里那行 WARNING 也只在首次出现。

**相关的熔断语义修正**（`circuit_breaker.py`）：`call_llm_with_cb` 原先把所有异常都记为熔断失败，
包括这类 **4xx 客户端错误**（参数不支持/鉴权/额度）。4xx 说明「请求本身有问题」，不是下游故障，
不应计入熔断。现按 `status_code` 区分：**4xx 不记，超时/5xx/连接错误照记**。

**`json_object` 模式的局限**：
- 只保证输出是合法 JSON，不保证结构符合 Schema
- 需要依赖 Prompt 约束 + 解析层兜底
- `json_object` 模式下，LLM 可能输出任意 JSON 结构

### 5.2 JSON Schema 定义

```python
REACT_DECISION_SCHEMA = {
    "name": "react_decision",
    "strict": True,
    "schema": {
        "type": "object",
        "properties": {
            "plan": {"type": "string", "description": "任务规划（首轮必填）"},
            "thought": {"type": "string", "description": "推理过程"},
            "evaluation": {"type": "string", "description": "评估当前进展（后续轮次必填）"},
            "decision": {"type": "string", "enum": ["continue", "answer", "abort"]},
            "action": {"type": "string", "enum": ["call_tools", "direct_answer"]},
            "tools": {
                "type": "array",
                "items": {
                    "type": "object",
                    "properties": {
                        "tool_name": {"type": "string"},
                        "arguments": {"type": "object"}
                    },
                    "required": ["tool_name", "arguments"],
                    "additionalProperties": False
                }
            },
            "execution_mode": {"type": "string", "enum": ["serial", "parallel"]},
            "direct_response": {"type": "string"}
        },
        "required": ["action"],
        "additionalProperties": False
    }
}
```

### 5.3 Structured Outputs 的局限

Structured Outputs 只保证 **JSON 结构合法**，不保证 **业务逻辑合法**：

| 校验层级 | 谁负责 | 示例 |
|---------|--------|------|
| JSON 格式 | Structured Outputs | 保证是合法 JSON |
| 字段类型 | Structured Outputs | `action` 必须是枚举值 |
| 工具名存在 | Scheduler `registry.validate()` | `query_weather` 在注册表中 |
| 参数 Schema | Scheduler `jsonschema.validate()` | `city` 是 string 类型 |
| 权限校验 | Scheduler `_check_tool_permission()` | 用户有权调用该工具 |
| 参数值合法 | 工具内部 | "北京"是有效城市名 |

## 6. 多层校验体系

```
LLM 输出（Structured Outputs 保证 JSON 合法）
    ↓
① Parser 层：JSON → AgentDecision（结构映射）
    ↓
② Scheduler 层：三重校验
    ├─ 2a. 工具名白名单：registry.validate() → "工具不存在"
    ├─ 2b. 参数 Schema：jsonschema.validate() → "参数类型错误"
    └─ 2c. 权限校验：_check_tool_permission() → "权限拒绝"
    ↓
③ 工具层：业务规则校验
    └─ 工具内部处理无效参数，返回错误信息
    ↓
④ LLM 观察：根据工具结果决定下一步
```

## 7. 关键设计决策

### 7.1 为什么不用 Function Calling

| 维度 | Function Calling | Structured Outputs |
|------|-----------------|-------------------|
| 输出内容 | 只有工具调用，无推理过程 | 完整 JSON（plan+thought+action） |
| 控制权 | LLM 直接调工具 | 框架解析后主动调度 |
| 审计留痕 | ❌ 无 plan/thought | ✅ 完整记录 |
| 适用场景 | "LLM 就是要调工具" | "LLM 先推理再决策" |

### 7.2 为什么采用自研五阶段而非原生四阶段

原生 ReAct 的四阶段（Thought→Action→Observation→循环）简洁高效，但在企业级场景下存在不足：

| 原生 ReAct 局限 | 自研五阶段改进 |
|----------------|---------------|
| Thought 混合推理和决策 | Evaluation 独立评估，Decision 显式决策 |
| 无法显式终止（abort） | `decision: abort` 明确终止语义 |
| 审计时难以分离"为什么继续" | Evaluation 字段独立记录评估过程 |
| 首轮无任务分解 | Plan 字段明确执行步骤 |

自研五阶段的 Evaluation 与 Thought 职责不同：
```
Thought:    "用户问了天气和故宫建议，先查天气"     ← 推理（怎么做）
Evaluation: "天气已查到，但故宫攻略还需搜索"        ← 评估（做到哪了）
Decision:   "continue"                             ← 决策（下一步）
```

### 7.3 正则解析 vs Structured Outputs

| | 正则解析（旧） | Structured Outputs（新） |
|---|---|---|
| JSON 合法性 | ⚠️ 依赖 LLM 遵循格式 | ✅ 强制合法 |
| 字段存在性 | ⚠️ 可能缺失 | ✅ required 保证 |
| 枚举值 | ⚠️ 可能输出非法值 | ✅ enum 约束 |
| 解析复杂度 | 高（多分支正则） | 低（直接 json.loads） |
| 容错 | 需要 try/except 兜底 | 基本不需要 |

## 10. 改造计划：引入独立 Judge 模型

### 10.1 背景与动机

当前架构中，终止判断（`decision: continue/answer/abort`）由主 LLM 在生成决策时一并输出。这种方式存在以下问题：

| 问题 | 说明 |
|------|------|
| **职责耦合** | 主 LLM 同时负责推理、工具调用和终止判断 |
| **成本浪费** | 仅为判断是否终止，需要调用完整决策流程 |
| **不可控** | LLM 可能在信息不足时过早终止，或过度循环 |

### 10.2 设计目标

引入独立的 **Judge 模型**，职责单一：**判断当前已收集的信息是否足够回答用户问题**。

### 10.3 架构改动

**改造前**：
```
┌─────────────────────────────────────────────────────┐
│  Observation → 主 LLM (Decision Engine) → 继续/终止  │
└─────────────────────────────────────────────────────┘
```

**改造后**：
```
┌─────────────────────────────────────────────────────┐
│  Observation → Judge 模型 (Yes/No)                   │
│                      │                               │
│                      ├─ No → 主 LLM 继续推理          │
│                      └─ Yes → 跳过主 LLM，直接生成答案 │
└─────────────────────────────────────────────────────┘
```

### 10.5 Judge Prompt 模板

```python
JUDGE_PROMPT = """#【任务目标】
{task_goal}

#【已收集信息】
{collected_info}

#【用户问题】
{user_query}

#【判断要求】
当前已收集的信息是否足够完整地回答用户问题？

#【输出格式】
只输出一个单词：Yes 或 No
- Yes：信息足够，可以生成最终答案

```

### 10.6 伪代码实现

```python
# unified_agent.py 改造后逻辑
async def _run(self, query: str, ...):
    # ... Skill 匹配逻辑 ...

    for round_idx in range(self.max_rounds):
        # 1. 主 LLM 生成 Thought + Action
        decision = self.decision_engine.decide(...)

        if decision.action == "direct_answer":
            return decision.direct_response

        # 2. 执行工具，获取 Observation
        observations = await self.scheduler.execute_tools(decision.tools)
        collected_info += format_observations(observations)

        # 3. 调用 Judge 模型判断是否足够（新增）
        if config.JUDGE_ENABLED:
            judge_result = await self.judge.evaluate(
                task_goal=query,
                collected_info=collected_info,
                user_query=query
            )

            if judge_result == "Yes":
                # 4a. 信息足够，直接生成最终答案
                return await self._generate_final_answer(query, collected_info)
            # 4b. 信息不足，继续下一轮
            continue
        else:
            # 使用原有主 LLM Decision 判断
            if decision.decision == "answer":
                return decision.direct_response
```

### 10.9 定位与边界（诚实评估）

Judge 的定位是「职责分离 + 可替换的软性组件」，**而非「更强的终止判断」**。需澄清以下常见误区：

| 说法 | 实际情况 |
|------|---------|
| ❌ Judge 成本约为主 LLM 的 1/10 | 默认 `JUDGE_MODEL` 与主模型相同（deepseek-flash），成本并未降低；「换更小模型省钱」是**潜力**，尚未兑现 |
| ❌ Judge 延迟约为主 LLM 的 1/5 | 同模型延迟相近，无此数量级优势 |
| ❌ 独立复核避免主 LLM「又当运动员又当裁判」 | Judge 是**同模型后验确认**，在主模型已选定工具并执行后才介入，复核的是主模型上一步的选择，非并行的第二意见 |
| ✅ 职责分离 | 终止判断从「下一步调什么工具」中解耦为独立二分类任务，架构清晰 |
| ✅ 可替换 | 二分类任务未来可换更小模型 / 规则 / 启发式 |
| ✅ 可审计 | 终止决策有独立落点，事后可单独分析「为什么这轮停了」 |

**结论**：Judge 的效果优势（终止更准）未经 A/B 数据验证；真正的强保证来自非 LLM 护栏（死循环检测、轮次上限、熔断），详见第 11 节。

## 11. 自研 vs LangChain AgentExecutor 对比总结

### 11.1 为什么不用 AgentExecutor

AgentExecutor 是 LangChain 对 ReAct 范式的具体实现类。本项目自研引擎替代它，源于三个结构性缺陷：

| 缺陷 | 说明 |
|------|------|
| **天然串行** | `while` 循环一次只执行一个工具，无法并行编排「查天气 + 查知识库」 |
| **终止语义弱** | 终止唯一出口是 LLM 输出 `Final Answer`，由单模型自我声明，框架不提供结构性校验；LLM 空转时只能跑满 `max_iterations` 硬断 |
| **输出靠正则** | OutputParser 用正则抠 `Action:` / `Final Answer:` 文本，格式跑偏即解析失败 |

### 11.2 核心差异

按「硬 / 软」分层，避免混淆效果优势与架构优势：

**硬能力（不依赖 LLM 自觉，真正的差异）**

| 能力 | AgentExecutor | 自研 |
|------|--------------|------|
| 并行执行 | 一轮只串行一个工具 | 无依赖工具异步并发执行 |
| 死循环检测 | ❌ 只会跑满硬断 | 调用指纹连续重复即打断（纯代码） |
| 熔断 + 限流 + 指数退避 | ❌ | 下游故障快速失败、频率受控、瞬时抖动重试 |

**软能力（架构层，非效果层）**

| 能力 | 说明 |
|------|------|
| 结构化输出 | 用输出约束强制合法 JSON，替代正则抠文本 |
| MCP 直连 | 去掉 Tool 抽象层，工具发现 / 调用全自控 |
| 五阶段 + abort 语义 | 把「答不了」和「答完了」从 `Final Answer` 拆开 |
| 技能路由层 | 关键词 + 向量双重匹配，失败无感降级 |

### 11.3 需澄清的「非差异」或「未证优势」

以下常被误当作自研优势，实为**非差异**或**未证优势**：

| 说法 | 实际情况 |
|------|---------|
| ❌ 自研循环「有界」vs AgentExecutor「无界」 | 两者**都有**次数上限（AgentExecutor 还多一个时间上限），循环外壳不是差异，差异在循环体内部 |
| ❌ 五阶段的「评估/决策」比 `Final Answer` 判断更准 | `evaluation`/`decision` 字段同样是 LLM 填的，与 `Final Answer` 在「谁来判断」上同构；真实价值是**可审计**与**显式 abort 语义**，非判断更准 |
| ❌ 独立 Judge 让终止更准 | Judge 是同模型后验确认，效果优势未经数据验证（见 10.9） |

### 11.4 优势清单（诚实标注强度）

| 优势 | 强度 | 说明 |
|------|------|------|
| 端到端延迟更低（并行） | 强 | 无依赖工具同时调，不等串行 |
| 输出解析可靠 | 强 | 约束到 JSON，不靠正则碰运气 |
| 终止不会失控 | 强 | 死循环检测 + 轮次上限 + 熔断，纯代码兜底 |
| 可审计、可追溯 | 中 | 五阶段字段落盘，每轮「为什么停」可回溯 |
| 可替换性 | 中 | 终止判断 / 工具接入可单独替换 |
| Judge 让终止更准 | 弱/未证明 | 同模型后验确认，无 A/B 数据 |

### 11.5 一句话总结

> 自研相对 AgentExecutor，核心是「并行 + 结构化输出 + 非 LLM 护栏」三点：它串行我并行、它正则我约束、它只有硬上限我加了死循环检测和熔断。其余（五阶段、Judge、技能路由）是架构清晰度和可维护性的加分项，不是效果层面的硬优势。

## 12. 工具失败后的「重新规划 or 降级」（2026-09 改造）

### 12.1 问题：护栏一刀切，把失败也推向了直接回答

原实现在 Prompt 构建时只判断一件事——**本轮有没有执行过工具**：

```python
has_executed = any("本轮已执行" in h for h in reflection_hints)
if has_executed:
    hints_text += (
        "\n\n⚠️ 上述工具已在本轮执行完毕并返回结果，"
        "请使用 direct_answer 汇总结果回答用户，不要再调用工具。"
    )
```

而"工具失败"写进历史的格式是 `[本轮已执行] 工具「X」→ 失败: ...`——**同一个前缀**，所以**失败同样命中这句话**。

后果：**工具失败后，Prompt 明确要求"不要再调用工具、直接汇总"，等于掐断了"换个工具重试"的路径。**

更麻烦的是基座模板里还有一条静态规则，同样是一刀切：

> 3. **已执行工具的处理**：如果"工具选择历史"中显示本轮已有工具成功执行并返回结果，你必须使用 direct_answer 汇总这些结果来回答用户，**不要再调用工具**。

（它的条件虽然写了"成功"，但结论只给了成功分支，失败时 LLM 没有可遵循的指引。）

### 12.2 为什么这是个真问题

工具失败的原因**并不相同**，恢复动作也不该相同：

| 失败原因 | 正确的恢复动作 | 一刀切护栏的实际效果 |
|---------|--------------|-------------------|
| LLM 编了不存在的工具名 | **换一个真实存在的工具** | ❌ 被推向直接回答 |
| 工具不存在/未注册 | 换工具或如实说明 | ❌ 同上 |
| 权限不足 | 换工具或如实说明 | ❌ 同上 |
| 参数校验失败 | **用正确参数重试或换工具** | ❌ 同上 |
| 瞬时故障（重试后仍超时） | 换工具或降级 | ❌ 同上 |

注意第一种——**"LLM 把 Skill 名当工具名调"** 是本项目真实踩过的坑（`scheduler._execute_one` 里专门为它写了「工具不存在 ≢ 权限拒绝」的区分逻辑）。这类失败**本来就该让 LLM 换个工具重试**，但旧护栏恰好把这条路堵死了。

### 12.3 改法：按成败状态分流引导

**核心思路**：护栏要区分「成功」和「失败」，给不同的下一步指引。

**① 动态引导（`prompt_templates.build_decision_prompt`）**

从已执行提示中解析状态，分三种情况：

```python
_EXECUTED_STATUS_RE = re.compile(r"\]\s*(?:工具|Skill)「[^」]*」→\s*(成功|失败)")
...
statuses = _EXECUTED_STATUS_RE.findall(hints_text)
n_ok, n_fail = statuses.count("成功"), statuses.count("失败")

if n_fail == 0:        # 全成功 → 要求汇总
    "…请使用 direct_answer 汇总结果回答用户，不要再重复调用同样的工具。"
elif n_ok == 0:        # 全失败 → 允许重规划或降级
    "…全部失败（已重试后仍失败），不要原样重试同一个工具。你可以二选一：
     ① 换用其他能达成目标的工具重新尝试；
     ② 若确无可用工具，使用 direct_answer 如实说明失败原因并给出可行的替代建议。"
else:                  # 部分成功 → 两条路径都提示
    "…{n_ok} 个成功、{n_fail} 个失败。已成功的结果可直接使用；
     失败的那些不要原样重试，可换用其他工具补齐，或基于已有结果用 direct_answer 回答。"
```

**② 基座静态规则同步分流**：把那条只讲成功的规则改成两分支，与新引导保持一致，避免 LLM 同时看到"不要再调用工具"和"换用其他工具"而困惑。

**③ 为什么可以正则解析**：这**不是**解析 LLM 输出，而是解析**本项目自己生成的确定性字符串**（格式由 `unified_agent` 唯一决定）。项目在 §7.3 明确反对用正则解析模型输出，但此处不适用——字符串是我们自己拼的，不存在格式漂移。正则还锚定在 `」→ ` 之后，避免**工具返回内容**里出现"成功/失败"字样时误判（已加测试覆盖）。

### 12.4 完整流转（改造后）

```
工具执行 → 失败（重试后仍失败）→ 以 is_error 结果返回（不抛异常）
   ↓
进 all_results → 下一轮拼进 hints：「[本轮已执行] 工具「X」→ 失败: <原因>」
   ↓
护栏识别为「全失败」→ 追加引导：可换工具重规划 / 或降级说明
   ↓
LLM 下一轮决策：
   ├─ 换一个工具 → 重新执行（真正实现"重新规划"）
   └─ direct_answer → 降级回答（如实说明失败原因）
   ↓
兜底：连续 3 次相同调用签名 → 死循环检测强制汇总
     轮次耗尽 / Token 预算耗尽 → 强制 final_answer 或返回中间结果
```

### 12.5 能力边界（诚实标注）

| 场景 | 能否触发重规划 | 说明 |
|------|:---:|------|
| **工具全部失败** | ✅ 是 | 循环继续，护栏引导换工具 —— 本次改造的主目标 |
| **部分成功**（Judge 开启且判"信息不足"） | ✅ 是 | Judge 会 `continue` 到下一轮，此时走"部分成功"引导 |
| **部分成功**（Judge 关闭 / Judge 异常） | ❌ 否 | 代码在"有任一工具成功"时直接 `final_answer` 汇总返回 |

最后一行是**保留的原有设计**：已有部分结果时，先把能答的答出来比继续循环更符合用户预期。若要让部分成功也强制重规划，需改动 `_pipeline` 的返回条件——本次未动，因为那会把"回答更快"换成"更全但更慢"，是产品取舍而非缺陷修复。

另：**死循环检测仍然生效**——若 LLM 换汤不换药地重复同一工具三次，会被 `LOOP_DETECTION_THRESHOLD` 强制终止汇总，所以放开重试不会导致无限循环。

### 12.6 验证

`test_replan_guardrail.py` **32 项全过**，覆盖：

- **正常**：全成功 / 全失败 / 部分成功 → 三种引导文案互斥且各自正确；Skill 失败同样识别；工具+Skill 混合计数正确
- **边界**：工具返回内容含"失败"字样但状态为成功 → 不误判；无已执行提示 → 不追加引导；hints 为空 → 走空分支；只有长期记忆 → 不误称"已执行"；正则对 5 种格式变体的鲁棒性
- **异常**：畸形条目不抛错且不误引导；空工具名等退化条目可解析不崩；首轮与后续轮模板都生效

### 12.7 一句话总结

> 原来的护栏只问"**做没做过**"，所以"做失败了"和"做成功了"得到同一句指引——**失败也被要求直接回答**。
> 改成问"**做得怎么样**"之后，失败才真正回到决策循环里，有机会**换个工具重规划**，或者**降级如实说明**。
> 这是"由 ReAct 决策循环重新规划或降级处理"这句话从**描述**变成**事实**的一次改造。
