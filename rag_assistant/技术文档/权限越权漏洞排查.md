# 权限越权漏洞排查（STAR 法则）

> 一份用 STAR 法则组织的技术复盘，既是排查记录，也可直接作为面试讲稿。
> 主题：完成 RAG 权限系统改造后，通过代码审查发现并定位了「权限越权泄露」安全隐患。

---

## S — 情境（Situation）

完成 RAG 知识库的**部署运维改造**（P0 模型服务化 + 权限重构，P1 熔断器 + 容器化）后，我没有直接交付，而是做了一次**代码审查**，专门核对改造是否真的解决了它声称要解决的问题。

改造声称「权限从全局 JSON 文件改为请求级参数透传」，但我发现代码里**残留了两处文件共享**：`set_current_kb_groups()` 仍在写文件、`set_current_user()` 仍在写用户身份文件。这两处当时被我标记为「设计权衡」，用于兼容旧调用路径。

问题在于：我没有验证这些「权衡」在**真实多用户并发**下会怎样。

---

## T — 任务（Task）

评估这两个残留如果**上线给真实用户使用**，会造成什么影响，判断它们是「可接受的权衡」还是「必须修复的隐患」。

具体要回答三个问题：

1. 文件兜底在并发下会不会串台？串台的方向是「权限收窄」还是「越权泄露」？
2. 长期记忆的文件共享会不会造成用户间的记忆混淆？
3. 根因是什么？是单一 bug 还是一个系统性的设计缺陷？

---

## A — 行动（Action）

我逐条推演了并发场景，发现了比预期严重得多的问题：

### 1. 文件兜底：不是「收窄」，是「双向串台」，且越权泄露致命

`search()` 的权限判断逻辑是：`kb_groups=None` 时回退读全局文件，文件读出来是空就「无过滤」。

推演出两条路径：

**路径 A（权限收窄，业务受损）**：
```
管理员登录 → 文件写 [] → 用户B登录覆盖成 ["dept_hr"]
→ 管理员再查 → 读文件得 ["dept_hr"] → 被错误限制只能看 dept_hr
```

**路径 B（越权泄露，安全事故）**：
```
管理员登录 → 文件写 []（空）
→ 任何走 None 路径的请求此刻读文件 → 空 → 无过滤 → 全库机密可见
```

**关键结论**：`kb_groups=None` 的语义本该是「管理员/不限权限」，但它和「文件被写成空」混淆了。多用户并发下「文件恰好为空」必然发生，等于给所有用户留了一个**随机出现的越权后门**——不是每次能越权，但随时可能。

### 2. 长期记忆：用户 A 会注入用户 B 的记忆

```
用户A登录 → 文件 {"user_id":"A"} → 用户B登录覆盖成 {"user_id":"B"}
→ 用户A再提问 → 读文件得 "B" → 对话注入 B 的私人记忆，且实体抽取污染 B 的记忆库
```

### 3. 顺带揪出两个改造引入的 bug

审查中还发现两个**我自己在改造时引入的 bug**：

- 🔴 **BM25 通道权限泄露**：向量通道传了 `kb_groups`，但 BM25 通道 `search_bm25` 无权限参数，RRF 融合后未授权文档进入候选集，跨组泄露。
- 🟠 **debug_rerank 参数断裂**：`_KB_TOOLS` 给 `debug_rerank` 注入了 `kb_groups`，但函数签名没有这个参数。

### 4. 根因定位

四个问题的本质是**同一个病**：**用「全局共享的可变文件」承载「请求级的隔离信息」**。只要有并发，共享可变状态就必然产生数据竞争。这不是四个独立 bug，是一个系统性的架构缺陷。

---

## R — 结果（Result）

**修复了两个 bug（已验证）**：

| 问题 | 修复 | 验证 |
|------|------|------|
| BM25 通道权限泄露 | `search_bm25` 加 `kb_groups` + 权限过滤 | 跨组查询无泄露 |
| debug_rerank 参数断裂 | 函数加 `kb_groups` 参数透传 | 语法通过 |

**收敛了两个残留（已彻底移除文件机制）**：

| 残留 | 生产影响 | 收敛结果 |
|------|---------|---------|
| 文件兜底 | 越权泄露（安全事故级） | `search()` 的 `kb_groups=None` 回归「无过滤」显式语义，删除 `set_current_kb_groups` / `kb_permission_context.json` |
| 长期记忆文件 | 记忆混淆/泄露 | `chat()` 加 `user_id` 参数，`_current_user_id()` 读实例属性，删除 `set_current_user` / `memory_user_context.json` |

**核心收获**：代码审查不能只看「功能是否正常」，更要推演「并发边界下的行为」。一个被标记为「设计权衡」的兼容性保留，在并发下可能就是一个越权后门——最终四个问题全部修复/收敛，权限语义回归清晰（None=无过滤，显式=过滤，跨组无泄露）。

**二次审查补充（fail-open → fail-closed）**：收敛文件机制后，又发现 `kb_groups=None` 的默认语义是「不限权限」，未登录用户会拿到全库（fail-open）。修复采用**登录守卫**——app.py 主区域加 `st.stop()` 拦截未登录，把「谁能进来」和「进来后能看什么」两层分离：入口 fail-closed，内部信任入参。权衡见 [部署运维改造.md](部署运维改造.md) 第八章。
