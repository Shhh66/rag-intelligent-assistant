## 一、这个模块是干什么的（认知覆盖）

模型网关层要解决的，是**把不可靠的上游变成可靠的依赖**。上层业务只调一个统一接口，
不关心背后是哪个厂商、哪个 Key、挂了怎么办。它承载 7 件事：

| # | 能力 | 解决什么问题 |
|---|------|-------------|
| 1 | **多模型路由** | 复杂推理/长文本走强模型，简单分类抽取走便宜小模型 → 省钱 |
| 2 | **负载均衡** | 同模型多部署（多 Key / 多区域）摊流量 → 提吞吐、避免单点 |
| 3 | **多 Key 轮转** | 单 Key 有 RPM/TPM 上限，轮转突破上限并隔离故障 |
| 4 | **请求重试** | 瞬时抖动（超时/连接闪断/429/5xx）自动重试 |
| 5 | **主备降级** | 主模型不可用（宕机/限流/上下文超长）→ 自动切备用 |
| 6 | **Token 用量监控** | 按调用点/模型/用户归因成本 → 知道钱花在哪 |
| 7 | **限流** | 保护上游不被打爆；区分"频率限流"与"用量配额" |

> **面试常被追问的区分**：**限流（rate limit）管频率**——每秒/每分钟多少次（RPM/TPM）；
> **配额（quota/budget）管总量**——一天/一月花多少 token 或多少钱。两者经常被混为一谈。

## 二、本项目真实已实现的部分（STAR，可以直言）

### S（情境）

LLM 调用散落在多个模块（决策引擎、技能执行器、检索管线），每个调用点各自 `OpenAI().chat.completions.create(...)`。
问题有三个：**下游故障时每个调用点各自重试、把故障放大**；**没有统一的费率保护**；
**成本无法归因**——只知道总花费，不知道是"意图判断"还是"最终回答"烧的钱。

### T（任务）

把 LLM 调用收口成**统一入口**，让容错与成本能力集中在一处，调用方不感知。

### A（行动）

**① 统一入口 `call_llm_with_cb`**：所有主进程 LLM 调用走它，内部按序串：

```
模型路由挂点 → 熔断检查 → LLM 级限流 → 实际调用 → 记成功/失败 → Token 记账
```

**② 熔断（per-destination 三态状态机）**
- CLOSED / OPEN / HALF_OPEN 三态，连续失败达阈值 → OPEN，快速失败不排队
- **fail-closed**：下游故障必须快速失败（与限流的 fail-open 相反）
- **4xx 客户端错误不计入熔断**——它不是下游故障，是我们的请求有问题，记进去会误熔断

**③ 限流（两层令牌桶，Redis Lua 原子操作）**
- 用户级 `rate:user:{username}`（防单用户刷）+ LLM 调用级 `rate:llm`（保护上游）
- **fail-open**：Redis 挂了就放行，不阻断主链路

**④ 成本归因 `token_tracker`**
- 每次调用带 `call_site` 标签（`decision_engine.*` / `retriever.*` / `memory.*` / `judge.*`）
- 三层统计：**单轮 / 本次会话 / 历史总计**
- 计价区分**缓存命中 vs 未命中**的输入价、以及**峰谷时段**（工作日 9-12、14-18 为峰时）
- 实时落盘 JSONL

**⑤ 单任务 Token 预算**：单次任务累计超上限 → 强制终止并返回中间结果（防多轮 ReAct 循环把 token 打爆）

**⑥ 模型路由挂点**：`route_model(call_site, default_model)` 已实现，按调用点分派模型

**⑦ 工具调用侧的重试**：`mcp_client_manager.call_tool` 用指数退避，**只重试瞬时故障**（超时/连接），业务错误与参数错误立即失败

### R（结果）

- 下游故障时**快速失败**而不是雪崩；4xx 不再误触发熔断
- 成本可按**调用点**归因——能回答"钱花在意图判断还是最终回答"
- 单任务不再可能因多轮循环无限烧 token

### ⚠️ 这一部分的三个诚实边界（被问到一定要主动交代）

| 能力 | 真实状态 | 主动交代的说法 |
|------|---------|--------------|
| **多模型路由** | 机制就位（`route_model` 已接进统一入口），但 `MODEL_ROUTE = {}` → **实际不路由** | "挂点留好了，**没启用**——只有一个模型在跑，路由没有对象" |
| **单任务 Token 预算** | 机制就位（`check_budget`），但 `TASK_TOKEN_BUDGET = 0` → **默认不限** | "代码写了，**默认关着**，因为还没遇到烧爆的场景" |
| **LLM 请求重试** | **没有**。重试只用在**工具调用**路径 | "LLM 调用我没做重试——失败多是确定性的（参数错/余额不足/内容审核），重试没意义，**快速熔断更合适**" |

> 最后一条特别值得展开：**它不是一个缺口，是一个判断**。面试官听到"我没给 LLM 加重试，
> 因为 LLM 失败大多确定性、重试只会浪费配额和时间；重试更适合放在工具调用这种瞬时故障为主的地方"
> ——这比"我做了重试"更显功力。

## 三、标准方案：LiteLLM Proxy（讲设计，**不要说成实现了**）

### 3.1 它是什么

LiteLLM Proxy 是一个**独立的 OpenAI 兼容网关服务**（自托管，也有云版）。
一句话：**上层代码只认 OpenAI 的 `/chat/completions` 协议，换厂商/换 Key/加降级全在网关的配置文件里改，业务代码零改动。**

- 支持 100+ provider（OpenAI / Anthropic / Azure / Bedrock / 通义 / DeepSeek / 本地 vLLM…）
- 对上暴露 OpenAI 协议 → **客户端一行不改**
- 自身是 FastAPI 服务，配置写 `config.yaml`

**为什么它是"标准答案"**：这些能力（多部署负载均衡、fallback、虚拟 Key 配额、成本看板）自己写要几百行且容易漏边界；LiteLLM 是社区事实标准。

### 3.2 逐条能力怎么解（对照第一节的 7 条）

| 能力 | LiteLLM 怎么解 | 关键点 |
|------|---------------|--------|
| **① 多模型路由** | `model_list` 里定义多个 `model_name`，业务按名字调用 | 路由是**业务侧显式选**（调 `gpt-4o` 还是 `cheap-model`）；也可用 `model_alias` 做别名 |
| **② 负载均衡** | **同名 `model_name` 写多条** → 自动在这几个 deployment 间分发 | 这是 LiteLLM 最常用的技巧：同一个对外名字，背后挂多个 Key/区域 |
| **③ 多 Key 轮转** | 两种：<br>a) 多个同名 deployment，各带不同 `api_key`（走负载均衡）<br>b) `api_key: os.environ/K1,os.environ/K2` 逗号分隔 | 配额是**按 Key 算**的，轮转才能突破单 Key 的 RPM/TPM |
| **④ 请求重试** | `num_retries` + `request_timeout`，指数退避 | 只对可重试错误生效（超时/429/5xx） |
| **⑤ 主备降级** | `fallbacks`: `{"主模型": ["备用模型"]}`<br>`context_window_fallbacks`: 上下文超长时切长窗口模型 | 第二条专门解"长文本"——主模型装不下时自动切 |
| **⑥ 用量监控** | `/spend/logs`、`/global/spend`；按 key/team/user 维度 | **聚合需要落库**（Postgres），否则只有进程内数据 |
| **⑦ 限流** | 每个 deployment 配 `rpm`/`tpm`；虚拟 Key 配 `rpm`/`tpm`/`max_parallel_requests` | 部署级 + Key 级两层 |

**额外的两个关键机制**：

- **`allowed_fails` + `cooldown_time`** —— 这**就是熔断**：某 deployment 连续失败 N 次 → 冷却 M 秒不再分发。
  与自研三态熔断的区别：LiteLLM 是**两态 + 定时恢复**；自研版有 HALF_OPEN 探活、更细的失败分类（4xx 不计入）。
- **虚拟 Key（`/key/generate`）** —— 给每个用户/团队发一个虚拟 Key，绑定 `max_budget` + `budget_duration`
  （如"每用户每月 $5"）+ 可用模型白名单。**这是"配额"的正解**，也是自研最麻烦的一块。
- **缓存**：可接 Redis 做精确缓存，或开语义缓存（相似问题命中同一答案）。

### 3.3 配置骨架（面试画出来会很加分）

```yaml
model_list:
  # 同名两条 → 自动负载均衡（多 Key 轮转就靠这个）
  - model_name: chat-model
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_KEY_A
      rpm: 500
  - model_name: chat-model
    litellm_params:
      model: deepseek/deepseek-chat
      api_key: os.environ/DEEPSEEK_KEY_B
      rpm: 500

  # 便宜小模型做简单任务
  - model_name: cheap-model
    litellm_params:
      model: openai/gpt-4o-mini
      api_key: os.environ/OPENAI_KEY

router_settings:
  routing_strategy: simple-shuffle      # 也可 least-busy / latency-based-routing / usage-based-routing
  num_retries: 3
  request_timeout: 30
  allowed_fails: 3                      # 连续失败 3 次
  cooldown_time: 30                     # 冷却 30s（≈熔断）
  fallbacks: [{"chat-model": ["cheap-model"]}]              # 主挂了切备用
  context_window_fallbacks: [{"chat-model": ["long-ctx-model"]}]  # 装不下切长窗口
```

> ⚠️ **参数名以你面试前查的官方文档为准**。LiteLLM 迭代很快，键名会变；
> 上面写的是**结构与思路**，面试讲"有这个配置项"足够，别背具体拼写。

### 3.4 代价与坑（**这部分是你独有的、别人答不出来的**）

LiteLLM 不是免费的，真引入要付：

| 代价 | 说明 |
|------|------|
| **依赖体量大** | `litellm` 本体约 8 个新包；`litellm[proxy]` 约 **35 个新包**（含 boto3/botocore、azure-*、msal、polars、gunicorn、rq、APScheduler…） |
| **会动既有依赖** | 实测 `litellm[proxy]` 会把 `mcp` 升级、把 `rich`/`websockets` **降级**——对以 MCP 为骨架的项目是直接风险 |
| **聚合功能要落库** | 配额/成本看板要 Postgres，单机项目凭空多一个存储组件 |
| **能力重叠** | 它自带 MCP 支持，与自研的 MCP 客户端职责重叠 |
| **自研被架空** | 引入后自己的熔断/限流/成本归因要么删（丢能力）要么双层（复杂） |

## 四、STAR：我评估过 LiteLLM Proxy，结论是暂不引入（真实故事）

> 这一段是**这一节最有价值的内容**——它不是"我做了什么"，而是"**我知道什么时候不该引框架**"。
> 对校招面试官来说，判断力比堆技术更能区分人。

### S（情境）

模型网关做了统一入口 + 熔断 + 限流 + 成本归因之后，我评估要不要**用 LiteLLM Proxy 替换自研部分**——
它能一次性补齐多模型、负载均衡、多 Key、fallback、虚拟 Key 配额。

### T（任务）

判断：**引，还是不引？**

### A（行动）

我没有拍脑袋，而是在**不影响主环境**的前提下实测依赖影响（`pip install --dry-run --report` 精确解析，不安装任何东西）：

| 方案 | 新增包 | 对已有依赖的影响 | 结论 |
|------|:---:|------|------|
| 纯 `litellm`（库） | 8 | 仅 aiohttp 补丁级升级 | ✅ 安全 |
| `litellm[proxy]` | **35** | **`mcp` 升级**、**`rich` 降级**、**`websockets` 降级**、cryptography 大版本升级 | ⚠️ 高风险 |
| 加 `mcp==1.28.0` 钉版本规避 | — | pip 回溯到旧版 litellm **源码包** → 需 Rust 编译 → **装不上** | ❌ 不可行 |

**关键判断**：它会动 `mcp`——而我整个项目的骨架就是 MCP（客户端、工具注册、stdio 子进程）。
为了一个**我当前场景没有对象**的能力（多模型/多 Key/多实例），去动核心依赖，**风险收益完全不匹配**。

顺带发现：`litellm[proxy]` 强依赖 `mcp`，是因为**它自带 MCP 支持**——这与自研的 MCP 客户端**能力重叠**。

### R（结果）

**结论：不引入。** 保留了自研的统一入口 + 熔断 + 限流 + 成本归因；把 LiteLLM 的能力清单和配置思路作为**设计储备**。

**判断依据（一句话）**：三项前提（多模型 / 多 Key / 多实例）在我这里**一项都不成立**，
引入只是徒增 35 个依赖和核心依赖风险，属于"为简历堆技术"。

### 这一段怎么讲（面试话术）

> "模型网关我做过一次**引入评估**。我调研了 LiteLLM Proxy——它能一次性给我多模型路由、
> 负载均衡、多 Key 轮转、fallback 和虚拟 Key 配额，是这块的标准方案。
>
> 但我没有直接引。我先用 `pip install --dry-run` 精确算了依赖影响：**proxy 版会引入 35 个新包，
> 并且会升级我的 `mcp`、降级 `rich` 和 `websockets`**——而我整个项目的骨架就是 MCP。
> 我又试了用版本钉住规避，结果 pip 会回溯到一个需要 Rust 编译的源码包，装不上。
>
> 所以最后的判断是：**这三个能力（多模型、多 Key、多实例）在我当前场景一项都不成立，
> 为它们去动核心依赖，风险收益不匹配**。我把统一入口、熔断、限流、成本归因保持自研——
> 其中三态熔断还是 LiteLLM 没有的（它只有 `allowed_fails` + `cooldown_time` 的两态冷却）。
>
> 我知道怎么做，也评估过成本，结论是**现在不该做**。"

**这段话为什么强**：它同时展示了 ① 知道标准方案 ② 会量化评估（不是感觉）③ 敢做"不引入"的决定 ④ 清楚自己方案的优势边界。

## 五、面试问答（逐条准备）

### Q1：你的模型网关怎么做的？
先讲真实做的（统一入口 → 熔断 → 限流 → 成本归因 → 预算），再主动划边界：
> "**多模型路由和负载均衡的挂点我留了但没启用**——只有一个模型、一个 Key、单实例，这些能力没有对象。"

### Q2：如果要支持多模型路由，你怎么做？
> "两条路。轻的：在统一入口按 `call_site` 映射模型，简单任务走小模型——**这个挂点我已经有了，填配置即生效**。
> 重的：上 LiteLLM Proxy，用 `model_list` 定义模型、业务按名字调用。我倾向先做轻的，因为**路由的价值取决于模型差价**，没有价差就不值得引框架。"

### Q3：主模型挂了怎么自动切备用？
> "LiteLLM 有 `fallbacks` 配主备、`context_window_fallbacks` 配上下文超长时切长窗口模型——**第二种专门解长文本**。
> 我这边没做，因为没有第二个模型可切；我的替代方案是**熔断快速失败**，让上层立刻感知，而不是悄悄换一个模型让结果不可预期。"

### Q4：多 Key 怎么轮转？
> "LiteLLM 里就是**把同一个 `model_name` 写多条、每条带不同 Key**，流量自动分摊，或者 Key 用逗号分隔。
> 核心动机是**突破单 Key 的 RPM/TPM 上限**并隔离单 Key 故障。我没有多 Key 场景。"

### Q5：限流和配额的区别？
> "**限流管频率**（RPM/TPM，防打爆），**配额管总量**（一天/一月多少 token 或多少钱）。
> 我只做了限流——两层令牌桶（用户级 + 模型调用级），配额没做。配额的正解是虚拟 Key 绑定 `max_budget` + `budget_duration`，要落库。"

### Q6：你的熔断和 LiteLLM 的冷却有什么区别？
> "LiteLLM 是 `allowed_fails` + `cooldown_time`——连续失败 N 次、冷却 M 秒，**两态 + 定时恢复**。
> 我的是三态状态机，多了 **HALF_OPEN 探活**（冷却后先放少量请求试探，成功才恢复），
> 而且**把 4xx 排除在失败统计外**——4xx 是我们的请求有问题，不是下游故障，记进去会误熔断。"

### Q7：LLM 调用为什么不加重试？
> "我**故意**没加。LLM 失败大多是**确定性**的：参数错、余额不足、内容审核不通过——
> 重试只会浪费配额和时间。重试我放在**工具调用**路径，因为那边是超时/连接闪断这类瞬时故障为主。
> **分清哪些故障值得重试**，比无脑加重试更重要。"

### Q8：成本怎么归因？
> "每次 LLM 调用带 `call_site` 标签，区分**缓存命中和未命中**的输入价，还按**峰谷时段**计价
> （工作日 9-12、14-18 是峰时）。所以我能回答'钱花在意图判断还是最终回答'。
> 这是我觉得比大多数方案做得细的地方——很多网关只按模型算总账。"

### Q9：为什么不用现成的网关？
→ 用第四节的完整话术。

> 这些都在跑。**多模型、多 Key、负载均衡这些能力我留了挂点没启用**，因为当前场景没有对象；
