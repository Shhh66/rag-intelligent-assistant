# RAG 重排（Reranking）更新计划

## 一、现状分析：当前检索链路的缺口

### 1.1 完整检索链路

```
用户提问
  ↓
retriever.py: answer_with_fallback(query, top_k=8)
  ├─ ① 中文检索  vector_store.search(query, top_k=8)   → ChromaDB 余弦相似度
  ├─ ② 查询翻译  _translate_query_for_search(query)    → LLM 中→英
  ├─ ③ 英文检索  vector_store.search(en_query, top_k=8) → ChromaDB 余弦相似度
  ├─ ④ 合并去重  按 page_content[:120] 去重
  ├─ ⑤ 构建 Prompt  build_prompt(query, merged_docs)
  └─ ⑥ LLM 生成
```

### 1.2 核心问题

**缺少重排环节**。当前④→⑤之间直接取 Top-K 余弦相似度结果就送进 Prompt，存在三个典型问题：

| 问题 | 表现 | 根因 |
|------|------|------|
| **语义漂移** | 相似度排名第 1 的片段可能不如第 5 个相关 | 余弦相似度只衡量向量空间距离，不衡量"真正回答问题"的能力 |
| **双语融合粗糙** | 中英文两个 Top-8 简单合并去重，没有重新统一排名 | 双语检索各自独立打分，尺度不可比，合并后顺序无意义 |
| **噪声放大** | 8+8 条去重后可能仍有 12+ 条无关片段混入 Prompt | 双语检索各自放宽召回，但缺乏精度过滤 |

**业界标准做法**：向量检索（粗排，高召回）→ 重排模型（精排，高精度）→ LLM 生成。本项目缺了中间的精排环节。

| 能力 | 说明 | 优先级 |

| **检索后重排** | 在双语合并去重后、Prompt 构建前，对候选片段做精确相关性排序 | P0 |

## 四、三种重排策略

### 策略 1：本地 Cross-Encoder 重排（推荐，默认）

**模型**：`BAAI/bge-reranker-v2-m3`（多语言，兼容中英文，568MB）

**原理**：Cross-Encoder 将 query 和 document 拼接后送入 Transformer，输出单个相关性分数。比 Bi-Encoder（向量检索）精确得多，但慢得多（不能用于全量召回，只能用于精排）。

**优点**：离线运行、零 API 成本、多语言原生支持、与现有 HuggingFace 模型管理方式一致。

**缺点**：增加 ~570MB 模型下载（首次），单次重排耗时 ~0.3-1s（16 条文档，CPU 半精度）。

**实现**：

```python
# reranker.py (新文件)
from transformers import AutoModelForSequenceClassification, AutoTokenizer
import torch

_model = None
_tokenizer = None

def _get_device():
    """自动适配设备：GPU 优先，CPU 回退"""
    if torch.cuda.is_available():
        return "cuda"
    # Mac MPS 加速
    if hasattr(torch.backends, "mps") and torch.backends.mps.is_available():
        return "mps"
    return "cpu"

def _get_reranker():
    """全局单例，懒加载 BGE-Reranker，首次加载打印提示"""
    global _model, _tokenizer
    if _model is None:
        print("   ⏳ 正在加载重排模型（首次使用需下载 ~570MB，请稍候）...", file=sys.stderr, flush=True)
        device = _get_device()
        _tokenizer = AutoTokenizer.from_pretrained(RERANK_MODEL)
        _model = AutoModelForSequenceClassification.from_pretrained(RERANK_MODEL)

        # CPU 场景自动启用半精度，老 CPU 不支持则回退 fp32
        if device == "cpu":
            try:
                _model = _model.half()  # fp16
                print("   📌 重排模型: CPU 半精度模式", file=sys.stderr, flush=True)
            except Exception:
                print("   📌 重排模型: CPU 全精度模式（设备不支持半精度）", file=sys.stderr, flush=True)
        else:
            _model = _model.to(device)
            print(f"   📌 重排模型: {device.upper()} 加速", file=sys.stderr, flush=True)

        _model.eval()
        print("   ✅ 重排模型加载完成", file=sys.stderr, flush=True)
    return _tokenizer, _model
```

## 五、落地细节优化（7 项，扣 8 分的提升空间）

以下都是真实落地容易踩、但不影响主流程的细节坑，按优先级排序。

### 细节 1：长文本智能截断，避免关键信息丢失导致打分失真

**问题**：设置 `max_length=512` 直接从头截断。但项目中的 chunk 普遍带标题路径 + 正文，很多长 chunk 的核心信息可能在中后段，直接从头截断会丢失关键内容，导致打分不准。

**优化**：

```python
def _smart_truncate(text: str, query: str, max_chars: int = 512) -> str:
    """关键词定位截断：找到 query 关键词在文本中的位置，取前后上下文

    轻量版（先落地）：匹配 query 关键词，定位 → 取前后各 200 字符
    稳妥版（后续增强）：滑动窗口分段打分，取最高分
    """
    if len(text) <= max_chars:
        return text

    # 提取 query 中的关键词（取长度 ≥2 的实词）
    keywords = [w for w in query if len(w) >= 2]

    # 找第一个关键词在文本中的位置
    best_pos = len(text) // 2  # 默认取中间
    for kw in keywords:
        pos = text.find(kw)
        if pos != -1:
            best_pos = pos
            break

    # 以关键词为中心取上下文
    half = max_chars // 2
    start = max(0, best_pos - half)
    end = min(len(text), start + max_chars)
    # 尽量不在词语中间切断
    if start > 0:
        start = text.find(" ", start) + 1 if text.find(" ", start) != -1 else start
    if end < len(text):
        end = text.rfind(" ", 0, end) if text.rfind(" ", 0, end) != -1 else end

    return text[start:end]


def _sliding_window_score(query: str, doc_text: str, tokenizer, model,
                          max_length: int = 512, stride: int = 256) -> float:
    """滑动窗口分段打分，取最高分（稳妥版，处理超长文档）"""
    tokens = tokenizer.encode(doc_text)
    if len(tokens) <= max_length:
        return _compute_pair_score(query, doc_text, tokenizer, model)

    best_score = -999
    for start in range(0, len(tokens) - max_length + 1, stride):
        window = tokenizer.decode(tokens[start:start + max_length])
        score = _compute_pair_score(query, window, tokenizer, model)
        best_score = max(best_score, score)
    return best_score
```

**收益**：轻量版改动量极小（~15 行），匹配关键词取上下文比直接从头截断的相关性判断准很多。

### 细节 2：元数据复用 — 把标题路径喂给重排模型，收益极高

**问题**：当前重排只输入纯正文内容，浪费了 chunk 里已有的 h1/h2/h3 标题层级元数据。标题里的关键词对相关性判断权重极高，不用非常可惜。

**优化**：送重排前，把标题路径拼在正文最前面，格式和分块时保持一致：

```python
def _build_rerank_text(doc) -> str:
    """拼接标题路径 + 正文，让重排模型感知章节主题"""
    parts = []
    for key in ('h1', 'h2', 'h3'):
        val = doc.metadata.get(key, '')
        if val and val != '文档前言':
            parts.append(val)

    if parts:
        header = " > ".join(parts)
        return f"【{header}】{doc.page_content}"
    elif doc.metadata.get('h1') == '文档前言':
        return f"【文档前言】{doc.page_content}"
    return doc.page_content
```

送入重排模型的效果对比：

```
改前: "机器学习是人工智能的核心分支，通过数据训练模型来完成任务..."
改后: "【第一章 概述 > 1.1 机器学习定义】机器学习是人工智能的核心分支..."
```

重排模型能直接感知到章节主题，打分准确率有明显提升，且改动量极小，仅需拼接一行字符串。

### 细节 3：双语打分校准，进一步统一中英文尺度

**问题**：BGE-M3 虽然支持多语言，但实际测试中，同语义强度的中英文片段，中文得分通常会略高于英文，导致中文结果天然靠前，英文优质内容被压后。

**优化**：

```python
def _calibrate_bilingual_scores(docs: list, scores: list) -> list:
    """轻量校准：统计候选集中英文文档的平均得分，拉平基准分"""
    cn_scores = []
    en_scores = []
    cn_indices = []
    en_indices = []

    for i, doc in enumerate(docs):
        text = doc.page_content[:200]
        # 简单启发式：中文字符占比 > 30% 判为中文文档
        cn_chars = sum(1 for c in text if '一' <= c <= '鿿')
        if cn_chars / max(len(text), 1) > 0.3:
            cn_scores.append(scores[i])
            cn_indices.append(i)
        else:
            en_scores.append(scores[i])
            en_indices.append(i)

    if cn_scores and en_scores:
        cn_avg = sum(cn_scores) / len(cn_scores)
        en_avg = sum(en_scores) / len(en_scores)
        # 英文得分略低时，乘校准系数拉平
        if en_avg < cn_avg:
            ratio = cn_avg / max(en_avg, 0.001)
            # 限制校准幅度，避免过度补偿
            ratio = min(ratio, RERANK_CALIBRATION_MAX_RATIO)
            for i in en_indices:
                scores[i] *= ratio

    return scores
```

日志中分别记录中英文的平均得分，方便后续调优校准系数，真正实现"同一尺度下统一排名"。

### 细节 4：性能与内存优化，CPU 场景体验提升明显

**问题**：默认加载 fp32 全精度模型，500+MB 在纯 CPU 环境下推理速度偏慢，老机器可能超过 2s。

**优化**：

| 措施 | 说明 |
|------|------|
| **设备自动适配** | 有 GPU 用 GPU，有 MPS（Mac）用 MPS，都没有用 CPU |
| **CPU 半精度** | CPU 场景默认 `model.half()`（fp16），内存减半，速度提升 30%+，精度几乎无损失 |
| **回退兜底** | 老 CPU 不支持半精度时自动回退 fp32，不报错 |
| **懒加载 + 提示** | 全局单例 + 首次加载打印"正在加载重排模型，首次使用请稍候"，避免用户以为卡住 |
| **预热候选数** | `RERANK_MAX_CANDIDATES` 上限 16，保证单次推理量可控 |

### 细节 5：LLM 重排增强，提升格式稳定性与打分一致性

**问题**：LLM 重排的 Prompt 偏简单，容易出现输出格式不规范、打分标准波动的问题，鲁棒性不足。

**优化**：

**① 从"打分制"改为"排名制"**：让 LLM 直接输出相关性从高到低的文档序号，比 0-10 打分更稳定，避免不同文档打分尺度不一致。

```python
def rerank_llm(query: str, docs: list, top_k: int = 5) -> list:
    """LLM 排名制重排：输出序号而非分数，格式更稳定"""
    prompt = f"""请按与问题的相关性从高到低排列以下文档片段。
只输出 JSON 数组，按相关性降序排列文档序号。不要任何解释。

示例输出: [3, 0, 5, 1, 2]

问题: {query}

"""
    for i, doc in enumerate(docs):
        # 拼接标题路径
        text = _build_rerank_text(doc)
        prompt += f"\n[{i}] {_smart_truncate(text, query, 300)}\n"

    prompt += "\n相关性从高到低排列（只输出 JSON 数组）:"

    # 调用 LLM，带重试和超时降级
    try:
        response = llm_client.chat(prompt, temperature=0.1, timeout=10)
        order = _parse_json_array(response)  # 解析 JSON 数组
        ranked = [docs[i] for i in order if 0 <= i < len(docs)]
        return ranked[:top_k]
    except (Timeout, JSONDecodeError):
        # LLM 超时/格式错误 → 降级到原始顺序
        print("   ⚠️ LLM 重排失败，使用原始排序", file=sys.stderr, flush=True)
        return docs[:top_k]
```

**② 超时降级**：LLM 调用超时/失败时，自动回退到原始序列，不阻塞主流程。

**③ 重试兜底**：JSON 解析失败时重试 1 次，提示 LLM 修正格式。

### 细节 6：按 Token 数动态截断，比固定 Top-K 更合理

**问题**：固定取 Top-5 条送入 Prompt，会出现"5 条很短，上下文浪费"或"5 条太长，超出上下文窗口"的问题。

**优化**：重排后不按条数截断，按总 Token 数截断：

```python
def _truncate_by_tokens(docs: list, max_tokens: int,
                         min_docs: int = 3, max_docs: int = 8) -> list:
    """按 Token 数动态截断，最大化利用上下文窗口

    max_tokens:  总 Token 上限（如 2000，留足空间给 Prompt 模板和 LLM 回答）
    min_docs:    最少保留条数（哪怕超出 max_tokens 也保留）
    max_docs:    最多保留条数（哪怕 Token 还没满也停止）
    """
    result = []
    total = 0
    for doc in docs:
        # 中文约 1 char ≈ 1.5 token，英文约 4 char ≈ 1 token
        text = _build_rerank_text(doc)
        est_tokens = len(text) // 2  # 粗略估算

        if len(result) >= min_docs and total + est_tokens > max_tokens:
            break
        if len(result) >= max_docs:
            break

        result.append(doc)
        total += est_tokens

    return result
```

同时设置最小/最大条数兜底（`min_docs=3`, `max_docs=8`），兼顾质量和稳定性。

**为什么用字符数粗略估算而不是 tokenizer 精确计算？**

刻意为之的工程取舍：重排阶段的截断只是"大概控制上下文长度"，最终 Prompt 构建时还会有二次校验，不需要绝对精确。省去每次截断都做 tokenize 的开销（每条要 encode→decode 一轮），对推理速度影响可忽略，工程性价比极高。中文 `//2`、英文 `//4` 的粗略估算偏差在 20% 以内，足够控制数量级。

### 细节 7：增加低分过滤，进一步减少噪声

**问题**：重排只做排序，哪怕最后一条完全不相关，也会被送进 Prompt，干扰 LLM 生成。

**优化**：增加可配置的 `RERANK_MIN_SCORE` 阈值：

```python
def _filter_low_score(docs: list, scores: list, min_score: float) -> list:
    """过滤低分片段：得分低于阈值的直接丢弃，哪怕没凑够 Top-K 也不强行凑数"""
    filtered = [(d, s) for d, s in zip(docs, scores) if s >= min_score]
    # 至少保留 1 条，避免空结果
    if not filtered:
        best_idx = scores.index(max(scores))
        return [docs[best_idx]]
    return [d for d, _ in filtered]
```

收益：Prompt 里的无效噪声更少，LLM 回答的准确率和抗干扰能力都会提升。

**阈值调优小技巧**：BGE-Reranker 输出的是 logits 分值，不是 0-1 概率，不同数据集、不同语言的分数基线会有差异。建议：

1. 初期默认 `RERANK_MIN_SCORE=0.0`（不过滤），先跑一段时间
2. 从日志里统计所有候选的得分分布：平均分、最低分、各百分位
3. 取第 20~30 百分位的分数作为截断点比较合理
4. 文档中标注的 `-2.0 ~ 2.0` 区间是合理初始范围，配合日志逐步调整，不用追求一步到位

import sys
import torch
from transformers import AutoModelForSequenceClassification, AutoTokenizer
from config import (
    RERANK_ENABLED, RERANK_STRATEGY, RERANK_TOP_K,
    RERANK_MAX_CANDIDATES, RERANK_MODEL,
    RERANK_MAX_TOKENS, RERANK_MIN_SCORE, RERANK_CALIBRATION_MAX_RATIO,

_model = None
_tokenizer = None
_device = None


def _get_device():
    global _device
    if _device is None:
        if torch.cuda.is_available():
            _device = "cuda"
        elif hasattr(torch.backends, "mps") and torch.backends.mps.is_available():
            _device = "mps"
        else:
            _device = "cpu"
    return _device


def _get_reranker():
    global _model, _tokenizer
    if _model is None:
        print("   ⏳ 正在加载重排模型（首次使用需下载 ~570MB，请稍候）...",
              file=sys.stderr, flush=True)
        _tokenizer = AutoTokenizer.from_pretrained(RERANK_MODEL)
        _model = AutoModelForSequenceClassification.from_pretrained(RERANK_MODEL)

        device = _get_device()
        if device == "cpu":
            try:
                _model = _model.half()
                print("   📌 重排模型: CPU 半精度", file=sys.stderr, flush=True)
            except Exception:
                print("   📌 重排模型: CPU 全精度（设备不支持半精度）",
                      file=sys.stderr, flush=True)
        else:
            _model = _model.to(device)
            print(f"   📌 重排模型: {device.upper()} 加速", file=sys.stderr, flush=True)

        _model.eval()
        print("   ✅ 重排模型加载完成", file=sys.stderr, flush=True)
    return _tokenizer, _model


def _build_rerank_text(doc) -> str:
    """拼接标题路径 + 正文"""
    parts = [doc.metadata.get(k, '') for k in ('h1', 'h2', 'h3')
             if doc.metadata.get(k) and doc.metadata[k] != '文档前言']
    header = " > ".join(parts)
    if doc.metadata.get('h1') == '文档前言' and not header:
        header = "文档前言"
    return f"【{header}】{doc.page_content}" if header else doc.page_content


def _smart_truncate(text: str, query: str, max_chars: int = 512) -> str:
    """关键词定位截断"""
    if len(text) <= max_chars:
        return text
    # 取 query 中长度 ≥2 的字符作为关键词
    keywords = [query[i:i+2] for i in range(len(query) - 1)]
    best_pos = len(text) // 2
    for kw in keywords:
        pos = text.find(kw)
        if pos != -1:
            best_pos = pos
            break
    half = max_chars // 2
    start = max(0, best_pos - half)
    end = min(len(text), start + max_chars)
    return text[start:end]


def rerank_cross_encoder(query: str, docs: list, top_k: int = 5) -> list:
    """BGE-Reranker 精排"""
    if len(docs) <= 1:
        return docs

    tokenizer, model = _get_reranker()
    device = _get_device()

    # 拼接标题路径 + 智能截断
    texts = [_smart_truncate(_build_rerank_text(d), query) for d in docs]
    pairs = [[query, t] for t in texts]

    with torch.no_grad():
        inputs = tokenizer(pairs, padding=True, truncation=True,
                          max_length=512, return_tensors="pt")
        if device != "cpu":
            inputs = {k: v.to(device) for k, v in inputs.items()}
        scores = model(**inputs, return_dict=True).logits.view(-1).cpu().tolist()

    # 双语校准
    scores = _calibrate_bilingual_scores(docs, scores)

    # 按分数降序
    ranked = sorted(zip(docs, scores), key=lambda x: x[1], reverse=True)

    # 低分过滤
    if RERANK_MIN_SCORE > 0:
        ranked = [(d, s) for d, s in ranked if s >= RERANK_MIN_SCORE]

    # 日志
    _log_rerank_result(ranked, docs)

    return [d for d, _ in ranked]


def _calibrate_bilingual_scores(docs: list, scores: list) -> list:
    """中英文得分校准"""
    cn_idx, en_idx = [], []
    for i, doc in enumerate(docs):
        text = doc.page_content[:200]
        cn_count = sum(1 for c in text if '一' <= c <= '鿿')
        (cn_idx if cn_count / max(len(text), 1) > 0.3 else en_idx).append(i)

    if cn_idx and en_idx:
        cn_avg = sum(scores[i] for i in cn_idx) / len(cn_idx)
        en_avg = sum(scores[i] for i in en_idx) / len(en_idx)
        if en_avg < cn_avg:
            ratio = min(cn_avg / max(en_avg, 0.001), RERANK_CALIBRATION_MAX_RATIO)
            for i in en_idx:
                scores[i] = min(scores[i] * ratio, max(scores))
    return scores


def rerank_llm(query: str, docs: list, top_k: int = 5) -> list:
    """LLM 排名制重排（兜底策略）"""
    import json
    from config import LLM_MODEL, GROQ_BASE_URL, GROQ_API_KEY
    from openai import OpenAI

    if len(docs) <= 1:
        return docs

    prompt = "请按与问题的相关性从高到低排列以下文档片段。\n"
    prompt += "只输出 JSON 数组，按相关性降序列出文档序号。不要任何解释。\n\n"
    prompt += f"示例输出: [3, 0, 5, 1, 2]\n\n问题: {query}\n\n"

    for i, doc in enumerate(docs):
        text = _smart_truncate(_build_rerank_text(doc), query, 300)
        prompt += f"[{i}] {text}\n\n"

    prompt += "相关性从高到低排列（只输出 JSON 数组）:"

    try:
        client = OpenAI(base_url=GROQ_BASE_URL, api_key=GROQ_API_KEY, timeout=10)
        response = client.chat.completions.create(
            model=LLM_MODEL,
            messages=[{"role": "user", "content": prompt}],
            temperature=0.1,
            max_tokens=200,
        )
        content = response.choices[0].message.content.strip()
        # 提取 JSON 数组
        import re
        match = re.search(r'\[[\d,\s]+\]', content)
        if match:
            order = json.loads(match.group())
            ranked = [docs[i] for i in order if 0 <= i < len(docs)]
            return ranked[:top_k]
    except Exception as e:
        print(f"   ⚠️ LLM 重排失败 ({e})，使用原始排序", file=sys.stderr, flush=True)

    return docs[:top_k]


def _log_rerank_result(ranked: list, original: list):
    """输出重排日志：排名变化"""
    print(f"   📊 重排: {len(original)}条候选 → {len(ranked)}条精选",
          file=sys.stderr, flush=True)
    for new_rank, (doc, score) in enumerate(ranked[:5]):
        try:
            old_rank = original.index(doc) + 1
        except ValueError:
            old_rank = "NEW"
        change = f"↑{old_rank - new_rank - 1}" if isinstance(old_rank, int) and old_rank > new_rank + 1 \
            else f"↓{new_rank + 1 - old_rank}" if isinstance(old_rank, int) and old_rank < new_rank + 1 \
            else "NEW" if old_rank == "NEW" else "—"
        preview = doc.page_content[:60].replace("\n", " ")
        print(f"   [{new_rank+1}] 得分{score:.2f} {change:<4} {preview}...",
              file=sys.stderr, flush=True)


def _truncate_by_tokens(docs: list, max_tokens: int,
                         min_docs: int = 3, max_docs: int = 8) -> list:
    """按 Token 数动态截断"""
    result = []
    total = 0
    for doc in docs:
        est = len(_build_rerank_text(doc)) // 2
        if len(result) >= min_docs and total + est > max_tokens:
            break
        if len(result) >= max_docs:
            break
        result.append(doc)
        total += est
    return result


def rerank(query: str, docs: list) -> list:
    """重排统一入口：策略分发 + 截断

    Args:
        query: 用户问题
        docs: 合并去重后的候选文档列表

    Returns:
        重排 + 截断后的文档列表
    """
    if not RERANK_ENABLED or len(docs) <= 1:
        return docs

    # 候选数上限
    if len(docs) > RERANK_MAX_CANDIDATES:
        docs = docs[:RERANK_MAX_CANDIDATES]

    # 策略分发
    if RERANK_STRATEGY == "cross-encoder":
        try:
            ranked = rerank_cross_encoder(query, docs)
        except Exception as e:
            print(f"   ⚠️ Cross-Encoder 重排失败 ({e})，降级 LLM 重排",
                  file=sys.stderr, flush=True)
            try:
                ranked = rerank_llm(query, docs)
            except Exception:
                print("   ⚠️ LLM 重排也失败，使用原始排序", file=sys.stderr, flush=True)
                ranked = docs
    elif RERANK_STRATEGY == "llm":
        ranked = rerank_llm(query, docs)
    else:
        ranked = docs

    # 动态 Token 截断
    return _truncate_by_tokens(ranked, RERANK_MAX_TOKENS)
```

### 1. 重排得分写入元数据，延伸价值超出预期

**问题**：当前重排只做排序，没有把相关性得分保留下来，下游无法利用这些信息。

**优化**：把 `rerank_score`、`rerank_rank` 两个字段追加到 chunk 的 metadata 中：

```

**收益**（不止是展示优化，更是架构层面的价值）：

| 场景 | 价值 |
|------|------|
| **混合召回融合** | 后续新增 BM25 关键词检索做多路召回时，用重排得分做统一加权融合，不用额外训练融合模型 |

| **知识库质量诊断** | 长期统计得分分布，反向判断知识库质量、嵌入模型匹配度——非常有价值的埋点数据 |
| **用户可感知** | 检索返回时展示相关性得分，用户直观感知片段匹配度 |

### 2. 智能截断增加兜底策略，极端场景更稳

**问题**：当前关键词定位截断，遇到 query 关键词完全不在文本中的极端情况，会默认取中间位置，可能截掉正文开头的重要信息。

**优化**：补充一层轻量兜底链：

```python
def _smart_truncate(text: str, query: str, max_chars: int = 512) -> str:
    if len(text) <= max_chars:
        return text

    # 策略1: 关键词定位
    keywords = [query[i:i+2] for i in range(len(query) - 1)]
    best_pos = None
    for kw in keywords:
        pos = text.find(kw)
        if pos != -1:
            best_pos = pos
            break

    if best_pos is None:
        # 策略2: 兜底—优先保留标题 + 正文前半段（chunk 核心信息通常靠前）
        # 如果文本以【开头（含标题路径），保留完整标题 + 正文前段
        if text.startswith("【"):
            header_end = text.find("】", 0, 200)
            if header_end > 0:
                header = text[:header_end + 1]
                body_start = min(len(text), max_chars - len(header))
                return header + text[header_end + 1:body_start]
        # 纯正文：直接取前半段
        return text[:max_chars]
    else:
        # 策略3: 关键词定位（当前逻辑）
        half = max_chars // 2
        start = max(0, best_pos - half)
        end = min(len(text), start + max_chars)
        return text[start:end]
```

层级清晰：关键词命中 → 标题+前半段兜底 → 纯截断保底，极端场景不翻车。

### 3. 双语校准增加白名单，避免混排文档误判

**问题**：当前用「中文字符占比 > 30%」判断中文文档，对于全英文专有名词、代码片段较多的文档可能误判。

**优化**：补充辅助规则，增强语言判断鲁棒性：

```python
def _is_chinese_doc(text: str) -> bool:
    """综合判断中文文档（避免中英混排误判）"""
    cn_chars = sum(1 for c in text if '一' <= c <= '鿿')
    total = max(len(text), 1)
    cn_ratio = cn_chars / total

    # 中文占比 > 30% → 直接判定中文
    if cn_ratio > 0.3:
        return True

    # 英文单词数 + 代码符号占比 → 辅助判定
    import re
    en_words = len(re.findall(r'[a-zA-Z]{3,}', text))
    code_symbols = sum(1 for c in text if c in '{}[]();<>=+-*/|&^%$#@!~`')
    code_ratio = code_symbols / total

    # 英文单词多 + 代码符号多 + 中文少 → 判定英文文档
    if en_words > 5 and code_ratio > 0.1 and cn_ratio < 0.1:
        return False

    # 边缘情况：默认按中文处理（宁可少校准，不过度补偿）
    return cn_ratio > 0.1
```

校准系数本身是可配置的兜底，不用追求 100% 准确，大体拉平尺度即可。

### 4. 增加短期 Query 缓存，重复查询提速

**问题**：用户连续追问、重复提问时，每次都重新推理，浪费计算。

**优化**：极轻量的内存缓存，以「query 哈希 + 候选集哈希」为 key：

```python
import hashlib
import time

_cache = {}           # {key: (result, expire_time)}
_cache_ttl = 600       # 10 分钟有效期

def _cache_key(query: str, docs: list) -> str:
    """query + 候选集内容 → 哈希"""
    h = hashlib.md5(query.encode())
    for doc in docs:
        h.update(doc.page_content[:80].encode())
    return h.hexdigest()

def _cache_get(key: str) -> list | None:
    entry = _cache.get(key)
    if entry and time.time() < entry[1]:
        return entry[0]
    return None

def _cache_set(key: str, result: list):
    _cache[key] = (result, time.time() + _cache_ttl)
    # 缓存条数上限 50，超出清理最早条目
    if len(_cache) > 50:
        oldest = min(_cache.items(), key=lambda x: x[1][1])
        del _cache[oldest[0]]
```

对话场景体验提升明显，开发量极小（~25 行），缓存命中时零延迟。

### 5. 批量推理的异常隔离

**问题**：当前一次性把所有候选送入模型推理，如果某一条文本格式异常导致推理报错，会连累整批。

**优化**：加一层 try/except 单条兜底：

```python
def _compute_pair_score(query: str, doc_text: str, tokenizer, model,
                         device: str = "cpu") -> float:
    """单条打分 + 异常隔离"""
    try:
        inputs = tokenizer([query], [doc_text], padding=True, truncation=True,
                          max_length=512, return_tensors="pt")
        if device != "cpu":
            inputs = {k: v.to(device) for k, v in inputs.items()}
        with torch.no_grad():
            score = model(**inputs, return_dict=True).logits.view(-1).item()
        return score
    except Exception:
        return -999.0  # 异常片段给最低分，不影响整体排序
```

在 `rerank_cross_encoder` 中改为循环调用 `_compute_pair_score`，批量推理失败时自动降级为循环单条打分：

```python
# 先尝试批量推理
try:
    scores = model(**inputs, return_dict=True).logits.view(-1).cpu().tolist()
except Exception:
    # 批量失败 → 降级循环单条
    print("   ⚠️ 批量推理失败，降级循环单条打分", file=sys.stderr, flush=True)
    scores = [_compute_pair_score(query, t, tokenizer, model, device) for t in texts]
```

进一步降低极端异常数据导致的整体失效概率。

## 十一、技术决策与面试话术

### 为什么选 BGE-Reranker-v2-m3 而非 Cohere Rerank API？

1. BGE 多语言版原生支持中英文，与现有 `paraphrase-multilingual-MiniLM-L12-v2` 嵌入模型互补（粗排+精排）
2. 零 API 成本，离线运行，不增加外部依赖
3. 与现有 HuggingFace 模型管理方式一致，架构统一

### 为什么不直接在向量检索阶段提高 Top-K 然后用 LLM 过滤？

这正是重排要做的事。区别在于：
- **Cross-Encoder 做精排**：专门训练的判别模型，一对 (query, doc) 打分，精度高、成本低
- **LLM 做精排**：生成模型做判别任务，延迟高、成本高、但理解能力强

两者互补：Cross-Encoder 默认，LLM 做兜底。

### 为什么不是 RRF（Reciprocal Rank Fusion）？

RRF 只是把两个排名字段融合，不解决"余弦相似度本身不准确"的问题。真正的精排需要一个更精确的打分器（Cross-Encoder），而不是对不准的分数做算术。

### 为什么用标题路径拼接而非独立特征？

重排模型的输入是一个文本对 (query, doc)，不支持多特征输入。把标题拼接在正文前是最简单有效的方式——模型本身有位置编码，Transformer 能学会区分标题和正文的权重差异。

## 十二、已发现 Bug：只排序不截断

### 问题

用户通过 `debug_rerank` 工具发现：初召回 6 条 → 重排后还是 6 条，排名变了但**数量没变**。

预期行为：重排 = 打分排序 + **精选截断**，初召回 6 条 → 重排后应该 ≤5 条（`RERANK_TOP_K=5`）。

### 根因

配置了 `RERANK_TOP_K=5`，但它从未真正参与截断逻辑：

```
rerank_cross_encoder()        ← 返回全部排序后的 docs，不截断
    ↓
_truncate_by_tokens(max_docs=8)  ← 6 条 < 8，不触发
    ↓
RERANK_MIN_SCORE=0.0          ← 关闭了低分过滤
    ↓
结果: 6 进 6 出，只排序不截断 ❌
```

具体三处断裂：

| 位置 | 问题 |
|------|------|
| `rerank_cross_encoder()` L506 | `sorted()` 后直接返回全部，没有 `[:RERANK_TOP_K]` |
| `rerank()` L645 | `_truncate_by_tokens(ranked, RERANK_MAX_TOKENS)` 第三个参数 `max_docs` 默认值 8，未传入 `RERANK_TOP_K` |
| `config.py` | `RERANK_MIN_SCORE=0.0` 语义模糊（0 是关闭还是阈值？），没有明确表示"不过滤" |

### 修复方案

**三处改动**：

**1. `reranker.py` `rerank_cross_encoder()` — 排序后立即按 TOP_K 截断**

```python
# 修改前
ranked = sorted(zip(docs, scores), key=lambda x: x[1], reverse=True)

# 修改后
ranked = sorted(zip(docs, scores), key=lambda x: x[1], reverse=True)
ranked = ranked[:RERANK_TOP_K]  # 硬截断：只留 Top N 条
```

**2. `reranker.py` `rerank()` — 把 `_truncate_by_tokens` 的 `max_docs` 绑定到 `RERANK_TOP_K`**

```python
# 修改前
return _truncate_by_tokens(ranked, RERANK_MAX_TOKENS)

# 修改后
return _truncate_by_tokens(ranked, RERANK_MAX_TOKENS,
                           min_docs=min(3, len(ranked)),
                           max_docs=RERANK_TOP_K)
```

**3. `config.py` — 明确 `RERANK_MIN_SCORE` 默认值语义**

```python
# 修改前
RERANK_MIN_SCORE = 0.0   # 0 表示不过滤（但 0 在 BGE logits 中可能恰好是低分区边界）

# 修改后
RERANK_MIN_SCORE = -999.0  # -999 明确表示"不过滤"，> -999 才启用低分过滤
```

对应 `rerank_cross_encoder()` 中的条件也要改：

```python
# 修改前
if RERANK_MIN_SCORE > 0:
    ranked = [(d, s) for d, s in ranked if s >= RERANK_MIN_SCORE]

# 修改后
if RERANK_MIN_SCORE > -100:  # 仅在显式设置了合理阈值时启用
    ranked = [(d, s) for d, s in ranked if s >= RERANK_MIN_SCORE]
```

### 修复后效果

```
初召回: 6 条 → 打分 → Top5 截断 → 重排后: 5 条
📊 统计: 初召回 6 条 → 重排后 5 条 → 压缩比 5/6 (83%)
```

### 涉及文件

| 文件 | 改动 | 行数 |
|------|------|------|
| `reranker.py` `rerank_cross_encoder()` | 排序后加 `ranked = ranked[:RERANK_TOP_K]` | +1 |
| `reranker.py` `rerank()` | `_truncate_by_tokens` 传入 `max_docs=RERANK_TOP_K` | ~3 |
| `reranker.py` `rerank_cross_encoder()` | 低分过滤条件改为 `> -100` | ~1 |
| `config.py` | `RERANK_MIN_SCORE` 默认改为 `-999.0` | ~1 |

## 十四、未来进阶计划：混合检索（BM25 + 向量 双通道）

> **现状定位**：召回侧目前是**纯向量单通道**（`vector_store.similarity_search`），所谓"双语检索"只是"中文原 query + LLM 译出的英文关键词"各跑一次**同一个向量检索器**，再按内容前缀去重合并——**两路都是稠密向量检索**，缺一路**稀疏/关键词检索**。重排（BGE Cross-Encoder）已完整落地，但**只能对召回结果精排，救不回"根本没被召回"的文档**。

### 14.1 为什么需要 BM25 关键词通道

向量检索（稠密）与 BM25（稀疏）各有盲区，**互补性极强**：

| 场景 | 纯向量检索 | BM25 关键词 |
|------|-----------|-------------|
| 精确术语 / 型号 / 缩写（如 "ISAC"、"RIS"、"M/M/1"、"2322030519"） | ❌ 易被语义泛化冲淡 | ✅ 精确命中 |
| 罕见专有名词 / 数字 / 代码标识 | ❌ 训练不足，向量不准 | ✅ 字面匹配 |
| 同义改写 / 口语化模糊提问 | ✅ 语义泛化强 | ❌ 关键词对不上 |
| 跨语言（中问英答） | ✅ 多语言嵌入 | ❌ 字面不通 |

**结论**：关键词精确匹配是向量检索的最大盲区，而这正是简历/技术文档类知识库（充斥术语、型号、编号）最需要的能力。补上 BM25 通道能显著提升**召回全面性**（对应 RAGAS `context_recall`）。

### 14.2 目标链路

```
        ┌─ 向量检索（Chroma，稠密）──┐
query ──┤                          ├─→ RRF 融合 → 候选集 → BGE Cross-Encoder 精排 → Top-K → LLM
        └─ BM25 检索（稀疏，关键词）─┘
```

**关键澄清（呼应第十一章"为什么不是 RRF"）**：本项目对 RRF 的定位与第十一章**不矛盾，而是分工**：
- **RRF 用于"融合两路召回"**（BM25 排名 + 向量排名）——它只需要"排名"不需要"可比的绝对分数"，正好回避了"BM25 分数与余弦分数不可直接相加"的问题。
- **RRF 之后仍由 BGE Cross-Encoder 做最终精排**——解决"余弦/BM25 分数本身不够准"的问题。

即：**RRF 负责"把两路合成一路候选"，Cross-Encoder 负责"精排"**，两者各司其职，不是二选一。

### 14.3 落地设计（增量，不改重排逻辑）

1. **依赖**：`requirements.txt` 增加 `rank_bm25`（轻量纯 Python，无重模型，符合 D 盘/离线约束）。
2. **BM25 索引**：新建 `bm25_index.py`：
   - 从 ChromaDB 或 `db_meta.json` 拉全量 chunk 文本，中文用 `jieba` 分词、英文按空格，构建 `BM25Okapi` 索引。
   - **索引与 Chroma 同源**：在 `vector_store` 增删改（`add_document`/`remove`）后同步重建/更新 BM25 索引，避免两侧不一致（复用现有 `filelock` 并发控制）。
   - 索引可持久化到本地文件（如 `bm25_index.pkl`），启动时加载，避免每次全量重建。
3. **融合检索**：新建 `hybrid_retriever.py` 或在 [retriever.py](rag_assistant/retriever.py) 增 `hybrid_search(query, top_k)`：
   - 并行取 BM25 Top-N 与向量 Top-N；
   - **RRF 融合**：`score(d) = Σ 1/(k + rank_i(d))`（`k≈60` 经验值，写入 `config.py`）；
   - 输出融合后的候选集，**直接接现有 `rerank()`**（重排层零改动）。
4. **接入点**：`retrieve_and_answer` / `answer_with_fallback` 把当前的 `search()` 替换/增补为 `hybrid_search()`，用开关 `HYBRID_ENABLED` 控制，默认可关，兼容现状。

### 14.4 配置项设计

```python
# config.py 新增

BM25_TOP_K = 10                # BM25 单路召回数
VECTOR_TOP_K = 10              # 向量单路召回数
RRF_K = 60                     # RRF 融合常数（经验值，越大越平滑）
BM25_RRF_WEIGHT = 1.0          # BM25 路 RRF 权重（预留，默认对等，后续可加权）
VECTOR_RRF_WEIGHT = 1.0        # 向量路 RRF 权重（预留，默认对等）

BM25_STOPWORDS_PATH = "./bm25_stopwords.txt"  # 中文停用词表（可选）
```

### 14.5 与评测体系联动验证

混合检索的价值必须用数据证明，正好复用已落地的 RAGAS 评测（见 `RAG评测体系.md`）：
- 新增 A/B 配置：`纯向量` vs `混合检索(BM25+向量+RRF)`，其余（双语、重排）保持一致。
- 核心看 **`context_recall`（召回全面性）** 与 **`context_precision`**：预期 BM25 通道对"术语/编号/精确匹配"类问题的召回率显著提升。
- 测试集里的 `simple_fact`（含"小蓝身高体重""学号"等精确字面题）与 `cross_lingual` 分层，最能体现 BM25 的增益差异。

### 14.6 优先级与代价

- **收益**：召回全面性提升，是"混合检索"这一高频面试考点的硬落地；改动集中在**召回侧**，重排/生成侧零改动。
- **代价**：需维护 BM25 索引与 Chroma 的**一致性**（增删改同步）；中文分词质量（jieba）影响 BM25 效果。
- **建议**：作为召回侧头号进阶项优先实现——改动可控、与现有重排天然衔接、评测体系可直接量化收益。

### 14.7 低成本优化补充（锦上添花，优先级不高）

以下四项是对混合检索的增强，按"性价比 / 何时做"排序，不影响主链路先行落地。

**① BM25 中文停用词过滤（成本极低，收益明显，随主功能一起做）**
jieba 分词后过滤掉「的、是、了、在、和」等无意义虚词，避免高频虚词稀释 BM25 打分、干扰关键词匹配精度。做法:网上取通用中文停用词表(几十~几百行)存为 `bm25_stopwords.txt`(配置项 `BM25_STOPWORDS_PATH` 已预留)，分词后 `[w for w in tokens if w not in stopwords]`。几乎零开发成本，直接提升关键词匹配精准度，建议随 BM25 通道一起落地。

**② RRF 融合权重可配置（预留接口，暂不调优）**
当前 RRF 两路权重对等，已在 14.4 预留 `BM25_RRF_WEIGHT` / `VECTOR_RRF_WEIGHT`。融合公式扩展为加权形式:
```
score(d) = BM25_RRF_WEIGHT × 1/(k+rank_bm25(d)) + VECTOR_RRF_WEIGHT × 1/(k+rank_vec(d))
```
默认都为 1.0(对等)。**现在只需按此公式实现、不必调参**；后续若发现技术文档场景 BM25 贡献更大，直接改配置加权即可，无需改代码。

**③ 双语 × BM25 四路融合（P2，后续扩展）**
现有双语检索是"中文 query + 英文译 query"各跑一次**向量**检索。后续可让 **BM25 也跑中英两路**，与向量的双语两路合计**四路一起 RRF 融合**，进一步提升跨语言召回。属 P2 级——**当前先做单语(中文)BM25 就足够**，四路融合待跨语言需求明确后再扩展。

**④ BM25 索引增量更新（规模上来再做）**
当前设计是增删改后**全量重建** BM25 索引，文档量少(几十~上百篇)时完全够用。若知识库增长到**上千篇**，全量重建变慢，可改为增量更新:新增文档直接追加进 `BM25Okapi` 语料、删除时按 chunk_id 移除，避免全量重建。属"规模驱动"的优化——**先做全量重建，规模真正上来了再考虑**。

**小结**:①随主功能做(顺手)、②实现时按加权公式写好留配置(不调参)、③④明确标注为后续/规模驱动的扩展项，避免过早优化。
