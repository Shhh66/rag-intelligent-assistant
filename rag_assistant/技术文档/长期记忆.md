> **实现状态（2026-09）**：✅ **V1.1 已实现并验证**（第九节：会话摘要压缩 + 实体 ID/权重改造 + 摘要驱动的长期抽取），103 项自动化测试全通过（33 + 39 + 31）。
> **实现状态（2026-09 增补）**：✅ **反思记忆已移除 + 沉淀判据改造**（9.11 节：实测收益不成立故整体移除；沉淀改读审计日志 + 计数/占比双条件 + 幂等写入），23 项测试通过。**注意：记忆体系现为「会话摘要 + 长期记忆」两层，不再是三层。**
> 定位：真补强——现有记忆是纯内存、重启即丢，补上"跨会话持久化 + 实体记忆检索"能让 Agent 记住用户是谁、聊过什么。

## 已实现部分（本轮）

- **核心模块** `long_term_memory.py`：Chroma（语义召回，独立 `memory` collection）+ SQLite（`memory.db` 结构化镜像）双写；复用 `vector_store.get_embeddings()`，无新依赖。
- **实体抽取**：`extract_and_store` 每轮对话后 LLM 抽取 `{mem_type(profile/entity/conclusion), content, confidence}`（`max_tokens=512` 避推理模型空返回坑）；抽取为空时兜底存一句摘要（V0.5）。
- **检索注入**：`retrieve` 按 user_id 过滤 + query 语义检索 + **权重排序**（相关度 `1/(1+距离)` × 类型权重 × 置信度 × 时间衰减）；结果与 reflection hints **并列注入** `_pipeline` 决策 prompt。
- **用户隔离**：`retriever.set_current_user()` 写共享文件 `memory_user_context.json`（仿 kb 权限模式），跨进程按 username 隔离，防串户。实测 bob 检索不到 alice 记忆。
- **去重更新**：抽取前语义查最近似记忆，相似度 ≥ `MEMORY_DEDUP_SIM` 则覆盖旧值+刷新时间戳，避免膨胀。
- **短→长沉淀闭环**：`_maybe_sediment_preference` 复用 reflection 的 `selected_tool`，某工具成功用满 3 次自动沉淀"用户偏好优先用 XX 工具"，**无需额外 LLM**。
- **Prompt 护栏**：注入时加"仅参考相关长期记忆，无关忽略"降幻觉。
- **降级安全**：`LONG_TERM_MEMORY_ENABLED=False`/DB异常/抽取失败 全静默跳过，不阻断主对话。
- **距离分陷阱**：本地嵌入的 `relevance_scores` 会返回负值（同 reranker logits 问题），改用 `similarity_search_with_score` 距离分转 `1/(1+dist)`。
- ✅ 验证：进程A（alice 说"在做6G无人机ISAC项目"）→ 重启进程B → alice 问"物理层安全和我研究方向的关系"→ 答案自动带项目背景（跨会话记忆生效）。

## 一、现状分析

| 记忆类型 | 现状 | 证据 |
|---------|------|------|
| 工具选型记忆 | 内存 `deque(maxlen=50)`，**重启即丢**（该模块已于 2026-09 移除，见 9.11） | `reflection_memory.py::ReflectionMemory`，字符 bigram Jaccard 召回 |
| 对话历史 | 实例属性 `_history`，**重启即丢** | `unified_agent.py` `self._history`（上限 20 条） |
| 跨会话记忆 | **无** | 进程重启后一切归零；无用户画像、无历史实体沉淀 |
| 持久化 | **无** | 两者都在内存，`clear_memory()` 一调即空 |

**核心缺口**：Agent 是"金鱼记忆"——每次重启、每个新会话都从零开始。用户上次说过"我在做 6G 无人机项目"，这次问"我的项目相关的物理层安全"时，Agent 无法关联。缺一个**跨会话、可检索、结构化**的长期记忆层。

---

## 二、目标能力

1. **跨会话持久化**：记忆落盘，进程重启/新会话仍可用。
2. **实体记忆**：从对话中抽取关键实体/事实（用户偏好、项目背景、历史结论），结构化存储。
3. **记忆检索**：新对话开始时，按当前 query 检索相关长期记忆，注入上下文，让回答带"记性"。
4. **分层不冲突**：短期记忆（现有易失 reflection/history）负责"本次会话连贯"，长期记忆负责"跨会话积累"，各司其职。

## 三、落地设计（引用现有代码）

### 3.1 存储层（复用现有基础设施）

两种复用路线，二选一：
- **路线 A（向量检索，推荐）**：复用现有 **ChromaDB + 嵌入模型**（`vector_store.get_embeddings()`），长期记忆作为独立 collection（如 `memory`），支持语义检索"相关记忆"。天然复用现有向量栈。
- **路线 B（结构化，SQLite）**：复用 `permission.db` 或新建 `memory.db`，按 `user_id / entity / value / timestamp` 存，适合精确键值型记忆（用户画像）。

建议：**A+B 混合**——实体事实存 SQLite（可精确查/更新），记忆的自然语言描述存 Chroma（可语义召回）。

### 3.2 记忆抽取

- **新建 `long_term_memory.py`**：`extract_entities(dialogue) -> list[MemoryItem]`，用 LLM 从一轮/多轮对话抽取值得长期记住的实体与事实（用户身份、项目、偏好、已确认结论）。
- 抽取时机：一次 `chat()` 结束后异步抽取（不阻塞回答），或达到 N 轮时批量抽取。
- **注意推理模型 max_tokens 陷阱**：`LLM_MODEL=deepseek-flash` 是推理模型，抽取调用须给足 `max_tokens`（≥512），否则 content 空（本项目已踩过此坑，见 CLAUDE.md）。

### 3.3 记忆检索与注入

- **新建 `retrieve_memory(query, user_id) -> list[str]`**：会话开始时按 query 语义检索 Top-K 长期记忆。
- **注入点**：`unified_agent.py::_pipeline()` 构造 prompt 时，与现有 `reflection` hints 并列注入（`prompt_templates.py`），格式如 `[长期记忆] 用户在做 6G 无人机项目`。

### 3.4 与现有记忆分层

```
短期记忆（现有，易失）          长期记忆（新增，持久）
├─ _history（对话连贯）         ├─ 实体事实（SQLite，精确）
└─ reflection（工具选型）        └─ 记忆描述（Chroma，语义召回）
     ↓ 本次会话内                    ↓ 跨会话累积
        └──────── 一起注入 ReAct 决策 prompt ────────┘
```

## 六、优先级与代价

- **优先级**：★★★★ 真补短板，且与现有向量栈契合度高。
- **代价**：新增抽取的 LLM 调用（成本/延迟，可异步）；记忆质量依赖抽取 prompt；需处理记忆更新/去重/过期（如用户改口）。
- **收益**："跨会话实体记忆"是高级 Agent 的标志能力，简历亮点明确。

---

## 七、风险与注意

- **记忆污染**：错误/过时记忆会持续误导后续回答，需设计更新与置信度机制（如同一实体新值覆盖旧值 + 时间戳）。
- **隐私与隔离**：记忆按用户隔离，防串户；敏感信息需评估是否该长期留存。
- **抽取成本**：每轮抽取会增加 Token 消耗，建议异步 + 批量 + 开关控制。
- **推理模型陷阱**：抽取/检索的 LLM 调用 `max_tokens` 给足（≥512），否则静默返回空（项目已知坑）。
- **降级**：记忆不可用时（DB 损坏/检索失败）静默跳过，不阻断主对话。

## 八、低成本高收益补充

### 8.1 轻量记忆淘汰与权重机制（大幅提升记忆质量）

不做复杂记忆管理，只加三条简单规则：

- **时间衰减**：召回打分时给旧记忆降权（如 `score × decay(age)`，3 个月以上显著降权），优先返回近期记忆，避免过时内容干扰。
- **置信度标记**：LLM 抽取时同步打 `confidence` 分（0~1），召回排序靠后低置信记忆，或只保留高置信实体。
- **记忆去重/更新**：抽取新记忆前先做相似度匹配（复用嵌入），命中相似项则**更新**（覆盖值 + 刷新时间戳）而非新增，避免记忆库冗余膨胀。

> `MemoryItem` 字段扩展：`confidence: float`、`updated_at`、`decay_weight`（召回时动态算）。

### 8.2 记忆类型分层 + 优先级注入（降幻觉）

长期记忆分三类，召回后按权重排序注入 Prompt（高权重在前）：

| 类型 | 权重 | 示例 |
|------|:---:|------|
| **用户画像类** | 最高 | "通信工程大三，求职 AI 方向" |
| **项目/实体类** | 中 | "在做 MCP+Skills 架构的 Agent 项目" |
| **历史结论类** | 最低 | "之前评估过混合检索收益高于纯向量" |

配合 Prompt 加一句护栏：**"仅参考与当前问题相关的长期记忆，无关内容直接忽略"**，大幅降低记忆污染导致的幻觉。`MemoryItem.mem_type` 字段承载分层。

### 8.3 MVP 分步落地（先跑通再迭代）

避免一上来做完整实体抽取，两步走：

- **V0.5 最简版（半天可落地）**：每轮对话结束生成**一句摘要**直接存 Chroma，检索按语义召回 Top3 注入。**不做实体抽取、不用 SQLite**。先验证"记忆对体验的提升"是否成立。
- **V1.0 完整版**：再加实体抽取、SQLite 结构化存储、8.1 的淘汰/权重/去重机制。

> 适合个人项目小步迭代——先用最小成本验证价值，再决定投入多少。对应 `MEMORY_BACKEND` 配置：V0.5 用 `chroma`，V1.0 切 `hybrid`。

### 8.4 短期→长期沉淀闭环（省 Token 且精准）

延伸 3.4 的"reflection 落盘"思路，做成**自动沉淀**而非每轮全量抽取：

- 监测短期记忆里的**高频模式**：用户连续 N 次使用某 Skill/工具 → 自动沉淀"用户偏好优先用 XX 工具"到长期记忆。
- 数据源：~~`reflection_memory` 已记录每次工具选型（`selected_tool`），统计频次即可触发沉淀~~
  → **已改为读工具审计日志**（`tool_audit.jsonl`，跨会话累积、按 user_id 隔离），**同样无需额外 LLM 抽取**。见 9.11。
- 形成 **"短期高频 → 长期沉淀"** 的记忆流转闭环：既省 Token（不每轮抽取），又精准（只沉淀真实高频行为）。

```
短期(reflection, 易失)  ──高频触发──▶  长期(持久)
  每次工具选型记录            连续3次用同一Skill
                              → 沉淀"用户偏好XX工具"
```

## 九、改造计划：会话记忆从「硬截断」到「摘要压缩」

### 9.1 问题

现有会话记忆（`unified_agent.py::_record_conversation`）是硬截断：

```python
self._history.append({"role": "user", "content": user_input})
self._history.append({"role": "assistant", "content": answer})
if len(self._history) > 20:
    self._history = self._history[-20:]      # 超出直接丢弃
```

三个问题：

| 问题 | 说明 |
|------|------|
| **早期上下文永久丢失** | 注意：**20 条消息 = 10 轮对话**（每轮 user+assistant 两条）。第 11 轮之前的全部内容被丢弃，不是"保留 20 轮" |
| **长任务中途失忆** | 用户第 3 轮设定的约束（如"只用中文回答""排除某部门文档"），到第 15 轮时已查不到，模型会违背早期约束 |
| **死配置** | `config.py::MAX_MEMORY_ROUNDS = 10` 原先**从未被读取**，代码硬编码 20。已于 9.5 修复（改为配置驱动，默认值下行为不变） |

### 9.2 目标

把「超出即丢弃」改为「超出即压缩」：早期对话由 LLM 压缩成 **500~1000 token** 的摘要，**保留核心决策与结论**；最近若干条保留原文（保真）。

### 9.3 设计

**触发时机**：历史超过阈值时触发一次压缩，压完长度回落，**不是每轮都压**（控制成本）。

**压缩策略**：
```
[最旧的 N 条]  ──LLM 压缩──▶  [摘要]     ← 释放 N 条，腾出空间
[最近的 M 条]                              ← 保留原文，保证近期上下文保真
```

**滚动压缩**（应对超长对话，防止摘要无限增长）：
```
第 1 次：summary₁ = compress(早期对话₁)
第 2 次：summary₂ = compress(summary₁ + 早期对话₂)    ← 旧摘要参与再压缩
```
旧摘要作为输入参与下一轮压缩，**摘要长度恒定**，不会随对话增长而膨胀。

**摘要存放**：新增实例属性 `self._session_summary: str`，**不污染 `_history` 的结构**（避免 role 混乱）。

**注入方式：单条 system，两块结构**

不新增多条 system 消息，而是把现有唯一一条 system 扩成两块：

| 块 | 内容 | 是否变化 |
|----|------|---------|
| 基础系统提示词 | 「你是 MCP Agent 平台智能助手。」 | 固定不变 |
| 【历史摘要】段落 | 压缩后的会话摘要 | 每 N 轮覆盖更新 |

- **更新策略**：每积攒 N 轮对话，重新合并、压缩摘要，**直接覆盖** system 内【历史摘要】段落
- **原始对话**保留固定窗口（`SESSION_SUMMARY_KEEP_RECENT`），**窗口外的对话丢弃，只保留摘要**
- 摘要段落独立于原始对话窗口，**不受窗口裁剪影响**

**实现方式（零破坏）**：`DecisionEngine` 实例由 `_run()` 每请求新建，Agent 在该实例上挂一个属性（`decision_engine.session_summary = self._session_summary`），决策引擎构建 system 时读取该属性拼装。
- **不修改任何函数签名**、不改变任何调用方式（符合零破坏原则）
- 决策引擎用 `getattr(self, "session_summary", "")` 读取，独立使用时自动降级为空

**摘要必须保留的内容**（写入压缩 Prompt 的指令）：
- 用户的核心诉求与目标
- 已确认的结论、决策、约束（如"只用中文""排除 X 文档"）
- 未完成的待办与进行中的任务
- 关键实体（项目名、专有名词、数字）

**可以丢弃的**：寒暄、重复确认、失败尝试的中间过程

**降级安全**：压缩调用失败 → **回退到现有硬截断**（保持原行为），绝不阻断主对话。

**成本**：一次额外 LLM 调用，`call_site="memory.compress"` 计入 `token_tracker`；因触发频率低（每积攒 N 条才一次），成本可控。

### 9.4 配置项设计

```python
# config.py

SESSION_SUMMARY_TARGET_TOKENS = 800   # 摘要目标长度（500~1000 区间中值）
SESSION_SUMMARY_MAX_TOKENS = 2000     # 压缩调用 max_tokens（推理模型需给足，否则 content 空）
```

> **配置合并说明**：原计划的 `SESSION_HISTORY_MAX` **取消**——它与 `MAX_MEMORY_ROUNDS` 管的是同一件事（对话窗口大小），保留两个会造成"改了这个那个不生效"的困惑。现统一由 `MAX_MEMORY_ROUNDS` 驱动（单位为**轮**，内部按 ×2 换算为消息条数）。

**零破坏保证**：`SESSION_SUMMARY_ENABLED=False` 时，行为与改造前**完全一致**（仍走硬截断）。

### 9.6 短期 → 长期：摘要驱动的记忆流转（推荐落地流程）

摘要不只是"塞进 system 就完了"——它同时是**长期记忆的抽取源**。每 N 轮形成一条完整流转链：

**第一步**：生成会话摘要 → 注入 system【历史摘要】（仅服务当前会话 = 短期记忆）
**第二步**：对该摘要做一次独立 LLM 抽取 → 只提长期有效信息，产出结构化实体
**第三步**：语义去重分流
- 实体**已存在** → 更新权重（正向强化）+ 刷新时间戳
- **全新实体** → 写入长期记忆库（初始权重 + 衰减系数）

**抽取口径**（与摘要本身的保留口径不同，这是关键区别）：

| ✅ 保留（长期有效） | ❌ 丢弃（短期无效） |
|-------------------|-------------------|
| 用户偏好 | 本次临时任务 |
| 固定参数 | 中间思考过程 |
| 业务规则 / 固定约束 | 一次性问答 |
| 高频工具选择经验 | — |

**为什么从摘要抽取、而不是从原始对话抽取**：
- **更省**：每 N 轮一次，而非每轮一次
- **更准**：摘要已过滤掉寒暄与中间过程，抽取信噪比更高

**与现有实现（V1.0）的差异（需改造）**：

| 维度 | 现状 | 新设计 |
|------|------|--------|
| 抽取源 | 每轮**原始对话** | 每 N 轮的**摘要** |
| 抽取频率 | 每轮 | 每 N 轮 |
| 遇到已存在实体 | **删旧存新**（`_delete_by_content` + 重新插入） | **权重正向强化** + 刷新时间戳（保留累积价值） |
| 记忆 ID | `md5(user_id\|content\|时间戳)` → 同内容不同时刻 ID 不同 | 需改为**稳定 ID**（不含时间戳），否则无法识别"同一实体" |
| 表结构 | 无 `weight` 字段 | 需新增 `weight` 列（承载累积强化） |

> ⚠️ **这是 schema 变更**：需给 `memory.db` 加 `weight` 列 + 把记忆 ID 改为稳定实体 ID。完整改造方案见 **9.7**。

**分层职责最终形态**：

```
会话摘要    ← 本次会话的连贯性（临时任务上下文）   → 注入 system【历史摘要】
长期记忆    ← 跨会话的稳定事实（用户画像/实体）    → 注入 hints
              （含工具选型经验——由审计日志判据沉淀而来，见 9.11）
```

两层职责不重叠：**摘要解决"本次会话记得住"，长期记忆解决"跨会话认得人"**。

> **变更（2026-09）**：原「反思记忆」一层已移除——实测匹配精度不足，且它沉淀的"用户偏好"实为 agent 自身选择（标签错位）。工具选型经验不再单独成层，而是**沉淀进长期记忆**，由长期记忆统一承载与注入。见 9.11。

### 9.7 实体 ID 与权重语义改造方案（已定）

9.6 的「权重正向强化」撞上现有实现的两个硬约束，必须一并改造。

**问题拆解**

| # | 问题 | 后果 | 本质 |
|---|------|------|------|
| ① | 记忆 ID = `md5(user_id\|content\|时间戳)`，**带时间戳** | 同一语义实体在不同时间插入 → ID 不同，系统只能当成两条独立记录，**权重无法累加更新** | 现在是**「事件 ID」，不是「实体 ID」** |
| ② | 表只有 `confidence`，没有 `weight`；重复策略是**删旧存新** | 与正向强化完全冲突——旧记录累积的权重直接丢失，永远无法增量叠加 | 两个字段语义被混用，职责未分开 |

**confidence 与 weight 的语义区分（必须分开，不可复用字段）**

| 字段 | 语义 | 性质 |
|------|------|------|
| `confidence` | 本次抽取时，模型认为这条实体是否可信 | **单次属性** |
| `weight` | 跨轮次累计的重要性、使用频次 | **长期累积属性** |

**方案：完整改造（推荐，生产级，需 DB 迁移）**

1. **实体 ID 生成规则**：`entity_id = md5(user_id + normalized_content)`
   - `normalized_content`：实体文本归一化（去多余空格、统一格式）
   - **去掉时间戳** → 同一用户下同一条实体永远得到同一个 ID
2. **新增 `weight` 浮点字段**，初始值 1.0
3. **插入逻辑改为**：
   - 先按 `user_id + entity_id` 查询
   - **已存在** → `weight += delta`（正向强化），可选刷新时间戳，**不删旧记录**
   - **不存在** → 新增记录，`weight = 初始值`
4. **存量处理**：数据迁移脚本——遍历存量记录，重新计算 `entity_id`，合并重复实体、合并权重（适合存量不多的场景）

**优点**：完全匹配记忆设计的「权重正向强化 + 时间衰减」，语义干净，后续扩展方便。

### 9.11 反思记忆移除 + 沉淀判据改造（2026-09）

#### 9.11.1 起因：实测反思记忆收益不成立

原 `reflection_memory.py` 是内存态 `deque(maxlen=50)`，记录每次工具选型（query / selected_tool / success / latency），用**字符 bigram Jaccard**（阈值 0.15）召回历史相似问题，格式化成提示注入决策 prompt。

拿 10 条历史选型 + 10 个新问题实测：

| 指标 | 实测值 |
|------|:---:|
| 触发率 | 40%（4/10 会注入提示） |
| 精度 | 75%（注入的提示里 1/4 是错的） |
| 召回率 | 60%（该匹配的漏了 2 个） |

错例：「今天股市怎么样」误召 `query_weather`；「南京冷不冷」「什么是向量数据库」漏召。

**根因是度量选错，不是阈值没调好**——分数分布完全重叠：

| 组 | Jaccard 分数区间 |
|------|:---:|
| 该召回 | [0.000, 0.500] |
| 不该召回 | [0.000, 0.200] |

且「今天股市怎么样」(0.200) 的分数**高于**真正的命中「什么是向量数据库」(0.143)。字符 bigram 无法表达语义（「南京冷不冷」与「上海今天热不热」共享二字组近乎为零），**任何阈值都无解**。

**第二个问题：标签错位。** 沉淀写入的是「**用户偏好**优先使用工具「X」」（`mem_type=profile`，注入权重最高 1.0），但工具是 **agent 自己选的**，不是用户表达的偏好——等于把 agent 的历史选择伪装成用户画像，再以最高优先级喂回给 agent，形成自我强化闭环。

#### 9.11.2 决策：整体移除，判据改读审计日志

| 消费方 | 原实现 | 处置 |
|--------|--------|------|
| 提示注入（历史选型→prompt） | `get_relevant_hints()` | **直接去掉**（实测精度不足）；长期记忆注入走同一条 hints 通道，质量高得多（向量召回 + 重排阈值） |
| 计数沉淀（高频→长期记忆） | 读内存 deque 计数 | **改读审计日志**（跨会话累积、按 user_id 隔离） |

> **前置改动**：审计记录原先**没有 user_id**，无法按用户聚合。已给 `log_tool_call` / `log_decision` 新增 `user_id` 可选参数（默认 `""`，旧调用点行为不变），由 `Scheduler.user_id` / `SkillExecutor.user_id` 透传。旧审计记录无该字段，计数时**不会被误算给任何用户**（向后兼容）。

#### 9.11.3 沉淀判据：计数 + 占比双条件

只按次数会出问题——「用过 3 个工具各 3 次」会写入 3 条**互相矛盾**的偏好。改为双条件：

```
回看该用户最近 MEMORY_SEDIMENT_WINDOW=100 次工具调用
沉淀条件：成功次数 ≥ MIN_COUNT(3)  且  占该用户成功调用比例 ≥ MIN_SHARE(0.5)
```

占比约束使同时达标的工具**至多 2 个**（各占比之和 ≤ 1），天然抑制矛盾偏好。

> 阈值来自实测：真实审计日志中 `query_weather` 88.9% / `search_knowledge_base` 11.1%，平均每次提问调 1.3 个工具——占比判据在本场景可有效区分主导与长尾。

#### 9.11.4 幂等写入（关键修复）

沉淀触发条件改为「从审计日志重新推导」后，原先依赖调用侧内存去重集合（`_sedimented`）的做法暴露缺陷：**该集合活在单个会话实例里，新会话即失效**，导致每个新会话重复调用 `record_tool_preference`。

实测后果（5 次调用）：

```
第 1 次 → 记录数=1  weight=[1.0]
第 5 次 → 记录数=1  weight=[5.0]
```

**记忆条目始终 1 条**（实体 ID 稳定 + 内容相同 → 精确命中），**真正在变的是 `weight`**——而 `weight` 语义是「跨轮次累计的**证据**」，不该随"被推导过几次"增长。更糟的是这些偏好是 `profile` 类型（注入权重 1.0），权重虚高会让它主导记忆注入。

修法：把判据从「**我这次会话沉淀过没有**」（内存态，跨会话失效）换成「**这条记忆在不在库里**」（持久态，天然幂等）：

```python
content = f"用户偏好优先使用工具「{tool_name}」"
if self._get_by_id(self._entity_id(user_id, content)):
    return                      # 已存在 → 直接返回
self._store_one(user_id, "profile", content, 0.7)
```

#### 9.11.5 验证

`test_sediment_audit.py` **23 项全过**，覆盖：user_id 写入、按用户聚合、跨会话累积、占比不足零沉淀、主导工具沉淀、**幂等（5 次调用仍 1 条 + weight 1.0）**、失败不计入、决策记录跳过、跨用户隔离、旧数据无 user_id 向后兼容、文件缺失、半行坏数据、空 user_id、审计未启用、长期记忆故障不抛出。

#### 9.11.6 遗留

「用户偏好优先使用工具「X」」这个**文案与 `profile` 类型仍有标签错位**（工具是 agent 选的，非用户偏好）。本次只修了「重复累加」与「互相矛盾」，**标签语义未改**——若要让 weight 反映真实频次，正确做法是用计数派生（如 `weight = count / threshold`），而非靠被推导次数。

## 十、与主流设计对照及短板（STAR）

> 把本项目的记忆实现，逐项对照主流 Agent 记忆机制的设计范式——**短期三策略**（消息裁剪 / 摘要压缩 / 选择性保留）、**长期两实现**（向量库语义召回 / 结构化精确存储）、**存取四因素**（Embedding 质量 / 分块策略 / 检索时机 / 混合检索）、**遗忘三策略**（时间衰减 / 显式覆盖 / 用户控制）。
>
> 结论先放这里：**主流范式共 10 项——本项目做到 6 项、半个 2 项、明确缺 2 项**；此外在范式之外做深 2 项（滚动压缩、压缩后校验）。缺的部分逐条写了原因，不留"看起来都有"的模糊地带。

### 10.1 S（情境）

记忆机制是 Agent 从"能演示"到"能用"的分水岭：短期记忆决定它能否撑住长任务，长期记忆决定它能否跨会话认得人。主流设计已沉淀出相对统一的范式（见上方括注）。

本项目初始状态是**金鱼记忆**——对话历史与工具选型都放内存，重启即丢，既无用户画像也无跨会话沉淀；短期记忆更是**超出窗口即硬截断**，早期约束（如"只用中文回答"）到第 15 轮就查不到。

### 10.2 T（任务）

补齐两层记忆，并**逐一核对主流范式的每一项**：能落地的落地、不适用或代价过高的明确标注。核心判断标准是「描述必须与代码实际能力对齐」——不为凑齐范式而写不存在的机制。

### 10.3 A（行动）

**短期记忆**：把「超出即丢弃」改为「超出即压缩」——早期对话由模型压成摘要，**旧摘要参与下一轮压缩**保证长度恒定；最近若干轮保留原文保真；压缩后**比对原文校验**，发现遗漏则带缺失项**定向重压**一次；压缩不可用时回退原有硬截断。

**长期记忆**：向量库（语义召回）+ 关系库（结构化字段与精确去重）双写落盘，按用户隔离；写入侧以**归一化实体 ID** 去重、**权重正向强化**（`weight += delta`，非删旧存新）、**改口覆盖**（语义命中但事实已变 → 新值优先、累积权重继承）、**时间衰减**维护质量；召回侧用**交叉编码器重排分**做相关性门槛。

**抽取源改造**：长期记忆的抽取从「每轮原始对话」改为「每 N 轮的会话摘要」——更省（每 N 轮一次 vs 每轮）、更准（摘要已滤掉寒暄与中间过程）。

**短→长沉淀**：从审计记录识别用户的高频**主导**工具，自动沉淀为长期偏好；判据为「成功次数 + 占比」双条件，写入幂等。

**移除反思记忆**（详见 10.6）。

### 10.4 R（结果）

- 长任务不再中途失忆（早期约束进入摘要并持续注入）。
- 跨会话认得人：进程重启后按用户召回其画像与项目背景。
- 记忆库不随重复对话膨胀（实体 ID 去重 + 改口覆盖）。
- 不相关内容不再硬塞进上下文（重排分门槛）。
- 记忆体系从「三层」收敛为**「会话摘要 + 长期记忆」两层**——工具选型经验不再单独成层，改由长期记忆承载。

### 10.5 逐项对照

**① 短期记忆管理策略**

| 主流策略 | 本项目 | 说明 |
|---------|:---:|------|
| 消息裁剪 | ✅ | `MAX_MEMORY_ROUNDS` 驱动，作为**降级兜底**（压缩失败才走） |
| 摘要压缩 | ✅ | 主力路径，`_compress_history` |
| **选择性保留** | ❌ | **无**。没有"按重要性标记、关键信息原样保留"的结构化通道 |
| *（滚动压缩）* | ✅ | 主流范式未提及——超长对话下摘要会无限膨胀，本项目让旧摘要参与再压缩，**长度恒定** |
| *（压缩后校验）* | ✅ | 对应主流"降低压缩丢信息风险"的思路；本项目实现为**定向重压**而非直接回退（理由见 10.7） |

**② 长期记忆存取四因素**

| 因素 | 本项目 | 说明 |
|------|:---:|------|
| Embedding 模型质量 | ⚠️ | **复用主库同一个嵌入模型，未针对记忆语料选型**——主库是长文档块，记忆是短句事实，未必最优 |
| 分块策略 | ✅ | **不适用**：记忆是原子句（一条一事实），天然规避了 chunk 断裂与重叠问题 |
| 检索时机 | ✅ | 每轮自动检索 + prompt 护栏（"仅参考相关的，无关忽略"）；放弃"模型主动触发"那一侧 |
| **混合检索** | ❌ | **记忆检索未接 BM25**。主链路 `hybrid_retriever` 有向量+BM25 混合，但**未复用到记忆**；工具名/项目代号这类专有名词，纯向量容易召不回 |

**③ 遗忘与更新**

| 策略 | 本项目 | 说明 |
|------|:---:|------|

| 用户控制 | ⚠️ | 仅支持**按用户整体清理**，**无逐条编辑/删除接口** |
| *（过期淘汰）* | ❌ | 只降权、不删除——长期不用的记忆仍留在库里参与召回竞争 |

### 10.6 为什么删掉「工具反思记忆」

原实现是一个内存态 `deque(maxlen=50)`，记录每次工具选型（query / 选中工具 / 成败 / 耗时），用**字符 bigram Jaccard**（阈值 0.15）召回"历史相似问题"，格式化成提示注入决策 prompt。**删除基于三项实测证据，不是主观取舍。**

#### 证据一：匹配精度不足，且调阈值无解

拿 10 条历史选型 + 10 个新问题实测：

| 指标 | 实测值 |
|------|:---:|
| 触发率 | 40%（10 个问题里 4 个会注入提示） |
| 精度 | **75%**（注入的提示里 1/4 是错的） |
| 召回率 | **60%**（该匹配的漏了 2 个） |

错例：「今天股市怎么样」误召 `query_weather`；「南京冷不冷」「什么是向量数据库」漏召。

进一步看分数分布，确认**根因是度量选错，而非阈值没调好**：

| 组 | Jaccard 分数区间 |
|------|:---:|
| 该召回 | [0.000, 0.500] |
| 不该召回 | [0.000, 0.200] |

**两组完全重叠**，且「今天股市怎么样」(0.200) 的分数**高于**真正的命中「什么是向量数据库」(0.143)。字符 bigram 表达不了语义——「南京冷不冷」与「上海今天热不热」共享二字组近乎为零。**任何阈值都无法分开。**

> 这与长期记忆检索遇到的问题同源：**度量选错时，调参没有意义**。长期记忆那边最终靠交叉编码器重排解决（见 10.5 ②），反思记忆这边因为没有等价的补救路径，直接移除。

#### 证据二：标签错位，形成自我强化闭环

沉淀写入的是「**用户偏好**优先使用工具「X」」，且 `mem_type=profile`——而 `profile` 在召回打分里的**类型权重最高（1.0）**。

但**工具是 agent 自己选的，不是用户表达的偏好**。等于把 agent 的历史选择包装成用户画像，再以最高优先级喂回给 agent 去影响下一次选择——**没有 ground truth 校正的自我强化循环**。

#### 证据三：两个消费方都能被现有能力替代

| 消费方 | 处置 | 理由 |
|--------|------|------|
| 提示注入（历史选型 → prompt） | **直接去掉** | 它注入的正是证据一里那 75% 精度的噪声；而长期记忆走**同一条 hints 通道**注入，质量高得多（向量召回 + 重排阈值） |
| 计数沉淀（高频 → 长期记忆） | **改读审计日志** | 原计数来自内存 deque，**随会话销毁**（`Agent` 实例是每 Streamlit 会话一个），"连续 3 次"实际只是"本标签页内 3 次" |

#### 删除的前置依赖（关键）

审计记录原先**没有 `user_id`**——而沉淀是按用户写的。所以顺序必须是：**先给审计补 `user_id` → 计数才能改读审计 → 反思记忆的 deque 才能删**。不补 `user_id` 就删不掉，因为它是当时**唯一持有「(用户, 工具, 成败) 三元组」的地方**。

补字段时保持向后兼容：`user_id` 是可选参数（默认空串），旧调用点行为不变；**旧审计记录无该字段，不会被误算给任何用户**。

#### 顺带修掉的两个沉淀缺陷（见 9.11）

- **互相矛盾**：只按次数判定，「用过 3 个工具各 3 次」会写入 3 条彼此冲突的"偏好" → 改为**计数 + 占比**双条件（占比之和 ≤ 1，同时达标至多 2 个）。
- **重复累加**：判据改为"从审计重新推导"后，原先靠会话内内存集合去重会失效，每个新会话都重复写入、把 `weight` 一次次 +1（实测 5 次调用 → `weight=5.0`）→ 改为**幂等写入**（判据从"我这次沉淀过没有"换成"这条记忆在不在库里"）。

### 10.7 遗留短板

| # | 短板 | 现状 | 为什么不现在做 / 正确做法 |
|---|------|------|------------------------|
| 1 | **选择性保留**（短期） | 无 | 需要"哪些信息必须原样保留"的结构化标记；当前靠压缩 prompt 软约束，非代码层保证 |
| 2 | **记忆检索未接混合检索** | 纯向量 + 重排 | 主链路已有 `hybrid_retriever`，**复用到记忆是明确的下一步**（专有名词场景纯向量易漏） |
| 3 | **标签错位未修** | 「用户偏好优先使用工具「X」」+ `profile` | 工具是 agent 选的；应改为任务-工具映射语义 + 非 `profile` 类型（避免抢占最高注入权重） |
| 4 | **无逐条记忆编辑** | 仅按用户整体清理 | 需要管理界面与接口，属产品化工作 |
| 5 | **无过期淘汰** | 只衰减不删除 | 长期不用的记忆仍占召回竞争位；可加"衰减到阈值以下即归档" |
| 6 | **Embedding 未针对记忆选型** | 复用主库模型 | 需要评测对比才谈得上选型，当前规模不划算 |

> **关于"压缩后校验为什么是定向重压而非回退"**：主流思路是"校验失败则回退"。但本项目认为**回退到硬截断是净损失**——硬截断会丢掉全部早期上下文，而一个 90% 完好的摘要仍优于它。因此校验失败时**带缺失项重压一次**，仍失败才沿用原摘要（`SESSION_SUMMARY_VERIFY_FALLBACK_TRUNCATE=True` 可恢复主流的"回退截断"行为）。这是有意偏离范式的一处，理由如上。
