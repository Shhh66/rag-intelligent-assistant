# 查询改写（Query Rewrite）计划

> 本文档描述 RAG 检索前的**查询改写**能力的现状、目标与落地计划。
> 核心命题:**用户问得好不好,直接决定检索命中率**。在检索前用大模型先优化用户提问,能显著提升模糊、口语化、多轮指代类问题的召回。

---

## 一、现状分析:目前只有"中译英翻译",没有真正的查询改写

当前检索链路在检索前的唯一 LLM 处理,是 [retriever.py](rag_assistant/retriever.py) 的 `_translate_query_for_search()`:

```python
def _translate_query_for_search(query: str) -> str:
    """将中文查询翻译为英文关键词，提升英文文档检索命中率"""
    # prompt: "将以下中文问题翻译为适合英文文档检索的英文关键词（5-10个词）"
```

它的作用与局限:
- ✅ **做到了**:把中文问题译成英文关键词,喂给"英文那一路"向量检索,提升跨语言命中(中问英答)。
- ❌ **没做到**:
  - 不澄清**模糊/口语化**提问(如"那个能量消耗问题咋回事")
  - 不做**查询扩写**(同义词、子问题拆解)
  - 不做 **HyDE**(生成假设答案再检索)
  - 不处理**多轮指代**(如"它呢""那这个方案的缺点")

**结论**:现状是最初级的"跨语言 query 变换",**不是**需求所指的"大模型先优化用户提问再检索"。查询改写属**未实现**。

---

## 二、为什么需要查询改写

检索质量的上限由 query 质量决定。真实用户的提问常常:
- **模糊/省略**:"这个方案缺点是啥" —— 缺主语,向量检索抓不到重点。
- **口语化**:"咋回事""为啥用不起来" —— 与文档正式书面语的向量距离远。
- **多轮指代**:"它的能耗呢" —— 单独看这句无法检索,需结合上文补全。
- **过窄/过宽**:一个问题其实包含多个子问题,单向量召回覆盖不全。

查询改写让 LLM 先把"人话"翻译成"适合检索的规范化 query",**直接抬高召回命中率**,且改动小、见效快——性价比最高的检索侧优化之一。

---

## 三、目标能力(分层,按性价比排序)

| 能力 | 说明 | 复杂度 | 优先级 |
|------|------|:---:|:---:|
| **① 查询规范化/澄清** | 口语化、模糊提问 → 清晰、书面化、含关键实体的检索 query | 低 | ⭐⭐⭐ |
| **② 多轮指代消解** | 结合对话历史,把"它/这个"补全为完整实体 | 低-中 | ⭐⭐⭐ |
| **③ 查询扩写(Multi-Query)** | 一个问题生成 2~3 个不同角度的等价 query,分别检索后合并 | 中 | ⭐⭐ |
| **④ HyDE(假设文档嵌入)** | LLM 先生成一段"假设答案",用它的向量去检索(答案与文档更同分布) | 中 | ⭐ |

---

## 四、落地设计(增量,不破坏现有链路)

### 4.1 新增统一入口 `query_rewriter.py`

```python
# query_rewriter.py（新文件）
def rewrite_query(query: str, history: list = None, mode: str = "clarify") -> str | list[str]:
    """检索前的查询改写统一入口。
    mode="clarify"     → 返回单条规范化 query（能力①②）
    mode="multi"       → 返回多条等价 query 列表（能力③）
    mode="hyde"        → 返回假设答案文本（能力④，供向量检索用）
    失败或超时 → 原样返回原 query（无感降级，绝不阻断检索）
    """
```

- 复用现有 DeepSeek 端点(`config.GROQ_API_KEY / GROQ_BASE_URL / LLM_MODEL`),`temperature=0` 保证稳定,`max_tokens` 小(改写输出短、成本低)。
- 复用 [token_tracker.py](rag_assistant/token_tracker.py) 的 `get_tracker().record()` 记账,与全链路成本追踪一致。

### 4.2 接入点

在 [retriever.py](rag_assistant/retriever.py) 的 `answer_with_fallback` / `retrieve_and_answer` **检索之前**插入改写步骤:

```
用户 query
   │
   ▼
rewrite_query(query, history)   ← 新增(能力①②,规范化+指代消解)
   │  改写后 query
   ▼
[现有] 向量检索(+ 未来 BM25 混合检索)
   ▼
[现有] 双语翻译检索 / 重排 / 生成
```

- **与现有双语翻译共存**:`_translate_query_for_search` 保留(跨语言用),查询改写在其**之前**,先把 query 变清晰,再翻译检索,两者叠加。
- **多轮指代**的 `history` 从 `mcp_unified_agent/` 的对话记忆取(已有 `MAX_MEMORY_ROUNDS` 机制)。

### 4.3 Multi-Query / HyDE(进阶,可选开关)

- **Multi-Query**:`rewrite_query(mode="multi")` 生成 N 条 query → 每条走检索 → 结果并入现有"合并去重"逻辑 → 交给重排精排。天然复用现有合并+重排管线。
- **HyDE**:`rewrite_query(mode="hyde")` 生成假设答案 → 用其 embedding 检索。对"文档是陈述句、问题是疑问句"的分布差异有奇效。

### 4.4 配置项

```python
# config.py 新增
QUERY_REWRITE_ENABLED = True         # 查询改写总开关
QUERY_REWRITE_MODE = "clarify"       # clarify | multi | hyde
QUERY_REWRITE_MULTI_N = 3            # multi 模式生成的 query 数
QUERY_REWRITE_MAX_TOKENS = 100       # 改写输出上限（短，控成本）
QUERY_REWRITE_CACHE_SIZE = 100       # 改写结果 LRU 缓存条数（0=关闭，见 8.1）
QUERY_REWRITE_COREF_ROUNDS = 3       # 指代消解引用的最近对话轮次（见 8.2）
```

## 五、无感降级(与项目降级哲学一致)

查询改写**绝不能阻断检索**。任何失败(超时/异常/空返回)都**回退原始 query**:

```python
try:
    rewritten = rewrite_query(query, history)
    if not rewritten or not rewritten.strip():
        rewritten = query          # 空返回回退
except Exception:
    rewritten = query              # 异常回退
```

这与项目现有的"Skill 未命中降级 ReAct""重排失败降级原始排序""翻译为空跳过英文检索"等降级链一脉相承。

## 六、与评测体系联动验证

查询改写的价值用 RAGAS 评测量化(见 `RAG评测体系.md`):
- 新增 A/B 配置:`无改写` vs `有改写(clarify)` vs `有改写(multi)`,其余条件一致。
- 核心看 **`context_recall`**(模糊问题召回是否变全)与 **`answer_relevancy`**(答案是否更切题)。
- 测试集里的 **`fuzzy`(边缘模糊)** 分层最能体现改写增益——现有 13 题里的"那个能量消耗问题咋回事""为啥AI飞控用不起来"正是典型模糊题,可直接作对照。

## 七、优先级与代价

- **收益**:模糊/多轮/口语化问题命中率提升,是"Query Rewrite"这一常见 RAG 优化点的硬落地;改动集中在**检索入口前**,对检索/重排/生成零侵入。
- **代价**:每次检索前多一次 LLM 调用(延迟 + 少量 Token);Multi-Query 会成倍增加检索次数(但可并行)。
- **建议顺序**:先做 **① 规范化 + ② 指代消解**(改动最小、覆盖最广、对多轮对话收益直接),验证有效后再上 **③ Multi-Query**,最后视需要做 **④ HyDE**。

---

## 八、低成本优化补充(锦上添花,优先级不高)

以下四项是对查询改写的增强,按"性价比 / 何时做"排序,不影响主功能先行落地。

**① 轻量改写缓存(成本极低,省 Token,随主功能顺手做)**
加一个 LRU 缓存(存最近 `QUERY_REWRITE_CACHE_SIZE=100` 条 query 的改写结果),相同 query 直接返回缓存,不再调 LLM。对**重复提问、多轮追问相似问题**的场景省下可观的改写 Token。实现极简:Python 标准库 `functools.lru_cache` 或一个 `OrderedDict`。注意:**带对话历史的指代消解结果不宜缓存**(历史一变结果就变),只缓存无历史的 `clarify`/`multi` 纯 query 改写即可。

**② 指代消解单独限制历史轮次(省 Token + 提升准确性)**
指代消解不需要全部对话历史,单独设更小轮次 `QUERY_REWRITE_COREF_ROUNDS=3`(最近 2~3 轮)。太久远的上下文会引入无关信息、干扰改写准确性,同时压缩 Prompt 长度省 Token。注意与全局 `MAX_MEMORY_ROUNDS`(10)区分——**记忆用 10 轮,指代消解只取尾部 2~3 轮**。

**③ 改写结果埋点,对齐 Bad Case 分析(强烈建议,几乎零成本)**
在日志里记录「原 query → 改写后 query」映射。后续做 bad case 分析时能**快速区分"是改写的问题还是检索的问题"**,与现有错误分析体系(见 `RAG评测体系.md` 第七章 Bad Case)对齐,也便于迭代改写 Prompt。可直接复用现有 [evaluation.py](rag_assistant/evaluation.py) 的 QA 日志或 `token_tracker` 的 `call_site` 机制,新增一个字段即可。

**④ Multi-Query 语义去重(可选)**
`mode="multi"` 生成的多条等价 query 可能高度重复,送检索前加一步轻量去重:规则过滤(编辑距离/前缀)或复用现有嵌入算相似度,滤掉高度相似项,避免无效检索浪费算力。属可选优化——生成数 N 本就不大(默认 3),收益有限,规模化或发现重复严重时再做。

**小结**:③埋点强烈建议(对齐现有 Bad Case 体系、几乎零成本)、①②随主功能实现时留好配置(已在四.4 预留)、④按需可选,避免过早优化。
