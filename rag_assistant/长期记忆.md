# 长期记忆计划（跨会话实体记忆与检索）

> **实现状态（2026-07）**：✅ **V0.5 + 部分 V1.0 已实现并验证**（跨会话持久化 + LLM 实体抽取 + 按用户隔离 + 语义检索注入 + 去重/权重 + 短→长沉淀闭环）。
> 定位：真补强——现有记忆是纯内存、重启即丢，补上"跨会话持久化 + 实体记忆检索"能让 Agent 记住用户是谁、聊过什么。

## 已实现部分（本轮）

- **核心模块** `long_term_memory.py`：Chroma（语义召回，独立 `memory` collection）+ SQLite（`memory.db` 结构化镜像）双写；复用 `vector_store.get_embeddings()`，无新依赖。
- **实体抽取**：`extract_and_store` 每轮对话后 LLM 抽取 `{mem_type(profile/entity/conclusion), content, confidence}`（`max_tokens=512` 避推理模型空返回坑）；抽取为空时兜底存一句摘要（V0.5）。
- **检索注入**：`retrieve` 按 user_id 过滤 + query 语义检索 + **权重排序**（相关度 `1/(1+距离)` × 类型权重 × 置信度 × 时间衰减）；结果与 reflection hints **并列注入** `_pipeline` 决策 prompt。
- **用户隔离**：`retriever.set_current_user()` 写共享文件 `memory_user_context.json`（仿 kb 权限模式），跨进程按 username 隔离，防串户。实测 bob 检索不到 alice 记忆。
- **去重更新**：抽取前语义查最近似记忆，相似度 ≥ `MEMORY_DEDUP_SIM` 则覆盖旧值+刷新时间戳，避免膨胀。
- **短→长沉淀闭环**：`_maybe_sediment_preference` 复用 reflection 的 `selected_tool`，某工具成功用满 3 次自动沉淀"用户偏好优先用 XX 工具"，**无需额外 LLM**。
- **Prompt 护栏**：注入时加"仅参考相关长期记忆，无关忽略"降幻觉。
- **降级安全**：`LONG_TERM_MEMORY_ENABLED=False`/DB异常/抽取失败 全静默跳过，不阻断主对话。
- **距离分陷阱**：本地嵌入的 `relevance_scores` 会返回负值（同 reranker logits 问题），改用 `similarity_search_with_score` 距离分转 `1/(1+dist)`。
- ✅ 验证：进程A（alice 说"在做6G无人机ISAC项目"）→ 重启进程B → alice 问"物理层安全和我研究方向的关系"→ 答案自动带项目背景（跨会话记忆生效）。

## 一、现状分析

| 记忆类型 | 现状 | 证据 |
|---------|------|------|
| 工具选型记忆 | 内存 `deque(maxlen=50)`，**重启即丢** | `reflection_memory.py::ReflectionMemory`，字符 bigram Jaccard 召回 |
| 对话历史 | 实例属性 `_history`，**重启即丢** | `unified_agent.py` `self._history`（上限 20 条） |
| 跨会话记忆 | **无** | 进程重启后一切归零；无用户画像、无历史实体沉淀 |
| 持久化 | **无** | 两者都在内存，`clear_memory()` 一调即空 |

**核心缺口**：Agent 是"金鱼记忆"——每次重启、每个新会话都从零开始。用户上次说过"我在做 6G 无人机项目"，这次问"我的项目相关的物理层安全"时，Agent 无法关联。缺一个**跨会话、可检索、结构化**的长期记忆层。

---

## 二、目标能力

1. **跨会话持久化**：记忆落盘，进程重启/新会话仍可用。
2. **实体记忆**：从对话中抽取关键实体/事实（用户偏好、项目背景、历史结论），结构化存储。
3. **记忆检索**：新对话开始时，按当前 query 检索相关长期记忆，注入上下文，让回答带"记性"。
4. **分层不冲突**：短期记忆（现有易失 reflection/history）负责"本次会话连贯"，长期记忆负责"跨会话积累"，各司其职。

## 三、落地设计（引用现有代码）

### 3.1 存储层（复用现有基础设施）

两种复用路线，二选一：
- **路线 A（向量检索，推荐）**：复用现有 **ChromaDB + 嵌入模型**（`vector_store.get_embeddings()`），长期记忆作为独立 collection（如 `memory`），支持语义检索"相关记忆"。天然复用现有向量栈。
- **路线 B（结构化，SQLite）**：复用 `permission.db` 或新建 `memory.db`，按 `user_id / entity / value / timestamp` 存，适合精确键值型记忆（用户画像）。

建议：**A+B 混合**——实体事实存 SQLite（可精确查/更新），记忆的自然语言描述存 Chroma（可语义召回）。

### 3.2 记忆抽取

- **新建 `long_term_memory.py`**：`extract_entities(dialogue) -> list[MemoryItem]`，用 LLM 从一轮/多轮对话抽取值得长期记住的实体与事实（用户身份、项目、偏好、已确认结论）。
- 抽取时机：一次 `chat()` 结束后异步抽取（不阻塞回答），或达到 N 轮时批量抽取。
- **注意推理模型 max_tokens 陷阱**：`LLM_MODEL=deepseek-v4-flash` 是推理模型，抽取调用须给足 `max_tokens`（≥512），否则 content 空（本项目已踩过此坑，见 CLAUDE.md）。

### 3.3 记忆检索与注入

- **新建 `retrieve_memory(query, user_id) -> list[str]`**：会话开始时按 query 语义检索 Top-K 长期记忆。
- **注入点**：`unified_agent.py::_pipeline()` 构造 prompt 时，与现有 `reflection` hints 并列注入（`prompt_templates.py`），格式如 `[长期记忆] 用户在做 6G 无人机项目`。

### 3.4 与现有记忆分层

```
短期记忆（现有，易失）          长期记忆（新增，持久）
├─ _history（对话连贯）         ├─ 实体事实（SQLite，精确）
└─ reflection（工具选型）        └─ 记忆描述（Chroma，语义召回）
     ↓ 本次会话内                    ↓ 跨会话累积
        └──────── 一起注入 ReAct 决策 prompt ────────┘
```

- 现有 `reflection_memory` 可选升级：`record()` 时同步落盘一份，重启后恢复（打通短期→长期）。

## 五、与现有体系联动

- **向量栈**：复用 `vector_store` 的 ChromaDB + 嵌入，不引入新向量库。
- **权限**：长期记忆按 `user_id` 隔离，复用 `api_server` 的用户体系，避免记忆串户。
- **可观测**：记忆抽取/检索作为 span 纳入 LangFuse（见 `可观测性LangFuse.md`）。
- **成本**：抽取的 LLM 调用经 `token_tracker` 记账（call_site="memory.extract"）。

## 六、优先级与代价

- **优先级**：★★★★ 真补短板，且与现有向量栈契合度高。
- **代价**：新增抽取的 LLM 调用（成本/延迟，可异步）；记忆质量依赖抽取 prompt；需处理记忆更新/去重/过期（如用户改口）。
- **收益**："跨会话实体记忆"是高级 Agent 的标志能力，简历亮点明确。

---

## 七、风险与注意

- **记忆污染**：错误/过时记忆会持续误导后续回答，需设计更新与置信度机制（如同一实体新值覆盖旧值 + 时间戳）。
- **隐私与隔离**：记忆按用户隔离，防串户；敏感信息需评估是否该长期留存。
- **抽取成本**：每轮抽取会增加 Token 消耗，建议异步 + 批量 + 开关控制。
- **推理模型陷阱**：抽取/检索的 LLM 调用 `max_tokens` 给足（≥512），否则静默返回空（项目已知坑）。
- **降级**：记忆不可用时（DB 损坏/检索失败）静默跳过，不阻断主对话。

## 八、低成本高收益补充

### 8.1 轻量记忆淘汰与权重机制（大幅提升记忆质量）

不做复杂记忆管理，只加三条简单规则：

- **时间衰减**：召回打分时给旧记忆降权（如 `score × decay(age)`，3 个月以上显著降权），优先返回近期记忆，避免过时内容干扰。
- **置信度标记**：LLM 抽取时同步打 `confidence` 分（0~1），召回排序靠后低置信记忆，或只保留高置信实体。
- **记忆去重/更新**：抽取新记忆前先做相似度匹配（复用嵌入），命中相似项则**更新**（覆盖值 + 刷新时间戳）而非新增，避免记忆库冗余膨胀。

> `MemoryItem` 字段扩展：`confidence: float`、`updated_at`、`decay_weight`（召回时动态算）。

### 8.2 记忆类型分层 + 优先级注入（降幻觉）

长期记忆分三类，召回后按权重排序注入 Prompt（高权重在前）：

| 类型 | 权重 | 示例 |
|------|:---:|------|
| **用户画像类** | 最高 | "通信工程大三，求职 AI 方向" |
| **项目/实体类** | 中 | "在做 MCP+Skills 架构的 Agent 项目" |
| **历史结论类** | 最低 | "之前评估过混合检索收益高于纯向量" |

配合 Prompt 加一句护栏：**"仅参考与当前问题相关的长期记忆，无关内容直接忽略"**，大幅降低记忆污染导致的幻觉。`MemoryItem.mem_type` 字段承载分层。

### 8.3 MVP 分步落地（先跑通再迭代）

避免一上来做完整实体抽取，两步走：

- **V0.5 最简版（半天可落地）**：每轮对话结束生成**一句摘要**直接存 Chroma，检索按语义召回 Top3 注入。**不做实体抽取、不用 SQLite**。先验证"记忆对体验的提升"是否成立。
- **V1.0 完整版**：再加实体抽取、SQLite 结构化存储、8.1 的淘汰/权重/去重机制。

> 适合个人项目小步迭代——先用最小成本验证价值，再决定投入多少。对应 `MEMORY_BACKEND` 配置：V0.5 用 `chroma`，V1.0 切 `hybrid`。

### 8.4 短期→长期沉淀闭环（省 Token 且精准）

延伸 3.4 的"reflection 落盘"思路，做成**自动沉淀**而非每轮全量抽取：

- 监测短期记忆里的**高频模式**：用户连续 N 次（如 3 次）使用某 Skill/工具 → 自动沉淀"用户偏好优先用 XX 工具"到长期记忆。
- 数据源现成：`reflection_memory` 已记录每次工具选型（`selected_tool`），统计频次即可触发沉淀，**无需额外 LLM 抽取**。
- 形成 **"短期高频 → 长期沉淀"** 的记忆流转闭环：既省 Token（不每轮抽取），又精准（只沉淀真实高频行为）。

```
短期(reflection, 易失)  ──高频触发──▶  长期(持久)
  每次工具选型记录            连续3次用同一Skill
                              → 沉淀"用户偏好XX工具"
```
