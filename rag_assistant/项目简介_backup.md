## 项目概述

基于 **MCP 协议**构建的可扩展 LLM 智能体框架。核心理念：Agent 不关心工具内部实现，只需一套标准协议即可将**任意业务系统**接入为可调用的工具。

**业务场景**：RAG 知识库问答 —— 用户上传私有文档（PDF/Word/TXT），系统自动解析、分块、向量化存入 ChromaDB，自然语言提问时 Agent 自动检索最相关片段 + LLM 生成回答，并标注引用来源。同时支持天气查询等外部 API 工具，Agent 自主发现工具、判断意图、编排调用。

### 技术成果

| 领域 | 实现 |
|------|------|
| **MCP 协议** | 自研 `UnifiedAgent` 通过 stdio 子进程启动 `mcp_server.py`，自动发现 5 个 MCP 工具（天气查询、知识库问答、语义检索、状态检查、对话记忆清空） |
| **ReAct 推理引擎** | 从 JSON 结构化决策演进为 Thought→Action→Observation 自然推理链，LLM 自主决定何时终止 |
| **Skills 技能层** | 声明式 Skill 定义（字典 → 零学习成本），3 个内置 Skill（综合查询、天气建议、深度检索），支持并行执行 + 失败降级 ReAct |
| **RAG 检索** | 双语检索（中/英）+ BGE-Reranker 重排 + LLM 兜底生成，Token 成本追踪 |
| **向量库管理** | ChromaDB 增量增删改 + 快照备份/回退 + `db_meta.json` 元数据索引 + CLI 管理工具 |
| **权限控制** | FastAPI + SQLite + JWT 鉴权，ChromaDB metadata 权限过滤（`kb_group` + `visibility`），Vue 3 管理后台 |
| **文档解析** | PyMuPDF 替换 PyPDFLoader，多栏检测、标题聚类、页眉页脚过滤、文本质量校验 |
| **前端** | Streamlit 对话界面（普通用户） + Vue 3 + Element Plus 管理后台（管理员） |

### 三层架构（面试重点）

```
MCP 工具层（锅碗瓢盆） → Skills 组合层（菜谱） → ReAct 决策层（厨师大脑）
```

| 层级 | 解决的问题 | 谁定义 | 示例 |
|------|-----------|--------|------|
| MCP 工具层 | 有什么能力可用 | 开发者 `@mcp.tool()` | query_weather, ask_knowledge_base |
| Skills 组合层 | 能力怎么组合用 | 业务 + 自动沉淀 | "综合查询"=天气+知识库并行 |
| ReAct 决策层 | 用户意图用哪个 | LLM 自主推理 | Thought→Action→Obs→Final Answer |

### 核心设计决策

1. **为什么不用 LangChain ReAct？** — 天然串行，失去并行能力。自研保留并行（"查天气 + 查知识库"同时调）
2. **为什么 Skill 声明式而非代码式？** — 零学习成本、可序列化存数据库、LLM 可自动生成
3. **Skill 匹配策略**：前置关键词+向量双重匹配 → Top3 交 LLM 确认 → 命中即 1 轮执行 → 未命中走 ReAct 兜底 → 失败无感降级
4. **为什么用 ChromaDB？** — 轻量级 `pip install` 即用，数据存本地文件夹，适合小项目和演示
5. **max_tokens 为什么设 4000？** — 安全网，防 LLM 输出截断导致并行工具调用写不完，非成本控制工具

## 先说一个最根本的问题：这个项目到底在干什么？

想象一个场景：你有一本 500 页的《人工智能入门》教材。

- **传统方式**：你想知道"什么是神经网络"→ 你翻目录 → 找到第 200 页 → 自己读 → 自己总结
- **你做的系统**：你把教材上传进去 → 系统自动"消化" → 你直接问"什么是神经网络" → 它告诉你在第 200 页有相关内容，并帮你总结好

这就是 **RAG（检索增强生成）** 的核心价值——让 AI 基于你的私有文件回答问题，而不是瞎编。

### 1. LLM（大语言模型）是什么？

**一句话**：LLM 就是一个"超级读了很多书的聊天机器人"。

它读了互联网上几乎所有的文章、书籍、代码，所以你跟它聊什么它都能接上话。但它有两个致命问题：
- 它的知识截止到训练时间（比如 2024 年），之后的不知道
- 它不知道你电脑里的私有文件（比如你公司内部的文档）

你项目里用的 DeepSeek 就是一个 LLM，相当于"大脑"。

### 2. 什么是 Prompt？

**一句话**：Prompt 就是你跟 LLM 说的那段话。

比如你问"什么是机器学习"，"什么是机器学习"就是 Prompt。

但你项目里的 Prompt 要复杂得多——你不会直接把问题发给 LLM，而是先查知识库，把查到的答案塞进 Prompt 里，然后再发给 LLM。这就是 **Prompt Engineering（提示词工程）**。

你在 `retriever.py` 里写的 `build_prompt` 函数，就在做这件事——组织一段包含检索结果的 Prompt。

### 3. 什么是 RAG（检索增强生成）？

**RAG = 检索 + 生成**

- **检索（Retrieval）**：用户问"什么是神经网络"→ 去知识库里搜，找到最相关的几个段落
- **增强（Augmented）**：把搜到的段落塞进 Prompt
- **生成（Generation）**：把 Prompt 发给 LLM，让它基于检索结果写回答

所以 RAG 本质上是：**先查资料，再回答问题**。就像考试开卷——不准瞎写，必须引经据典。

### 4. 什么是向量（Vector/Embedding）？

这是最容易被问到的概念。想象一个坐标系：

- "猫"可能被映射到 [0.8, 0.5, 0.3, ...]
- "狗"可能被映射到 [0.7, 0.5, 0.4, ...]
- "汽车"可能被映射到 [-0.2, 0.1, 0.9, ...]

"猫"和"狗"的向量很接近（因为它们都是宠物），而"汽车"的向量离它们很远（不相关）。

向量就是一堆数字，用来表示一段文字"在语义空间的位置"。语义相似的文字，向量也相似。

你项目里的 `all-MiniLM-L6-v2` 模型就在做这件事——把文字变成向量。

### 5. 什么是向量数据库（ChromaDB）？

普通数据库存的是"一行行数据"。向量数据库存的是"向量"，支持"查找最相似"的搜索。

**类比**：
- 普通数据库：`SELECT * FROM books WHERE title = '人工智能'`（精确匹配）
- 向量数据库：`找到与"什么是深度学习"最相似的 5 个段落`（语义相似）

你项目里的 ChromaDB 就是向量数据库，你问一个问题，它找到意思最接近的段落。

### 6. 什么是 Agent（智能体）？

**一句话**：Agent = 能自主做决策的 AI。

你手机上的 Siri 不是 Agent——它只是你说啥它做啥。

真正的 Agent 会：
- **感知**：接收用户的自然语言输入
- **决策**：统一走检索优先策略，LLM 自主判断相关性（`retriever.py`）
- **执行**：检索知识库 + LLM 生成回答，不相关则 LLM 兜底
- **记忆**：记住之前的对话（`memory_manager.py`）

你的项目就是一个 Agent——所有问题先查知识库，查到就引用，查不到就 LLM 直接回答并标注来源。

### 7. 什么是 LangChain？

LangChain 是一个 Python 库，封装了构建 AI 应用常用的功能，让你不用从零写。

你用 LangChain 做了：
- `langchain_huggingface` → 调用嵌入模型
- `langchain_chroma` → 操作向量数据库
- `langchain_core.documents.Document` → 统一文档格式

### 8. 什么是检索优先 + LLM 兜底？

用户的所有问题，系统统一走一条流程：
1. 中英文双语检索知识库（`retriever.py`）
2. 检索结果注入 Prompt，LLM 自主判断相关性
3. 相关 → 基于知识库回答 + 引用来源
4. 不相关 → LLM 用自己的知识回答 + 标注"由大模型直接生成"

这样避免了以前"意图识别误判"导致的问题（比如"你是什么模型"被判为查知识库，返回"未找到"）。

### 9. 什么是对话记忆？

没有记忆的对话：
> 你："什么是 Python？"
> AI："一种编程语言。"
> 你："它有什么优点？"
> AI：**"你问的'它'是什么？"**

有记忆的对话：
> 你："什么是 Python？"
> AI："一种编程语言。"
> 你："它有什么优点？"
> AI：**"Python 语法简洁，库丰富。"** ← 知道"它"是 Python

你的 `memory_manager.py` 保存最近 10 轮对话，让 AI 能理解"它"、"那个"这类指代词。

## 第三部分：常见面试问题速答

### Q1：你的项目用了什么技术栈？
"后端 Python + FastAPI + LangChain + ChromaDB + DeepSeek API。前端 Streamlit（用户端）+ Vue 3 + Element Plus（管理后台）。嵌入模型 paraphrase-multilingual-MiniLM-L12-v2（支持中英双语），重排用 BGE-Reranker-v2-m3 Cross-Encoder，本地运行不花钱。MCP 协议实现工具标准化接入。"

### Q2：为什么要用 RAG？LLM 自己不能回答吗？
"LLM 的知识有截止日期，而且不知道我的私有文档。RAG 把'检索'和'生成'解耦——先精确找到相关段落，再让 LLM 基于段落回答，相当于给 LLM 一本参考书让它照着回答，大大减少胡编乱造（幻觉）。"

### Q3：文本为什么要分块？不能整篇塞进去吗？
"每一块是一个独立的检索单元。如果整篇文章塞成一个向量，语义太模糊了。切成小块后，每个块代表一个具体的知识点，检索更精准。500 字和 50 字重叠是我设置的参数——重叠保证不会恰好把一句话切断。"

### Q4：为什么用 ReAct 而不是传统的意图分类？
"传统意图分类（if-else / 关键词 / 分类模型）太死板。'给我讲讲 RAG' 和 'RAG 是啥' 语义一样但关键词不同，分类模型容易误判。ReAct 让 LLM 自主推理——先 Think 用户想干嘛，再 Action 调工具，观察 Observation 后决定继续还是结束。而且 LLM 自主输出 Final Answer 来终止，不再依赖外部代码 `for turn in range(5)` 强行截断。"

### Q5：对话记忆怎么实现？
"我用一个 ConversationMemory 类，内部维护一个消息列表，最多保留 10 轮（20 条消息）。每次新消息进来，自动把最旧的移出去，防止记忆过长撑爆上下文窗口。"

### Q6：向量数据库为什么选 ChromaDB？
"因为是轻量级的，一个 pip install 就能用，不需要装 Docker 或服务端。数据存在本地文件夹里，适合演示和小项目。生产环境可以考虑 Milvus 或 Pinecone。"

### Q7：评测日志有什么用？
"记录每条问答的意图类型、检索片段数、响应延迟。通过分析日志可以发现：哪些类型的问题检索效果差？意图识别准确率多少？响应时间是否稳定？这对应 JD 里提到的'自动化评测与回测机制'。"

### Q8：如果要改进，你会做什么？
"已完成：① BGE-Reranker 重排提升检索精度；② 权限控制系统（FastAPI + JWT + ChromaDB metadata 过滤）；③ Skills 技能组合层；④ ReAct 推理引擎替换 JSON 决策；⑤ 文档解析 PyMuPDF 升级。后续方向：① 混合检索（BM25 关键词 + 向量语义）提升召回率；② 多轮 Query 改写（'那它呢' → 自动补全）；③ 用户反馈闭环（点赞/点踩 → 自动沉淀 Skill）；④ 检索效果 A/B 评测体系。"

## 第五部分：ReAct + MCP + Skills 架构设计（面试核心章节）

### 5.1 为什么需要三层架构？

**一句话回答**："在 MCP 工具层和 LLM 决策层之间加了一层 Skill 抽象，把高频工具组合沉淀为可复用的执行模板。"

**用做饭类比**：
- **MCP** = 厨房里的锅碗瓢盆（有什么工具可用）
- **Skills** = 菜谱（这些工具怎么组合用，宫保鸡丁不是每次从零发明）
- **ReAct** = 厨师的大脑（决定用什么菜谱、什么时候该出锅）

### 5.2 当前项目 vs 改造后

| 维度 | 改造前 | 改造后 |
|------|--------|--------|
| 决策方式 | JSON `{"action":"call_tools"}` | ReAct：`Thought → Action → Observation` |
| 何时停止 | 外部代码 `for turn in range(5)` | LLM 自主输出 `Final Answer` |
| 多工具调用 | LLM 每次从零推理组合 | Skill 命中 → 1 轮直接执行 |
| 高频场景 | 3-5 轮 LLM 调用 | 1 轮搞定（延迟降 50%+，Token 省 40-60%） |
| 失败处理 | 无降级，继续循环 | Skill 失败 → 无感降级到 ReAct 兜底 |
| 工具组合复用 | 无法复用 | 声明式 Skill，一次沉淀反复使用 |

### 5.3 核心设计决策（面试官可能追问）

**Q1: 为什么不直接用 LangChain 的 ReAct Agent？**

LangChain ReAct 天然串行（每步只调一个工具），会失去并行执行能力——"查天气 + 查知识库"变成顺序等待，延迟翻倍。且 LangChain Tool 需要手动注册每个工具，无法利用 MCP 的自动发现。

采用自研轻量 ReAct：保留并行执行能力，Promp 让 LLM 输出 Thought→Action→Observation 推理链，工具仍通过 MCP 自动发现。

**Q2: Skill 为什么用声明式（字典）而不是代码式（类）？**
- 学习成本为零：业务团队无需写代码，填字段即可
- 可序列化：可存入数据库、可视化编辑、LLM 自动生成（自动沉淀）
- 自动沉淀可靠：LLM 生成字典比生成代码语法错误概率低得多

**Q3: Skill 匹配怎么做的？误匹配怎么办？**
- 三重保障：关键词初筛 → 描述向量相似度排序 → Top3 交给 LLM 最终确认
- 负向关键词过滤（`exclude_keywords`）：问"天气API怎么开发"不会被误匹配到天气 Skill
- 置信度阈值可配：通用 Skill 设 0.4 提高命中，精准 Skill 设 0.7 避免误触发
- 匹配置信度不足时不强制执行，交给 ReAct 判断

**Q4: Skill 执行失败了怎么办？**

多层降级保障：
1. 参数缺失 → 反问用户补充（"请问你想查哪个城市？"）
2. 参数格式错误 → LLM 修正 1 次 → 仍失败 → 降级 ReAct
3. 单个工具失败 → 并行其他结果正常返回，串行返回已完成步骤
4. 整体 Skill 失败 → 无感降级到 ReAct 循环，用户无感知

**Q5: Skill 数量多了怎么办（Prompt 膨胀）？**

Prompt 中只放 Top3 候选 Skill，不放全量列表。前置向量匹配已完成筛选，不相关的 Skill 不会出现在 Prompt 里。后续支持千人千面的 Skill 可见性（不同租户/角色看到不同 Skill 列表）。

**Q6: Skill 怎么自动沉淀？质量怎么保证？**

沉淀门槛三重筛选：
1. 该工具组合历史执行成功率 ≥ 80%
2. 平均需要 ≥ 2 轮 ReAct 才能完成（确实能降本增效）
3. 必须能泛化出通用参数槽位（如识别"上海""北京"→抽象为 `{city}`）

自动生成 → 人工审核 → 灰度验证 → 全量发布/下线，完整闭环。

### 5.4 面试中展示项目时的话术建议

**30 秒版本**（自我介绍）：
"我独立开发了一个基于 MCP 协议的多工具智能问答系统。用户上传文档即可构建私有知识库，自然语言提问 Agent 自动选择最优策略。目前正在向 ReAct + Skills 三层架构演进，把高频工具组合沉淀为可复用技能。"

**2 分钟版本**（项目介绍）：
"这个项目的核心创新在于三层架构设计：

底层是 MCP 协议工具层，我实现了 5 个工具——天气查询、知识库问答、语义检索等，通过 `@mcp.tool()` 注册后 Agent 自动发现。新增工具只需加一个装饰器，Agent 代码零改动。

中间层是我正在构建的 Skills 技能组合层。每个 Skill 是声明式定义——描述、触发词、工具步骤、参数槽位。新增 Skill 和 MCP 加工具一样零摩擦，建个文件就行。

顶层是 ReAct 推理层，从原来的 JSON 结构化决策改为 Thought→Action→Observation 自然推理链。LLM 优先匹配 Skill，命中就 1 轮执行完毕；匹配不到走 ReAct 完整推理兜底。Skill 执行失败自动无感降级到 ReAct，用户感知不到。

这套架构让我从 5 轮 LLM 调用优化到 1 轮，延迟降低 50% 以上，Token 成本节省 40-60%。"

### 5.5 补充关键词中英对照（架构相关）

| 中文 | 英文 | 简单解释 |
|------|------|---------|
| 推理与行动 | ReAct (Reasoning + Acting) | LLM 一边推理一边调工具 |
| 技能组合 | Skill Composition | 把多个工具调用的固定流程打包 |
| 声明式技能 | Declarative Skill | 用字典定义技能，不写代码 |
| 工具编排 | Tool Orchestration | 决定哪个工具先调、哪个后调 |
| 自动沉淀 | Auto-Discovery / Auto-Curation | 系统自动把高频组合固化为技能 |
| 降级策略 | Fallback / Degradation | 某条路走不通时自动切换备选方案 |
| 熔断器 | Circuit Breaker | 下游故障率过高时自动切断保护 |
| 槽位填充 | Slot Filling | 从用户输入中提取参数填入技能模板 |
| 意图匹配 | Intent Matching | 判断用户想问什么、该用什么技能 |
| 多轮上下文 | Multi-turn Context | 利用对话历史补全缺失的参数 |
